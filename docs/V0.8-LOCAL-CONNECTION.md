# v0.8 — 공개 웹 화면과 로컬 Agent 연결 구조

PR #14 초판은 **https 로 배포된 RailFlow 페이지가 `http://127.0.0.1:4319` 의
로컬 Agent를 직접 호출**하는 구조였다. 이 문서는 그 구조가 왜 실제
브라우저에서 동작하지 않는지, 어떻게 바꿨는지를 기록한다.

---

## 1. 결론

**바꿨다. 이제 화면과 API가 같은 출처에 있다.**

```
바뀌기 전                                바뀐 뒤
https://…vercel.app  ──X──▶ 127.0.0.1    http://127.0.0.1:4319/      (화면)
   (브라우저가 막음)                       http://127.0.0.1:4319/api/… (API)
                                              └─ 같은 출처
```

Agent가 자기 화면(`agent/src/console-page.mjs`)을 직접 제공한다. 사용자는
`2-RailFlow실행.cmd` 를 누르면 되고, Agent가 기본 브라우저로 그 화면을 연다.

공개 배포본(Vercel)의 자동예약 탭은 **설치 방법과 상태 설명만** 한다.
로컬 Agent에 요청을 보내지 않는다 — 시도조차 하지 않는 것이 테스트로
고정돼 있다(`tests/e2e/live-agent-panel.spec.ts`).

---

## 2. 왜 https → localhost 가 막히는가

세 가지가 각각 걸린다. 하나를 해결해도 다음이 남는다.

### 2-1. Mixed Content

https 문서에서 http 하위 리소스 요청은 차단된다. `http://127.0.0.1` 도
예외가 아니다 — 브라우저는 `127.0.0.1` 을 "potentially trustworthy origin"
으로 취급하지만, 그건 **그 오리진이 보안 컨텍스트로 인정된다**는 뜻이지
https 문서가 그리로 평문 요청을 보낼 수 있다는 뜻이 아니다. Chrome은
localhost 대상 요청을 mixed content 차단에서 예외로 두지 않는다.

### 2-2. CORS

로컬 서버가 `Access-Control-Allow-Origin` 을 배포본 오리진으로 열어 줘야
응답을 읽을 수 있다. 그런데 그렇게 열면 **그 오리진의 아무 페이지나**
로컬 Agent를 부를 수 있게 된다. 실제 예약을 만들 수 있는 프로그램에
그런 문을 만드는 것은 받아들일 수 없다.

### 2-3. Private Network Access (PNA)

공개 오리진에서 사설/로컬 주소로 가는 요청에는 preflight 가 붙고
(`Access-Control-Request-Private-Network`), 로컬 서버가
`Access-Control-Allow-Private-Network: true` 로 답해야 한다. Chrome은 이
정책을 단계적으로 강화해 왔고, 버전과 설정에 따라 동작이 달라진다.
**버전에 따라 되기도 하고 안 되기도 하는 구조**를 정과장님 PC의 실증
경로로 삼을 수는 없다.

### 2-4. WebSocket

`wss://` 에서 `ws://127.0.0.1` 로도 같은 mixed content 제약이 걸린다.
그래서 WebSocket으로 우회하는 선택지도 없다. 현재 구조는 같은 출처의
짧은 주기 폴링을 쓴다(로컬 통신이라 비용이 없다).

### 2-5. 브라우저별 차이

Chrome/Edge(Chromium)와 Firefox, Safari의 PNA 적용 시점과 범위가 다르다.
**이 차이에 기대는 구조를 만들지 않는 것**이 이번 결정의 핵심이다.

## 3. 이 환경에서 실제로 확인한 것 / 확인하지 못한 것

### 확인한 것 (실제 Chromium)

| 확인 항목 | 결과 |
|---|---|
| 로컬 화면이 실제 브라우저에서 뜨는가 | ✅ `http://127.0.0.1:4321/` 정상 렌더링, JS 오류 없음 |
| 다른 출처에서 Agent API 호출 | ✅ **차단됨** — `http://localhost:9999` 페이지에서 `fetch` 시 `Failed to fetch` |
| 다른 출처에서 `/ping` 호출 | ✅ **차단됨** (CORS 헤더를 아예 내보내지 않음) |
| 토큰 없는 API 호출 | ✅ 401 `PAIRING_REQUIRED` |
| 교차 출처 + 올바른 토큰 | ✅ 403 `CROSS_ORIGIN_BLOCKED` (토큰이 맞아도 막힘) |
| 같은 출처 + 토큰 | ✅ 200 |
| 배포본 페이지가 로컬 Agent를 호출하는가 | ✅ **요청 0건** (Playwright 네트워크 감시) |

교차 출처 테스트는 **http → http** 다. 실제 배포본은 여기에 mixed content
까지 더해지므로 더 확실히 막힌다.

### 확인하지 못한 것

- **실제 https 오리진에서의 mixed content / PNA 동작**. 이 개발 환경은
  외부 https 사이트에 접근할 수 없어 실제 배포본 페이지를 브라우저로 열
  수 없었다. 위 2-1~2-3 은 브라우저 동작에 대한 설명이며, 이 환경에서
  재현한 것이 아니다.
- **Edge / Firefox / Safari에서의 동작.** 이 환경에는 Chromium만 있다.

> 다만 이 구조에서는 그 확인이 필요 없다. 배포본은 로컬 Agent를 호출하지
> 않고, 실제 조회는 같은 출처에서만 일어나기 때문이다. 확인하지 못한
> 항목이 실증 경로를 막지 않는다.

---

## 4. 하지 않은 것

- 브라우저 보안 설정을 낮추라고 안내하지 않았다.
- 인증서 경고를 무시하라고 하지 않았다.
- 브라우저 확장 프로그램을 요구하지 않았다.
- `--disable-web-security` 같은 플래그를 쓰지 않았다.
- 로컬에 자체 서명 https 서버를 세우지 않았다(인증서 경고가 생긴다).

---

## 5. 현재 구조의 보안 경계

| 경계 | 방법 |
|---|---|
| 외부에서 접근 | `127.0.0.1` 에만 바인딩. `0.0.0.0` 으로 열지 않는다 |
| 다른 사이트에서 호출 | `Origin` 헤더 검사. 자기 출처가 아니면 403 |
| CORS 우회 | `Access-Control-Allow-*` 헤더를 전혀 내보내지 않는다 |
| 다른 로컬 페이지에서 호출 | 실행마다 새로 만드는 토큰. 화면 HTML 안에만 있고 교차 출처에서는 읽을 수 없다 |
| iframe 삽입 | `X-Frame-Options: DENY` |
| 응답 캐시 | `Cache-Control: no-store` |
| 예약·결제 경로 | **존재하지 않는다.** 없는 경로는 404 (테스트로 고정) |

토큰은 파일로 저장하지 않으며, 사용자가 손으로 입력할 필요도 없다 —
Agent가 내보내는 화면에 이미 들어 있다.

---

## 6. 절충한 점

- **공개 배포본에서는 실제 조회 상태를 볼 수 없다.** 실제 상태는 로컬
  화면에만 있다. 배포본과 로컬 화면 사이에 상태를 동기화하려면 사용자의
  PC 데이터를 서버로 보내야 하는데, 그건 이 프로젝트가 하지 않기로 한
  일이다.
- **로컬 화면은 Next.js 앱이 아니라 Agent가 직접 만든 단일 HTML 이다.**
  사용자의 PC에서 Next.js 빌드를 돌리지 않아도 되도록 한 선택이다. 대신
  공개 배포본의 디자인 시스템을 그대로 쓰지는 못한다(색과 기본 형태만 맞췄다).
