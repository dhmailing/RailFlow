# RailFlow v0.7 — 자동화 경계(Automation Boundary)

이 문서는 "자동화가 실제로 무엇을 할 수 있고 무엇을 절대 할 수 없는가"를 코드 위치와 함께 명확히 한다. `lib/automation/**`를 수정하는 모든 사람이 이 경계를 먼저 읽어야 한다.

## 1. 절대 원칙

RailFlow의 자동화 Worker(Playwright 기반 `mock-browser` Provider)는 **RailFlow 자신이 소유·운영하는 주소만** 열 수 있다. 이것은 정책 문서의 약속이 아니라 코드 수준의 강제다: `lib/automation/host-guard.ts`의 `assertAutomationTargetAllowed()`가 화이트리스트 매칭에 실패하는 모든 주소를 예외(`AUTOMATION_TARGET_NOT_ALLOWED`)로 막고, 어떤 네트워크 요청도 보내기 전에 이 검사가 먼저 실행된다.

## 2. 허용 목록 / 차단 목록

| 구분 | 값 | 근거 |
| --- | --- | --- |
| 허용 | `http://localhost:3000`, `http://127.0.0.1`, `http://[::1]` | 로컬 개발 |
| 허용 | `https://<VERCEL_URL>` (Vercel 플랫폼이 이 배포에 직접 할당한 호스트명, 앱 설정으로 바꿀 수 없음) | 승인된 Preview 배포 자신 |
| 차단(명시적 방어심층) | `korail.com`, `letskorail.com`, `srail.or.kr`, `srail.co.kr`, `sr.co.kr`, `data.go.kr`, `kric.go.kr`(및 서브도메인) | 실제 철도/공공데이터 도메인 |
| 차단(그 외 전부) | 사설 프록시 주소, 임의의 IP 리터럴(모든 표기법 — WHATWG URL 파서가 정규화한 뒤에도 loopback 문자열과만 비교), 사용자 입력 URL, 위 두 목록에 없는 모든 도메인 | 화이트리스트 방식이므로 새 외부 도메인이 생겨도 별도 차단 규칙 추가가 필요 없다 |

**중요**: 이것은 화이트리스트 기반이다. 차단 목록은 방어심층(defense-in-depth)일 뿐이고, 실제 방어는 "이 두 허용 항목이 아니면 전부 거부"라는 화이트리스트 자체다.

## 3. 재검증 지점 (한 번이 아니라 두 번)

1. **탐색 전**: `buildAutomationTargetUrl()`이 목표 URL을 만들 때마다 `assertAutomationTargetAllowed()`를 통과해야 반환된다. 호출자는 URL/host/port를 절대 넘길 수 없다 — 오직 이 모듈이 이미 알고 있는 path+query만 넘긴다(§7 참고).
2. **탐색 후(리디렉션 대응)**: `page.goto()`가 리디렉션을 이미 따라간 뒤, `assertPostNavigationTargetAllowed(page.url())`로 최종 주소를 다시 검사한다. 최초 요청이 허용된 주소였더라도 그 응답이 외부로 리디렉션시켰다면 여기서 잡힌다.

DNS 재바인딩 방어를 별도로 구현하지 않은 이유: 허용되는 호스트가 `localhost`/`127.0.0.1`/`::1`(항상 로컬 루프백으로 해석됨)과 이 배포 자신의 Vercel 호스트명(Vercel 플랫폼이 라우팅을 통제함) 두 가지뿐이라, "정상적인 DNS 응답이면 안전하고 조작된 DNS 응답이면 위험한" 시나리오 자체가 성립하지 않는다.

## 4. 운영(Production) 무조건 차단

- `isRealProductionEnvironment()`(`lib/automation/feature-flags.ts`)는 `VERCEL_ENV === "production"`으로만 판정한다. `NODE_ENV`가 아니다 — Vercel Preview 배포도 Next.js를 "production" 모드로 빌드하지만(`NODE_ENV=production`), 이 PR의 요구사항은 승인된 Preview를 시연 대상으로 명시적으로 허용하기 때문이다. `VERCEL_ENV`는 Vercel 플랫폼이 직접 설정하며 앱 코드나 이 저장소의 어떤 환경변수로도 위조할 수 없다.
- `isRealProductionEnvironment() === true`이면 `SEAT_AUTOMATION_PROVIDER`/`ENABLE_SEAT_AUTOMATION_JOBS`/`ENABLE_MOCK_BOOKING_SITE` 값이 무엇이든 자동화 작업 생성·진행·Mock 사이트 노출이 전부 거부된다(503 `JOBS_DISABLED`, 또는 Provider가 `unavailable`처럼 동작). 임의의 환경변수 조작으로 우회할 수 없다 — 이 판정 자체가 코드에 하드코딩된 조건이다.

## 5. 실행 환경별 실제 동작 여부 (정직한 구분)

이 저장소는 **두 개의 서로 다른 빌드/배포 경로**를 갖고 있다(둘 다 이번 PR 이전부터 존재):

| 빌드 명령 | 산출물/런타임 | Playwright 실제 구동 가능 여부 |
| --- | --- | --- |
| `pnpm dev` / `next dev` (일반 Node.js 프로세스) | 로컬 Node.js 서버 | **가능** — Node.js 프로세스에서 `child_process`로 실제 Chromium을 띄울 수 있다. |
| `pnpm exec next build` + Node 서버(`vercel-build`가 쓰는 경로) | Vercel Serverless/Edge가 아닌 일반 Node 런타임 함수라면 **가능**. Vercel Edge Runtime으로 배포되면 **불가능**(Edge Runtime은 `child_process`가 없다). | 배포 설정에 따라 다름 — 이 PR은 어느 쪽으로 배포되는지 직접 확인하지 않았다. **확인 필요.** |
| `pnpm build`(`node scripts/run-framework.mjs build`, vinext → Cloudflare Workers, `wrangler`) | Cloudflare Workers 격리 환경(`nodejs_compat` 플래그를 켜도 실제 OS 프로세스 생성/`child_process.spawn`은 지원하지 않는다) | **불가능.** Workers 격리 환경 자체가 실제 브라우저 바이너리를 자식 프로세스로 실행할 수 있는 런타임이 아니다. |

이 표가 의미하는 것: **`mock-browser` Provider(실제 Playwright 자동화)는 이 저장소가 Cloudflare Workers로 배포하는 경로에서는 애초에 동작할 수 없는 기능이다.** 이는 추측이 아니라 이 세션에서 실제로 재현·확인한 사실이다:

- **재현한 결함**: `pnpm build`가 통과하도록 `playwright`/`playwright-core`를 external로 뺀 뒤 `pnpm dev`(이 레포의 로컬 개발 서버도 동일한 Cloudflare Workers/workerd 런타임으로 뜬다)로 자동화 라우트(`/api/automation-jobs/provider-status`)를 실제로 호출했더니, `SEAT_AUTOMATION_PROVIDER`를 기본값(`unavailable`)으로 둔 상태에서도 요청이 500으로 죽었다. 원인은 당시 `lib/automation/provider.ts`가 모듈 최상단에서 `mock-browser-provider.ts`(→ `playwright`)를 항상 즉시 import하고 있었기 때문이다: workerd 런타임은 `__dirname`(playwright-core가 내부적으로 쓰는 CJS 전역)을 지원하지 않아 `Error: __dirname is not defined`로 죽었다. **즉 이 문제는 Provider를 mock-browser로 켰을 때만 나는 게 아니라, 안전한 기본값(unavailable, 운영 환경의 항상-거부 포함)에서도 자동화 관련 라우트 전체가 이 런타임에서는 아예 응답하지 못하는 실제 회귀였다.**
- **적용한 수정**: `lib/automation/provider.ts`의 `getSeatAutomationProvider()`를 비동기로 바꾸고, `mock-browser-provider.ts`(및 `playwright`)를 `SEAT_AUTOMATION_PROVIDER=mock-browser`이고 `isAutomationProviderUsable()`이 참일 때만 `await import(...)`로 지연 로드하도록 바꿨다. 이 동적 import가 실패하면(바로 이 workerd 런타임처럼 애초에 로드가 불가능한 경우) 예외를 잡아 일반적인 `AutomationError("NOT_CONFIGURED", ...)`로 변환해 반환한다 — 처리되지 않은 크래시가 아니라, 다른 Provider 실패와 똑같은 방식으로 호출자가 이미 처리할 수 있는 오류가 된다.
- **수정 후 재확인**: 같은 `pnpm dev`(workerd) 서버에서 `/api/automation-jobs/provider-status`가 다시 `{"seatAutomationProvider":"unavailable", ...}`을 정상적으로(200) 반환하는 것을 확인했다.
- **확인하지 못한 것**: 이 dev 서버(Cloudflare Vite 플러그인)는 호스트 셸의 환경변수를 workerd 격리 환경의 `process.env`로 그대로 전달하지 않는다(실제 Cloudflare Workers도 동일 — `wrangler.toml`의 `vars`/Secret으로 명시적으로 등록해야 한다). 이 때문에 이 세션에서 `SEAT_AUTOMATION_PROVIDER=mock-browser`를 실제로 이 workerd 서버에 주입해 "동적 import가 실패 → catch → NOT_CONFIGURED 오류로 정상 응답"이라는 catch 경로 자체를 실제 요청으로 재현하지는 못했다(코드 검토와 `tsc`로만 확인). 이 catch 경로를 실제로 트리거해 보려면 이 레포의 Cloudflare Workers 설정에 `vars` 바인딩을 추가하는 별도 작업이 필요하며, 이번 PR 범위 밖으로 남긴다. **확인 필요.**

추가로:

1. 빌드 자체가 실패하지 않도록 `vite.config.ts`에 `playwright`/`playwright-core`를 rolldown external로 지정했다(코드가 그 패키지를 정적으로 번들링하려다 실패하는 문제를 막을 뿐, Workers 런타임에서 그 패키지를 실제로 동작하게 만들어주지는 않는다).
2. `isAutomationProviderUsable()`가 `false`인 모든 경우(기본값 `unavailable`, 또는 운영 환경) `mock-browser-provider.ts`의 코드는 이제 전혀 로드되지 않는다(동적 import 자체가 실행되지 않음).
3. 실제로 이 기능을 시연하려면 **Cloudflare Workers 경로가 아닌, Playwright가 실행 가능한 일반 Node.js 프로세스**(순수 `next dev`, 또는 Node.js 런타임의 Vercel Preview Serverless Function)에서 `SEAT_AUTOMATION_PROVIDER=mock-browser`와 `ENABLE_SEAT_AUTOMATION_JOBS=true`를 켜야 한다. 이 PR이 생성하는 Vercel Preview가 실제로 어느 런타임으로 API 라우트를 실행하는지는 **확인 필요**로 남긴다(최종 보고 참고).

## 6. Playwright가 조작할 수 있는 범위 (§4 요구사항)

- 오직 `data-testid="train-result"`/`"seat-status"`/`"purchase-button"`/`"reserve-button"`/`"reservation-result"` locator만 사용한다(`lib/automation/providers/mock-browser-provider.ts`). 좌표 클릭, OCR, 이미지 인식은 코드에 존재하지 않는다.
- Worker가 기록하는 값: job ID, 후보 열차 ID, 현재 단계(`status`), 시도 횟수(`attempts`), 마지막/다음 실행 시각, 좌석발견 시각, 구매클릭 시각, 예약완료 시각, 실패 코드(`lastError`), 결제기한(`AutomationJob` 타입, `lib/automation/types.ts`).
- 절대 기록하지 않는 값: 비밀번호, 쿠키, 세션 토큰, 카드정보. `scripts/verify-booking-simulator.cjs`가 소스 전체를 정적으로 검사해 이 문자열들의 저장 코드가 없음을 확인한다(§18).

## 7. 이 Provider가 절대 받지 않는 입력

`mock-browser-provider.ts`의 모든 public 메서드(`searchAvailability`/`clickPurchase`/`reserve`/`getReservation`/`cancelReservation`)는 `url`, `host`, `port` 파라미터를 받지 않는다 — 오직 `candidateId`/`idempotencyKey`처럼 이미 RailFlow 서버가 발급한 값만 받는다. 목표 URL은 항상 `buildAutomationTargetUrl()`이 내부적으로 구성하며, 이 함수 자체가 §3의 재검증을 통과해야 값을 반환한다. 따라서 API 호출자(클라이언트 UI 포함)가 임의의 URL을 이 Worker에게 열게 만들 수 있는 경로가 코드상 존재하지 않는다.

## 8. 금지 사항 (구현하지 않음, 앞으로도 구현하지 않음)

- 실제 코레일/SRT 조회·클릭·로그인, 비공개 API 추측·호출.
- 계정/쿠키/세션 정보 저장.
- CAPTCHA·대기열 우회, UA/IP/기기 위장, 프록시 로테이션, 탐지회피용 랜덤 지연·클릭.
- AccessibilityService 등을 이용한 외부 앱 화면 조작.
- 실제 결제, 카드정보 저장.

실제 외부 사이트 자동화가 어떤 이유로든 필요해지는 상황이 오면, 이 PR의 원칙에 따라 구현하지 않고 STOP하여 보고한다.
