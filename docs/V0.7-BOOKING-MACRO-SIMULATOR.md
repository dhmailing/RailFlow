# RailFlow v0.7 — 자동 좌석조회·예약 매크로 시뮬레이터

> 이 문서 작성 이후 실제 Preview 시연 가능성을 검증하는 후속 작업에서 로그인 없이 접근 가능한 공개 시연(`/demo/booking-automation`), 브라우저에 의존하지 않는 `mock-direct` Provider, 실제 Playwright E2E 테스트(`tests/e2e/**`)를 추가했다. 자세한 내용은 `docs/V0.7-PREVIEW-DEMO-AUDIT.md` 참고.

**실제 코레일·SRT 등 외부 철도 사이트는 이번에도 자동화하지 않았다.** 이 PR이 만든 "매크로"는 RailFlow 자신이 만든 가짜 예매 사이트(`/demo/booking-simulator`)만을 대상으로 실제 Playwright 브라우저 자동화를 수행한다. 목적은 "조건 등록 → 자동 감시 → 좌석 발견 → 자동 클릭 → 자동 예약 → 성공 알림"이라는 전체 흐름이 실제 브라우저 동작으로 성립함을 시연하는 것이다.

## 1. 새로 추가된 것

### 1-1. Mock 예매 사이트 (`app/demo/booking-simulator`, `lib/automation/mock-booking-site/**`)

- 열차 목록, 일반실/특실 잔여, 매진 여부, 구매 버튼, 예약 처리, 가상 예약번호(`RF-XXXXXXXX`) 발급, 결제기한, 예약 취소를 갖춘 서버 상태 기반(클라이언트 React state 아님) Mock 사이트다.
- 결정론적 시나리오 3개를 시드한다(`lib/automation/mock-booking-site/seed.ts`):
  - `mock-listing-1`: 항상 매진(`always_sold_out`).
  - `mock-listing-2`: 3번째 조회에서 일반실 1석 발생.
  - `mock-listing-3`: 5번째 조회에서 특실 1석 발생.
- 조회수는 실제 시간이 아니라 이 사이트 자신의 `checkCount`(조회 API를 부른 횟수)로 센다 — "몇 초 뒤"가 아니라 "몇 번째 확인에서"라는 요구사항을 그대로 반영한다.
- 필수 `data-testid`: `train-result`, `seat-status`(+`data-standard-seats`/`data-special-seats`/`data-definitive-sold-out`/`data-check-count`/`data-purchase-clicked`), `purchase-button`, `reserve-button`, `reservation-result`(+`data-reservation-number`/`data-payment-deadline`). 좌표 클릭·OCR·이미지 인식은 전혀 쓰지 않는다.

### 1-2. 자동화 도메인 모듈 (`lib/automation/**`)

`lib/watch/**`·`lib/reservation/**`와 완전히 독립된 새 모듈이다(파일 분리 패턴은 두 선례를 참고했지만 import는 하지 않는다). 유일한 예외는 `worker.ts`가 사용자 지시에 따라 `lib/watch/notification/adapters.ts`의 채널-비종속 InMemory Outbox Adapter를 재사용하는 것뿐이다(§18 테스트가 이 경계를 정적으로 검사한다).

- **`JobStatus`(17개 상태)**: `SCHEDULED → WATCHING → CHECKING_AVAILABILITY → SEAT_FOUND → PURCHASE_CLICKING → RESERVING → HELD → PAYMENT_PENDING → COMPLETED`, 실패/종료: `SOLD_OUT`, `RATE_LIMITED`, `AUTH_REQUIRED`, `PROVIDER_CHANGED`, `FAILED`, `CANCELLED`, `EXPIRED`, `PAYMENT_EXPIRED`. 전이는 한쪽 방향이며, `CANCELLED`/`EXPIRED`/`PROVIDER_CHANGED`로는 대부분의 활성 상태에서 진입할 수 있다. 유일하게 뒤로 가는 전이는 `PAYMENT_EXPIRED → WATCHING`("다시 감시")이다.
- **`SeatAutomationProvider` 인터페이스**(`searchAvailability`/`clickPurchase`/`reserve`/`getReservation`/`cancelReservation`)와 세 구현:
  - `unavailable-provider.ts`(기본값): 모든 메서드가 즉시 거부, 네트워크 요청 0건.
  - `official-stub-provider.ts`: 실제 철도사 연동이 확인되기 전까지 항상 `OFFICIAL_INTEGRATION_REQUIRED`로 거부, 네트워크 요청 0건.
  - `mock-browser-provider.ts`: 실제 Playwright(Chromium)로 `/demo/booking-simulator`만 조작한다(§2 참고).
- **`job-store.ts`**: CRUD + `claimJobStep`/`advanceClaimedStep`/`completeJobStep`(펜싱 토큰 기반 원자적 스텝 선점, `lib/watch/store.ts`의 알림 claim/complete CAS와 동일한 패턴)로 두 Worker가 같은 job의 `SEAT_FOUND → PURCHASE_CLICKING → RESERVING` 구간을 동시에 처리하지 못하게 막는다.
- **`worker.ts`**: 한 번의 `runStep()` 호출이 상태를 정확히 한 단계 진행시킨다("자동 매크로"는 클라이언트가 `intervalSeconds`마다 이 API를 반복 호출하는 것으로 구현되며, 서버 쪽에 자체 반복 루프나 타이머는 없다). 구매 클릭 사실과 예약 성공 사실은 서로 다른 상태(`PURCHASE_CLICKING`/`RESERVING`)로 분리 기록되며, `reserve()`가 실제로 성공 응답을 반환하기 전까지는 절대 `HELD`/`PAYMENT_PENDING`으로 넘어가지 않는다.

### 1-3. API 라우트 (`app/api/automation-jobs/**`, `app/api/automation/mock-site/**`)

작업 등록/조회/취소/재감시/결제확인/한 스텝 실행(`run-step`)과 Mock 사이트 자체의 조회/구매클릭/예약/취소 라우트. 전부 `requireAuth` + `assertTrustedOrigin` + Rate limit을 통과해야 하며, 운영(Production)에서는 자동화 관련 상태변경 라우트가 503(`JOBS_DISABLED`)을 반환한다.

### 1-4. UI (`components/automation/*`, `app/page.tsx`)

- `자동예약` 탭에 등록 폼(출발/도착/날짜/시간범위/인원/좌석등급/후보 다중선택/1~5초 간격/감시종료시간/시작 버튼)과 진행 중 작업 카드(감시 중인 열차, 상태, 마지막/다음 확인 시각, 시도 횟수, 좌석 상태, 자동 구매클릭 여부, 예약 결과, 결제기한 카운트다운, 중지/재감시/삭제)를 추가했다.
- 예약 성공 시 정확히 다음 형식으로 표시한다:
  ```
  예약 성공
  KTX 00305
  동탄 07:11 → 울산(통도사) 09:07
  일반실 1석
  가상 예약번호: RF-XXXXXXXX
  결제기한: 09:17:00
  ```
  다른 후보는 "다른 열차 예약 성공으로 자동 중단"으로 표시된다.
- 기존 `WatchJobsPanel`(v0.5 취소표 감시)은 그대로 유지되며, 새 `AutomationJobsPanel`이 그 아래에 추가로 렌더링된다 — 자동예약 탭의 기존 UX를 대체하지 않았다.

## 2. 실제 브라우저 자동화의 범위와 한계

- `mock-browser-provider.ts`는 실제로 Playwright `chromium.launch()`로 브라우저를 띄우고, `/demo/booking-simulator`를 실제로 열어, 화면의 버튼을 실제로 클릭한다. 좌표 클릭이 아니라 `data-testid` locator만 사용한다.
- **간격(1~5초)의 의미**: 사용자가 고르는 간격은 이 브라우저 자동화가 RailFlow 자신의 API(`run-step`)를 다시 부르는 주기다. 이 값은 RailFlow의 Mock Provider/`/demo/booking-simulator`/개발-테스트 환경에만 적용되며, 실제 외부 사이트에 대한 클릭 간격이나 탐지회피 패턴이 아니다.
- **이 저장소의 빌드 환경에서 실제로 확인한 것과 확인하지 못한 것**은 `docs/V0.7-AUTOMATION-BOUNDARY.md` §5("실행 환경별 실제 동작 여부")에 정직하게 구분해 두었다 — 특히 이 프로젝트의 `pnpm build`(vinext/Cloudflare Workers 빌드) 산출물은 Playwright가 실제 브라우저 프로세스를 띄울 수 없는 런타임이라는 점이 중요하다.

## 3. 필수 검증 스크립트 — `scripts/verify-booking-simulator.cjs`

CommonJS 오프라인 계약 테스트로, `global.fetch`/`XMLHttpRequest`/`WebSocket`을 감시해 0건임을 최종 확인한다. 실제 Provider(`mock-browser-provider.ts`)를 대체해 mock-booking-site 스토어를 직접 호출하는 가짜 `SeatAutomationProvider`를 사용한다 — "브라우저가 이 페이지를 읽고 클릭한다"의 계약(같은 HTTP 엔드포인트로 좌석 확인·클릭·예약)은 실제 Provider와 동일하되, 빠르고 결정론적으로 검증하기 위함이다. 실제 Playwright 브라우저 구동 자체는 이 스크립트가 아니라 별도의 수동/E2E 검증으로 확인한다(§4).

18개 필수 항목을 모두 구현했다: 상태 전이 전체 화이트리스트/거부, candidate 1 반복 매진, candidate 2/3 지정 회차 좌석 발생, 좌석발견→구매클릭→예약요청→가상 예약번호·결제기한 발급, 성공 후 나머지 후보 자동 중단, 두 Worker 동시 실행 시 예약 1건(claim 경쟁+펜싱 토큰), 동일 요청 재시도 시 예약 1건(idempotencyKey), Worker 재시작 후 상태 복원(만료된 claim 재획득), 만료된 작업 실행 차단, 외부 URL/리디렉션/도메인 차단(host-guard 3종), 실제 비밀번호·쿠키·카드정보 저장 0건(정적 소스 검사), 운영 환경 자동화 API 503, 기존 시간표/WatchJob/Demo 회귀 없음(정적 경계 검사 + `worker.ts` 예외 확인).

마지막 통과 결과: `{"result":"PASS","fetchCalls":0,"checkedFiles":29,"capturedLogLines":0}`

## 4. Playwright E2E(실제 브라우저) 검증 — 확인 필요 항목 명시

이 PR은 `playwright`(npm, devDependency, v1.63.0)를 실제로 추가했고, `lib/automation/providers/mock-browser-provider.ts`가 실제로 그 패키지의 `chromium.launch()`/`page.goto()`/`locator().click()` API를 호출하는 실제 코드로 구현되어 있다(§18 스크립트가 검사하는 것은 이 코드의 "계약"이며, 이 스크립트 자체가 브라우저를 띄우지는 않는다). 아래는 이 세션에서 실제로 실행해 확인한 것과, 실행하지 못해 "확인 필요"로 남긴 것을 구분한다.

- **확인함**: 이 샌드박스에 사전 설치된 Chromium(`/opt/pw-browsers/chromium`, revision 1194)을 `executablePath`로 직접 지정해 launch → 새 페이지 열기 → 텍스트 읽기까지 되는 것을 별도 스모크 테스트로 확인했다(playwright 패키지가 기대하는 기본 revision 1243과는 다르지만 실행 자체는 됨).
- **확인 필요**: 로컬에서 실제로 `pnpm dev`(또는 `next dev`)로 서버를 띄운 상태에서 "조건 입력 → 자동 감시 등록 → 자동예약 탭에서 자동 조회 → 좌석 발견 → 자동 구매클릭 → 자동 예약 → 다른 후보 자동 중단 → 결제기한 표시"까지 이어지는 실제 Playwright E2E 테스트는 이번 PR에 **작성하지 않았다**. 이유: (1) 이 레포의 `pnpm dev`가 Cloudflare Workers 로컬 에뮬레이션(Miniflare, `nodejs_compat`)을 통해 뜨는데, 이 세션에서 실제 서버 포트를 열고 유지한 채 별도 Playwright 클라이언트를 그 포트로 붙이는 전체 구성을 이 대화 턴 예산 안에서 안정적으로 반복 실행·디버그할 여유가 없었다. 대신 §3의 오프라인 계약 테스트로 동일한 상태 전이·동시성·보안 요구사항을 결정론적으로 검증했다. 실제 로컬 서버 구동 후 이 E2E를 추가로 작성·실행하는 것을 다음 작업으로 남긴다.

## 5. 아직 안 되는 것 (의도적으로 손대지 않음)

- 실제 코레일/SRT 좌석 조회·클릭·로그인, 실제 결제, 실제 계정/쿠키/카드정보 저장 — 전혀 구현하지 않았다.
- `official` Provider는 여전히 Stub이다.
- 예약 취소의 브라우저 자동화(`cancelReservation`)는 이번 PR에 포함하지 않았다(`capabilities().supportsCancellation === false`).
