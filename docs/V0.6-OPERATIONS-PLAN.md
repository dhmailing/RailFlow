# V0.6 실제 운영 인프라 전환 계획

이 문서는 계획서다. **이번 PR(v0.6)에서는 아래 어떤 인프라도 실제로 연결하지
않는다.** `SEAT_AVAILABILITY_PROVIDER`의 Production 기본값은 계속
`unavailable`이며, `AUTH_STORE`/`WATCH_STORE`도 계속 `disabled`가 기본값이다.
Demo Showcase(`/demo`, `docs/V0.6-OPERATIONS-PLAN.md`가 다루는 범위 밖의
클라이언트 전용 화면)는 이 계획과 무관하게 이미 별도로 동작한다.

관련 기존 문서: `docs/V0.5-SEAT-WATCH.md`(도메인 모델), `docs/adr/0001-*.md`
(Queue/Worker 저장소 1차 설계), `docs/adr/0002-*.md`(인증·알림 저장소 설계),
`db/postgres/`(스키마 SQL, 설계만 존재).

## 1. PostgreSQL Auth/Watch/Audit/Outbox Adapter 구현 순서

1. `lib/audit/postgres-store.ts` — 다른 두 저장소가 감사 이벤트를 기록할
   대상이므로 가장 먼저 만든다. `AuditStore` 인터페이스(`lib/audit/types.ts`)를
   그대로 구현하고, `audit_events` 테이블(`db/postgres/migrations/0001_init.sql`)
   에 쓴다.
2. `lib/auth/postgres-store.ts` — `AuthStore` 인터페이스 구현. 회원가입/로그인/
   세션 조회/계정 삭제가 각각 `lib/audit/postgres-store.ts`와 같은 트랜잭션
   안에서 감사 이벤트를 남기도록 만든다(§3, 아래 "같은 트랜잭션" 참고).
3. `lib/watch/postgres-store.ts` — `WatchStore` 인터페이스 구현(WatchJob/
   Device/NotificationDelivery/ConsentHistory). Outbox 패턴(`claim_token`
   CAS 조건 포함, `db/postgres/migrations/0001_init.sql`에 SQL 문서화됨)을
   실제 `UPDATE ... WHERE status='sending' AND claim_token=$1` 문으로 옮긴다.
4. 두 저장소 모두 완성된 뒤에만 `AUTH_STORE=postgres`/`WATCH_STORE=postgres`를
   실제로 selectable하게 만든다(`lib/auth/feature-flags.ts`,
   `lib/watch/feature-flags.ts`의 `isAuthStoreUsable`/`isWatchStoreUsable`을
   Postgres 연결 여부로 확장).
5. 계정 삭제 트랜잭션(§3 순서)과 알림 claim CAS부터 통합 테스트로 먼저
   검증한 뒤, 나머지 CRUD 경로를 순서대로 이전한다.

## 2. 마이그레이션 적용 및 롤백 방법

- `db/postgres/migrations/0001_init.sql`을 순서대로 실행하는 단일 진입점
  스크립트(`pnpm db:migrate`)를 추가한다. 개별 `.sql` 파일에 대응하는
  `*_down.sql` 롤백 파일을 반드시 함께 작성하고, "적용 전 상태로 완전히
  되돌릴 수 있는가"를 CI에서 적용→롤백→재적용으로 검증한다.
- 운영 적용은 항상 블루/그린이 아니라 **먼저 하위 호환되는 스키마 변경**만
  배포하고(예: nullable 컬럼 추가), 애플리케이션 코드가 새 컬럼을 실제로
  사용하기 시작한 뒤에야 NOT NULL 제약이나 컬럼 삭제 같은 되돌리기 어려운
  변경을 별도 마이그레이션으로 분리해 배포한다.
- 실패 시 즉시 롤백할 수 있도록 마이그레이션은 항상 트랜잭션 안에서
  실행하고(가능한 DDL만), 장시간 락을 유발하는 변경(대형 테이블 인덱스 생성
  등)은 `CREATE INDEX CONCURRENTLY`처럼 운영 트래픽을 막지 않는 방식을
  우선한다.

## 3. Queue/Worker 후보 비교

| 후보 | 장점 | 단점 | 비고 |
|---|---|---|---|
| Cloud Run Worker(또는 유사 서버리스 컨테이너) | 코드가 이미 Worker 모듈(`lib/watch/worker.ts`)로 분리돼 있어 이식 부담이 적음. 스케일 아웃/다운이 단순 | 상시 폴링 구조라면 유휴 시에도 최소 인스턴스 비용 발생. 자체 스케줄링(주기 실행) 별도 구성 필요 | 소규모로 시작하기 가장 단순 |
| Redis/BullMQ | 재시도·지연 작업·우선순위 큐가 라이브러리 수준에서 이미 제공됨. 처리량이 커져도 확장 용이 | Redis라는 새 유료/관리형 인프라가 추가됨(§9). 운영 대상이 하나 더 늘어남 | 알림 발송량이 커지면 유리 |
| PostgreSQL 기반 Job Queue(`SELECT ... FOR UPDATE SKIP LOCKED`) | 이미 도입할 PostgreSQL 하나로 저장소+큐를 겸함 -- 새 인프라 없음. Outbox와 큐잉을 같은 트랜잭션으로 묶기 쉬움 | 초당 처리량이 매우 높아지면 Redis 대비 성능 상한이 낮음 | **1차 권장**: 이번 PR의 Outbox/claim 설계와 가장 자연스럽게 이어짐 |

**권장**: 처음에는 PostgreSQL 기반 Job Queue로 시작하고, 실제 알림 발송량이
초당 요청을 기준으로 병목이 확인되면 그때 Redis/BullMQ로 교체한다(새 유료
인프라를 트래픽 근거 없이 먼저 들이지 않는다).

## 4. 서버리스 요청과 백그라운드 Worker 분리 구조

- API 라우트(`app/api/watch-jobs/**`)는 오직 "등록/조회/취소/재감시" 같은
  사용자 상호작용만 처리하고, 실제 좌석 확인·알림 발송은 절대 요청-응답
  안에서 동기 실행하지 않는다(현재도 `simulate` 라우트만 예외적으로 테스트
  용도로 한 단계를 즉시 실행함 -- 실제 Provider가 붙으면 이 라우트 자체를
  제거한다).
- Worker는 API 서버와 별도 프로세스/컨테이너로 배포하고, 오직 PostgreSQL
  Job Queue(§3)만 폴링한다. Vercel Serverless 함수는 상시 실행 프로세스를
  가질 수 없으므로 Worker는 Vercel 바깥(Cloud Run 등)에서 실행돼야 한다 --
  이는 `AUTH_STORE`/`WATCH_STORE`가 왜 Vercel Serverless에서 memory로
  "usable"하지 않은지와 같은 이유(인스턴스별 프로세스 메모리 격리)다.

## 5. 중복 실행 방지와 fencing token 적용

- 이번 PR에서 이미 구현한 `claimNotification`/`completeNotificationClaim`의
  `claim_token` CAS 패턴(`lib/watch/store.ts`, `db/postgres/migrations/0001_init.sql`
  주석)을 Postgres 어댑터에 그대로 옮긴다: `UPDATE notification_deliveries
  SET status=$1, claim_token=$2, locked_at=now(), lock_expires_at=$3 WHERE
  id=$4 AND status IN ('pending','failed') AND (lock_expires_at IS NULL OR
  lock_expires_at < now()) RETURNING *`.
- 좌석 확인(SeatAvailabilityProvider 실제 구현) 자체도 같은 패턴이 필요하다:
  WatchJob마다 "지금 확인 중"이라는 소유권을 먼저 획득한 Worker만 실제
  Provider를 호출하도록, `watch_jobs`에도 `check_claim_token`/
  `check_lock_expires_at` 컬럼을 추가해 알림과 동일한 CAS 규칙을 적용한다.
- 서비스 목표는 계속 **at-least-once**다(§6 참고, 기존 ADR 0002 §9와 동일한
  솔직한 한계). "정확히 한 번" 외부 호출을 주장하지 않는다.

## 6. 스케줄러 장애·재시작·재시도 처리

- Worker가 죽거나 재시작돼도 진행 중이던 claim은 `lock_expires_at`이 지나면
  다른 Worker가 자동으로 재획득한다(§5). 별도의 "죽은 Worker 감지" 로직이
  필요 없다 -- lease 만료가 그 역할을 한다.
- 재시도 횟수 상한(예: `attemptCount >= 5`)에 도달한 알림/좌석확인은
  `FAILED`로 못박고 더 이상 자동 재시도하지 않는다 -- 무한 재시도 루프
  금지(§13 "1~5초 간격으로 실제 철도 서버 반복 호출 금지"와 같은 원칙: 재시도도
  무제한이면 안 된다).
- Worker 자체의 헬스체크(예: 마지막으로 폴링한 시각을 별도 테이블/키에
  기록)와, 그 값이 오래되면 알리는 모니터링(§11 운영 로그와 연계)을 별도로
  둔다.

## 7. FCM/WebPush/Telegram/Email 연결 순서

1. **Email** 먼저 연결한다 -- 계정 없이 SMTP/트랜잭션 이메일 API(예:
   Resend, SES)만 있으면 되고, 이미 `NotConfiguredNotificationAdapter`
   인터페이스가 잡혀 있어 어댑터 하나만 교체하면 된다.
2. **Telegram** -- 봇 토큰 발급만 필요하고 사용자 소유권 확인(§ 아래
   "필요한 계정·키") 절차만 별도로 설계하면 됨.
3. **WebPush** -- VAPID 키 발급 및 브라우저 구독 저장이 필요하지만 앱스토어
   심사 등 외부 승인 절차는 없다.
4. **FCM** -- Android 네이티브 앱(§8)이 실제로 존재해야 의미가 있으므로
   Android MVP 이후로 미룬다.
- 채널마다 `Device.verified`(현재 이미 있는 필드, `lib/watch/types.ts`)를
  실제 소유권 확인 절차로 채운다: email은 확인 링크 클릭, telegram은
  `/start` 딥링크 후 대화 시작 확인 -- 이 절차가 없으면 §5 검토사항(타인의
  주소로 알림을 보내는 문제)이 재발한다.

## 8. Android 앱 전환 경로

`docs/ANDROID-MVP-PLAN.md`(v0.5)의 계획을 그대로 따르되, 이 PR과 관련해
갱신할 지점만 요약한다: 세션은 이미 쿠키/Bearer 토큰 양쪽을 지원하도록
설계돼 있으므로(`lib/auth/session.ts`) Android는 Bearer 토큰 경로만 쓰면
된다. FCM 연결(§7-4) 이후에야 실제 Android 알림이 의미가 있다.

## 10. 필요한 계정·키·도메인·권한

- PostgreSQL 호스팅 계정 및 `DATABASE_URL`(현재 `.env.example`에 자리만
  있음, 값 없음).
- Worker를 배포할 컨테이너 호스팅 계정(§4).
- 채널별: 이메일 발신 도메인의 SPF/DKIM 설정 권한, Telegram Bot 토큰,
  WebPush VAPID 키 쌍, (Android 이후) Firebase 프로젝트/FCM 서버 키.
- Production `APP_ORIGIN` 값은 이미 필요(§ CLAUDE.md, `lib/security/
  origin-guard.ts`) -- 커스텀 도메인을 쓰게 되면 그 값을 갱신해야 한다.
- **공식 좌석 Provider 연동 권한(§12)은 이 목록에서 가장 불확실한 항목이며,
  아직 어떤 형태로도 확보되지 않았다.**

## 11. 개인정보·보안·운영 로그 보존 정책

- 감사 이벤트(`AuditEvent`)는 계정 삭제 시 즉시 가명처리(공유 UUID)하며
  원본 매핑을 저장하지 않는다(이미 구현, `lib/audit/`) -- Postgres 전환 후에도
  이 규칙은 그대로 유지한다.
- 애플리케이션 로그에는 비밀번호/세션 토큰/알림 수신처 원문을 남기지 않는다
  (현재 `scripts/verify-seat-watch.cjs`가 이를 회귀 테스트로 고정하고 있음).
- 로그 보존 기간은 운영 착수 전 별도로 정해야 하는 미결 사항이다 -- 개인정보
  보호법상 목적 달성 후 지체 없이 파기 원칙에 따라, 감사 로그도 무기한
  보존하지 않고 보존 기간(예: N개월)을 명시한 뒤 자동 파기 배치를 둔다.
- 개인정보처리방침(`app/privacy/page.tsx`, 현재 초안)은 실제 Postgres/Queue
  연결 전에 반드시 법률 검토를 거쳐 갱신해야 한다(§13과 중복 강조).

## 12. 공식 좌석 Provider가 없을 때의 제한

**PR #6의 조사 결과(`docs/V0.4-INTEGRATION-RESEARCH.md`)에 따르면, 실시간
좌석 잔여 조회를 위한 공식 self-service API는 현재까지 확인되지 않았다.**
확인된 것은 코레일 승차권 진위확인 API(좌석 조회 아님)와 코레일×Klook 같은
개별 B2B 계약 사례뿐이다. 이 상태가 유지되는 한:

- `SeatAvailabilityProvider`의 Production 기본값은 계속 `unavailable`이어야
  한다 -- 이 계획서를 포함해 어떤 문서도 이 기본값을 바꾸는 근거가 되지
  않는다.
- Postgres/Queue/Worker(§1~§6)를 먼저 구축하더라도, 마지막 조각(실제 좌석
  확인)이 없으면 사용자에게는 여전히 `PROVIDER_UNAVAILABLE`만 보인다 --
  이 사실을 사용자에게 숨기지 않는다(§13).
- 공식 채널이 확인되기 전까지 비공식/비공개 API 리버스엔지니어링, 매크로,
  탐지 회피는 이 프로젝트에서 어떤 상황에서도 시도하지 않는다(원칙 유지).

## 13. 실제 예약 연동 전 별도 법률·약관 검토 항목

- 통신판매업 신고 필요 여부(RailFlow가 매개하는 거래의 성격에 따라 결정).
- 전자지급결제대행업(PG) 등록 필요 여부 -- 실제 결제를 대행/중개하지 않고
  "공식 사이트로 안내만" 하는 현재 설계를 유지한다면 불필요할 가능성이
  높지만, 자동화 수준이 올라갈수록(예: 자동 로그인 대행) 재검토 필요.
- 개인정보보호법상 처리방침 고지 사항 전체 항목 재검토(현재 초안, §11).
- 코레일/SR(코레일+) 이용약관상 자동화 도구 사용 제한 조항 확인 -- 위반
  시 계정 정지 등 사용자에게 미치는 영향을 사전 고지해야 한다.
- 이 항목들은 전부 **1차 조사 수준(PR #6)이며 원문 사이트 직접 확인이 아직
  안 된 상태**다 -- 실제 예약 연동 착수 전 반드시 원문으로 재확인한다.

## 14. 배포 단계별 Go/No-Go 체크리스트

1. **Postgres 연결(§1~§2)**: 마이그레이션 적용/롤백 리허설 통과 +
   계정삭제·가명처리 트랜잭션 통합테스트 통과 → Go.
2. **Queue/Worker 배포(§3~§6)**: 재시작 시 claim 재획득 테스트, 재시도 상한
   테스트, Worker 헬스체크 알림 확인 → Go.
3. **알림 채널 연결(§7)**: 채널별 소유권 확인 절차 구현 및 오배송 0건 확인
   (테스트 계정 기준) → 채널별 개별 Go.
4. **공식 좌석 Provider 연동(§12)**: **공식·승인된 연동 방식이 실제로
   확인되기 전까지 이 단계 자체가 No-Go로 고정**된다. 확인되더라도 계약
   조건(요청 빈도 제한, 이용약관)을 검토한 뒤에만 Go.
5. **개인정보처리방침/약관 최종본(§11, §13)**: 법률 검토 완료 전까지
   실사용자 대상 정식 오픈은 No-Go.
6. **Production 배포**: 위 1~5가 각 해당 기능 범위에서 전부 Go일 때만 그
   기능의 `*_STORE`/`*_PROVIDER` 플래그를 Production에서 활성화한다. 이번
   v0.6 PR 시점에는 어떤 플래그도 바뀌지 않는다.
