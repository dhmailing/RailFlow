# ADR 0003 — 브라우저 자동화 Agent를 폐기하고 제품 코드에서 제외한다

- 상태: 채택
- 날짜: 2026-09-28
- 관련: [V0.9-SERVER-RESERVATION.md](../V0.9-SERVER-RESERVATION.md),
  [V0.9-KORAIL-INTEGRATION-RESEARCH.md](../V0.9-KORAIL-INTEGRATION-RESEARCH.md),
  [ADR 0004](./0004-server-side-autobook.md)

## 배경

v0.8에서 사용자의 Windows PC에서 실행하는 로컬 Agent를 만들었다. 설계상의
전제는 다음과 같았다.

- 사용자가 소유한 계정, 사용자가 직접 시작한 작업
- 화면이 보이는(headed) 브라우저, 사용자의 수동 로그인
- 공개된 공식 예매 UI의 일반적인 조회 흐름만 사용
- 결제 이전 단계까지만 자동화, 차단·추가 인증 시 즉시 중단
- 인증정보·세션을 서버로 전송하지 않음

이 전제를 지킨 상태로 실제 공식 예매 화면(SRT 예매 화면)에 Playwright로
접속했다. 읽기 전용 조회만 수행했고, 예약·결제 코드는 켜지지 않은
상태였다.

## 확인된 사실

**운영자 측에서 해당 접속을 자동화된 요청으로 판정해 접속을 제한했다.**

- 조회만 하는 경우에도 동일하게 제한됐다. 요청 빈도를 낮추는 것으로
  달라지지 않았다.
- 즉 문제는 "너무 자주 조회했다"가 아니라 **브라우저 자동화 도구로
  공식 화면에 접근한 것 자체**가 탐지 대상이라는 점이다.
- 제한 화면에 표시된 식별정보(요청 식별자, IP, 계정 정보 등)는 이 저장소에
  기록하지 않는다. 사실관계 판단에 필요하지 않고, 기록할 이유도 없다.

이 사실은 **이용약관상 금지가 확정됐다는 뜻은 아니다.** 약관 원문을 대조하지
못했다(`V0.9-KORAIL-INTEGRATION-RESEARCH.md` §2-4). 다만 최소한 이 방식이
운영자에게 환영받지 않는다는 강한 신호다.

## 결정

### 1. 되살리거나 우회하지 않는다

탐지를 피하는 방향의 대응을 하지 않는다. 구체적으로 다음을 구현하지 않는다.

브라우저 지문 위장, User-Agent 위조, 헤드리스 탐지 회피, 요청 간격
무작위화를 통한 탐지 회피, IP·프록시·VPN 순환, 계정·세션 로테이션,
CAPTCHA 해결·우회, 대기열 우회, 비공개 API 추측·복제, 앱 트래픽 가로채기,
인증서 우회, 앱 디컴파일, 세션 토큰 추출.

차단은 우회 대상이 아니라 **설계를 바꿔야 한다는 신호**로 취급한다.

### 2. Windows Agent 전체를 제품 코드에서 제외한다

폐기된 기능을 "꺼진 상태로" 남겨 두지 않고 저장소에서 빼기로 했다. 이유는
세 가지다.

1. **되살아날 경로를 없앤다.** 플래그 하나로 다시 켜질 수 있는 코드가
   남아 있으면, 이 결정은 설정값에 불과해진다.
2. **차단용 런타임 코드도 필요 없다.** Agent 코드 자체가 없으면 그것을
   실행 시점에 막는 코드(폐기 안내·강제 중단 모듈 등)도 존재 이유가 없다.
   "막는 코드"는 "막을 대상이 있다"는 뜻이기도 하다.
3. **정직한 상태 표시를 위해서다.** 눌러도 동작하지 않는 버튼과 진단 화면만
   남기면, 사용자는 준비 중인 기능으로 오해한다.

폐기 경위는 코드가 아니라 이 문서로 남긴다.

### 3. 서버형 구조로 전환한다

브라우저 화면을 조작하는 방식을 버리는 대신, 다음 구조를 택했다.

- **서버에서 감시 → 좌석 확보 → 사용자가 공식 앱에서 직접 결제**
- 좌석 조회·예약은 **공개·승인된 연동 경로가 확인된 경우에만** 수행한다.
  확인 전까지 Provider는 `unavailable` 이고, 화면은 무엇이 없어서 못 하는지
  표시한다.

전환 이유:

1. **화면 구조에 의존하지 않는다.** UI 개편마다 선택자를 다시 맞추는 구조는
   유지할 수 없고, 잘못된 칸을 읽으면 잘못된 열차를 예약한다.
2. **승인 여부를 판단할 지점이 생긴다.** 브라우저 조작은 "허용된 사용인가"를
   물을 대상이 없다. 공개 API·파트너 연동은 명세와 이용 권한이 문서로
   존재하므로, 확인되지 않으면 구현을 멈출 수 있다.
3. **사용자 PC 의존을 없앤다.** PC가 켜져 있어야 동작하는 구조는 취소표
   감시에 맞지 않는다.
4. **동시성 문제를 코드로 다룰 수 있다.** 서버 큐라면 분산 락·펜싱 토큰·
   멱등키로 중복 예약을 막을 수 있다. 자세한 설계는 ADR 0004.

## 결과

- `agent/**`, `lib/live/**`, `tests/agent/**` 는 이 저장소에 없다.
  경계 검사는 `scripts/verify-autobook.cjs` 가 수행한다.
- v0.9의 서버형 기반(`lib/autobook/**`)은 실제 좌석 조회·예약을 **하지
  않는다.** 승인된 연동 명세를 확보하지 못했기 때문이다.
- 다음에 확인할 것은 코레일 공식 "예약대기" 기능으로 사용자의 필요가 이미
  해결되는지다(`V0.9-KORAIL-INTEGRATION-RESEARCH.md` §6).

## 대안과 그것을 택하지 않은 이유

| 대안 | 택하지 않은 이유 |
|---|---|
| 조회 간격을 더 늘려 재시도 | 빈도 문제가 아니었다. 간격 조정은 탐지 회피 시도가 된다 |
| Agent를 꺼진 채로 유지 | 플래그 하나로 되살아난다. 폐기 결정이 설정값으로 약해진다 |
| 비공개 API 직접 호출 | 추측·복제에 해당한다. 구현 범위 밖이다 |
| 기능 자체를 포기 | 공식 연동 경로가 확인되면 구현 가능하다. 구조는 미리 만들어 둘 수 있다 |
