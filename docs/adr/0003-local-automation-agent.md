# ADR 0003 — 실제 예매 화면 자동화를 로컬 Agent로 분리한다

- 상태: 채택
- 날짜: 2026-09-24
- 관련: [V0.8-LIVE-BOOKING-AGENT.md](../V0.8-LIVE-BOOKING-AGENT.md),
  [ADR 0002](./0002-auth-storage-notification.md)

## 배경

v0.7까지 RailFlow의 "자동예약"은 전부 시뮬레이터였다. 실제 좌석 상태를 읽고
실제 예약을 만드는 기능은 없었다. 이번 단계의 목표는 실제 공식 예매 화면에서
좌석을 읽고, 승인받은 경우에만 결제 직전까지 예약하는 것이다.

두 가지 제약이 설계를 결정했다.

1. **Vercel 함수 안에서는 불가능하다.** 서버리스 함수는 요청 단위로 죽고,
   화면이 보이는 브라우저를 띄울 수도, 사용자의 로그인 세션을 유지할 수도
   없다. 이 저장소의 `pnpm dev`는 Cloudflare Workers/workerd 위에서 돌아
   `playwright` 를 아예 로드하지 못한다(docs/V0.7-AUTOMATION-BOUNDARY.md §5).
2. **개발 환경에서 공식 화면을 볼 수 없다.** 관련 호스트로 나가는 연결이
   정책으로 차단돼 있다(CONNECT 403). 우회하지 않기로 했으므로, 실제 DOM을
   본 적이 없는 상태로 선택자를 쓰는 일은 불가능하다.

## 결정

### 1. 실제 자동화는 사용자의 PC에서 도는 별도 프로그램으로 분리한다

`agent/` 에 독립 실행형 Node.js 프로그램을 둔다. 웹 앱과 코드를 공유하지
않고, `127.0.0.1` HTTP로만 통신한다. 서버(Vercel)는 이 경로에 관여하지
않는다.

의존성을 최소화하기 위해 빌드 단계 없는 순수 ESM(`.mjs`)으로 작성했다.
Windows 사용자가 `npm install` 한 번이면 `node` 로 바로 실행할 수 있다.

### 2. 선택자와 화면 문구를 코드에 두지 않는다 — 사이트 프로필로 분리

Provider는 다음 두 가지만 코드로 갖는다.

- **의미 기반 구조 탐색**: 결과 표는 `role="row"`/`<tr>` 로 읽고, 열 위치를
  가정하지 않으며, 행 안의 값은 내용으로 식별한다.
- **접근성 기반 컨트롤 탐색**: 버튼·링크는 role + 접근성 이름으로 찾는다.
  좌표 클릭은 쓰지 않는다.

사이트별 어휘("매진", "예약하기", 조회 폼 라벨, 주소)는 전부 프로필 파일에
있고, 그 파일은 `railflow-agent capture` 가 **사용자의 PC에서 실제 화면을
열어** 만든다. 프로필이 `verified: true` 가 아니면 Agent는 조회도 클릭도
하지 않는다(`PROVIDER_PROFILE_REQUIRED`).

**대안으로 검토했다가 버린 것**: 공개된 스크린샷이나 기억에 기대어 선택자를
써 두고 "안 맞으면 고치자"고 하는 것. 이건 지침이 금지한 추측이고, 잘못된
열차를 예약할 위험을 만든다. 채택하지 않았다.

### 3. 실제 예약은 2단계로 잠근다

`LIVE_READ_ONLY` 가 기본이고, 상태 기계에 `SEAT_FOUND → RESERVING` 전이가
**아예 없다**. `LIVE_RESERVATION_ARMED` 로 승인해야 그 전이가 생긴다.
승인 요청에는 화면이 보여준 조건을 그대로 되돌려 보내 Agent가 대조한다.

플래그 하나로 켜고 끄는 방식을 쓰지 않은 이유: 플래그는 실수로 켜질 수
있지만, 존재하지 않는 전이는 실수로 실행될 수 없다.

### 4. "눌렀다"와 "예약됐다"를 분리한다

예약 버튼 클릭 결과는 성공 판정에 쓰지 않는다. 예약내역을 다시 조회해
열차번호·시각·구간이 일치하는 예약을 찾아야 성공이다. 못 찾으면
`RESULT_UNCERTAIN_USER_CHECK_REQUIRED` 로 남기고 **재클릭하지 않는다.**

### 5. 시뮬레이터와 이름·모드를 섞지 않는다

실제 Provider의 이름은 `live:` 로 시작하고 대상 사업자를 포함해야 한다.
계약 검사가 이를 강제한다. 조회 주기도 시뮬레이터의 값을 재사용하지 않고
`livePollingIntervalSeconds` 라는 별도 이름을 쓴다(기본 60초, 하한 30초).

## 결과

### 얻은 것

- 실제 연동 코드가 서버에서 완전히 분리돼, 웹 배포가 실제 예약을 유발할 수
  없다.
- 추측한 선택자가 저장소에 들어갈 수 없다(구조로 막힘).
- 읽기 전용 검증 없이 실제 예약이 일어날 수 없다(상태 기계로 막힘).
- 차단 우회 기능이 Provider에 들어올 수 없다(계약 검사로 막힘).

### 치른 비용

- **Agent는 프로필 없이는 동작하지 않는다.** 사용자가 `capture` 를 한 번
  실행하고 빈칸을 채워야 한다. 이건 설계상 의도한 마찰이다.
- 사용자가 PC와 Node.js를 준비해야 한다. iPad만으로는 실제 연동을 쓸 수
  없다. `CLAUDE.md` 의 "사용자는 iPad를 쓴다" 전제와 충돌하는 부분이며,
  실제 연동에 한해 예외로 둔다.
- Agent 창이 닫히면 감시가 멈춘다. 상시 감시가 필요하면 별도 설계가
  필요하다(이번 범위 아님).

### 검증 상태

자동 테스트(45개)는 통과했지만, 그건 가짜 Provider를 상대로 한 것이다.
**실제 사이트 접속·실제 좌석 읽기·실제 예약은 아직 한 번도 하지 않았다.**
그 검증은 사용자의 PC에서 LIVE_READ_ONLY 부터 순서대로 해야 한다.
