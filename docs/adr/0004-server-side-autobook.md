# ADR 0004 — 서버형 자동예약을 새 모듈로 만들고, 승인된 연동 전까지 fail-closed 로 둔다

- 상태: 채택
- 날짜: 2026-09-28
- 관련: [V0.9-SERVER-RESERVATION.md](../V0.9-SERVER-RESERVATION.md),
  [V0.9-KORAIL-INTEGRATION-RESEARCH.md](../V0.9-KORAIL-INTEGRATION-RESEARCH.md),
  [V0.8-LIVE-AUTOMATION-POSTMORTEM.md](../V0.8-LIVE-AUTOMATION-POSTMORTEM.md)

## 배경

v0.8의 브라우저 자동화가 운영자에게 자동화된 요청으로 판정돼 중단됐다.
동시에 KayRail 같은 서비스가 "서버에서 감시 → 좌석 확보 → 사용자가 직접
결제" 구조로 동작하는 것이 확인됐다.

그러나 조사 결과 **좌석 조회·예약 생성을 지원하는 공개·승인 API를 확인하지
못했다.** 코레일 Open API 는 시간표와 승차권 진위확인까지다.

## 결정

### 1. 새 모듈로 만든다 (`lib/autobook/**`)

v0.4·v0.5·v0.7 모듈의 *패턴*(claim + fencing, 멱등키, Outbox, fail-closed)은
재사용하되 **import 하지 않는다.** verify 스크립트가 이를 검사한다.

이유: 이 PR이 기존 상태 기계를 망가뜨릴 수 없어야 한다. v0.5의 WatchJob 은
지금도 동작해야 하는 코드다.

### 2. 실제 Provider 를 Stub 으로 남긴다

허용된 요청·응답 명세와 이용 권한을 확인하지 못했으므로 구현하지 않는다
(지침 §3). 추측한 endpoint 를 넣는 것은 비공개 API 복제다.

**버린 대안**: 다른 비공식 서비스의 동작을 관찰해 endpoint 를 유추하기.
그건 앱 트래픽 가로채기나 리버스 엔지니어링이며, 하지 않기로 한 일이다.

### 3. 작업 생성 API 를 만들지 않는다

읽기 전용 상태 API 만 둔다. 작업 생성 라우트를 미리 만들어 두면 "플래그 하나
바뀌면 도는" 경로가 생긴다. 승인된 Provider 와 Postgres 어댑터가 모두 갖춰진
뒤에 추가한다.

### 4. 불명확한 결과에서 재예약하지 않는다

상태 기계에 `RESERVATION_CLAIMING → SEAT_FOUND` 전이를 **넣지 않았다.**
플래그로 막는 대신 전이 자체를 없앴다 -- 플래그는 실수로 켜질 수 있지만
존재하지 않는 전이는 실행될 수 없다.

`AMBIGUOUS_RESULT` 는 종료 상태다. 사람이 확인해야 한다.

### 5. 계정 비밀번호를 받지 않는다

공식 OAuth·API credential·단기 세션 중 어느 것도 확인하지 못했으므로
지침 §6의 4번("실제 Provider 미구현")이다. `account-link.ts` 에 비밀번호를
받는 함수가 없고, Postgres 스키마에 비밀번호 컬럼이 없다.

## 결과

### 얻은 것

- 동시 Worker 10개가 같은 작업을 잡아도 예약 요청은 1회(테스트로 고정)
- 오래된 Worker 가 아무 것도 쓰지 못함(fencing token)
- 응답이 유실돼도 예약내역 재조회로 확정하고, 확정 못하면 멈춤
- 운영에서 Mock Provider·메모리 저장소가 값과 무관하게 차단됨
- 화면이 "공식 연동 준비 중"을 정직하게 표시

### 치른 비용

- **지금 시연할 수 있는 실제 기능이 없다.** Mock 으로 Worker 흐름을 보여줄
  수는 있지만 그건 시뮬레이션이다.
- 작업 생성 API 가 없어 UI 가 상태 표시에 그친다.
- Postgres 어댑터가 없어 실제 서버형 운영이 불가능하다.

이 비용들은 전부 "승인된 연동이 없다"는 하나의 원인에서 나온다. 그 원인을
숨기고 동작하는 것처럼 보이게 만드는 것보다, 드러내고 멈추는 쪽을 택했다.

### 검증 상태

자동 테스트 33개가 통과했지만 **전부 Mock Provider 기준**이다.
실제 좌석 조회·예약은 0건이다.
