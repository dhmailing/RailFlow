# RailFlow v0.7 — Preview 시연 가능성 감사 및 보완

이 문서는 v0.7 1차 PR(dhmailing/RailFlow#10) 병합 전 요청받은 "실제 시연 가능성 검증"의 결과다. 추측이 아니라 이 세션에서 실제로 재현·확인한 사실만 적는다. 확인하지 못한 것은 §7에 "확인 필요"로 남긴다.

## 1. 기존 Preview 시연이 불가능했던 원인

### 1-1. 회원가입/로그인이 Vercel Preview에서 막힌다

`lib/auth/feature-flags.ts`의 `isAuthStoreUsable()`은 다음과 같이 판정한다:

```ts
export function isAuthStoreUsable(): boolean {
  return getAuthStoreMode() === "memory" && process.env.NODE_ENV !== "production";
}
```

**`NODE_ENV`로 판정한다 — `VERCEL_ENV`가 아니다.** Next.js는 `next build`(Vercel이 Preview 배포에도 사용하는 바로 그 명령)를 실행하면 `VERCEL_ENV`가 `"preview"`여도 `NODE_ENV`는 항상 `"production"`으로 빌드한다(Next.js/Vercel의 잘 알려진 표준 동작). 따라서:

- `AUTH_STORE=memory`를 Preview 환경변수로 등록해도 `isAuthStoreUsable()`은 `false`를 반환하고, `POST /api/auth/signup`/`login`은 항상 503(`AUTH_STORE_DISABLED`)을 반환한다.
- `lib/watch/feature-flags.ts`의 `isWatchStoreUsable()`도 동일한 `NODE_ENV` 패턴을 쓴다 — 취소표 감시(WatchJob) 저장소도 Preview에서 똑같이 막힌다.
- **`lib/automation/feature-flags.ts`만 의도적으로 `VERCEL_ENV`로 판정**하도록 v0.7에서 새로 설계됐다(자동화 기능 자체는 Preview에서 허용하려는 의도였다) — 하지만 자동화 작업 API(`/api/automation-jobs/**`)는 전부 `requireAuth()`를 먼저 통과해야 하므로, 로그인 자체가 막힌 Preview에서는 자동화 Provider 설정과 무관하게 이 API에 도달할 수조차 없었다.

**결론: 1차 PR 상태의 Preview에서는 회원가입·로그인이 실제로 불가능했고, 이것이 "자동예약 탭에서 작업 등록부터 예약 성공까지 안 됨"의 근본 원인이었다.**

이번 세션은 `lib/auth/feature-flags.ts`/`lib/watch/feature-flags.ts`를 수정하지 않았다 — v0.5에서 이 `NODE_ENV` 판정을 선택한 이유(Vercel Serverless는 인스턴스마다 별도 메모리를 가져 인메모리 계정 저장소를 Preview에서 "켜도" 실제로는 신뢰할 수 없다는 문서화된 이유, `lib/auth/feature-flags.ts`의 주석 참고)가 여전히 유효하기 때문이다. 대신 **로그인 자체가 필요 없는 완전히 독립된 공개 시연 경로**(§3~§4)를 추가하는 쪽을 선택했다.

### 1-2. (수정 전) Cloudflare Workers 런타임에서 자동화 라우트 자체가 죽었다

PR #10에서 이미 발견·수정한 별도의 문제(PR #10 본문 §3)로, Preview(Vercel, Node.js 런타임으로 추정)와는 무관하지만 이 저장소의 로컬 개발/빌드 경로(Cloudflare Workers)에서 자동화 라우트 전체가 기본값에서도 500으로 죽던 문제였다. 이미 수정·검증 완료 상태였다.

### 1-3. (이번 세션에 새로 발견·수정) Mock 예매 사이트 UI의 구매클릭 결과가 반영되지 않았다

실제로 로그인이 되는 환경(로컬 `next dev`, Node.js)에서 실제 Playwright 브라우저로 자동화 작업을 처음부터 끝까지 돌려보니(§2), `구매` 버튼을 실제로 클릭한 뒤 서버는 정상적으로 클릭을 기록했지만(HTTP 200), 화면의 `data-purchase-clicked` 속성이 `"false"`로 멈춰 있어 `mock-browser-provider.ts`의 `waitForAttribute()`가 15초 타임아웃 후 `PURCHASE_CLICK_FAILED`로 실패했다.

**원인**: `components/automation/booking-simulator.tsx`의 `clickPurchase()`가 구매 클릭 API 호출 성공 후 좌석 상태를 다시 불러오지 않았다. 화면의 `data-purchase-clicked` 속성은 `status?.purchaseClicked ?? clicked`로 렌더링되는데, `status`(서버에서 가져온 마지막 스냅샷)가 이미 존재했으므로 `??`가 로컬 `clicked` 값으로 넘어가지 못하고 클릭 이전의 stale한 `false`를 계속 표시했다.

**수정**: `clickPurchase()` 성공 시 `void checkStatus(listingId)`를 호출해 서버 상태를 즉시 다시 가져오도록 했다(`components/automation/booking-simulator.tsx`).

**수정 후 실제로 확인함**: 같은 방식으로 로그인 → 자동화 작업 등록 → `run-step` 반복 호출 → 실제 Playwright 브라우저가 후보 2(candidate 2)를 3번째 확인에서 발견 → 자동 구매클릭 → 자동 예약까지 **실제로 HELD → PAYMENT_PENDING**에 도달하는 것을 API 레벨에서 직접 확인했다(가상 예약번호 `RF-D21AC17B` 발급, 결제기한 발급). 이 수정이 없었다면 이 흐름은 실제로 한 번도 끝까지 완주하지 못했을 것이다.

## 2. Preview 실행 가능성 감사

| 구간 | 필요 조건(실제 코드의 정확한 이름) | Preview(Vercel, 추정 Node.js 런타임) | Production |
| --- | --- | --- | --- |
| 회원가입 | `AUTH_STORE`(`lib/auth/feature-flags.ts`) — `memory`이고 `NODE_ENV !== "production"` | **불가능** — `next build`는 `VERCEL_ENV`와 무관하게 `NODE_ENV=production`으로 빌드되므로 `AUTH_STORE=memory`를 설정해도 항상 503 | 불가능(설계상 의도, §1 참고) |
| 로그인 | `AUTH_STORE` + `APP_ORIGIN`(`lib/security/origin-guard.ts`, `NODE_ENV=production`에서만 강제 검증) | 회원가입과 동일하게 **불가능** | 불가능 |
| 자동화 작업 생성 | 저장소: 별도 `AUTOMATION_STORE` 플래그 없음(`lib/automation/job-store.ts`는 항상 인메모리) + `ENABLE_SEAT_AUTOMATION_JOBS=true` + `SEAT_AUTOMATION_PROVIDER≠unavailable` + `requireAuth()` | 로그인 자체가 안 되므로(위 행) **불가능** — Provider 설정과 무관 | 항상 503(`isRealProductionEnvironment()`가 `VERCEL_ENV==="production"`일 때 무조건 차단) |
| Worker 한 단계 실행 | `SEAT_AUTOMATION_PROVIDER`(`unavailable`/`mock-browser`/`mock-direct`/`official`) + 해당 Provider가 이 런타임에서 로드 가능한지 | `mock-direct`: 가능(브라우저 불필요). `mock-browser`: Preview가 Node.js 런타임으로 API 라우트를 서비스한다면 가능(§7 확인 필요), Edge 런타임이면 `RUNTIME_NOT_SUPPORTED` | 항상 차단(위와 동일) |
| Playwright 실행 | Chromium 바이너리 + Node.js `child_process` 지원 런타임 | **확인 필요**(§7) — 이 세션은 Vercel Preview의 실제 서버리스 런타임을 재현하지 못했다. 로컬 `next dev`(Node.js)에서는 실제로 동작함을 확인했다(§1-3) | 자동화 Provider 자체가 항상 차단되므로 무관 |
| 알림 | `lib/watch/notification/adapters.ts`의 InMemory Outbox Adapter(worker.ts가 재사용) — 실제 서비스 키 불필요, 항상 usable | 가능(테스트용 Adapter이므로 Preview/Production 구분 없이 항상 동작) | 가능(단, 자동화 작업 자체가 Production에서 생성되지 않으므로 실질적으로 발동하지 않음) |

**`NODE_ENV=production`과 `VERCEL_ENV=preview`를 혼동하지 않았는지**: 위 표의 핵심이 바로 이 구분이다 — `lib/automation/feature-flags.ts`는 의도적으로 `VERCEL_ENV`만 본다(Preview를 자동화 대상으로 허용하려는 의도), 반면 `lib/auth/feature-flags.ts`/`lib/watch/feature-flags.ts`는 `NODE_ENV`를 본다(Preview에서도 계정/감시 저장소를 막으려는 기존 v0.5 의도) — 이 둘의 판정 기준이 서로 다르다는 사실 자체가 "로그인이 막힌 채로 자동화만 열려 있는" 이번 문제의 정확한 원인이다.

## 3. `mock-direct`와 `mock-browser`의 차이

| | `mock-browser`(기존) | `mock-direct`(신규) |
| --- | --- | --- |
| 구현 위치 | `lib/automation/providers/mock-browser-provider.ts` | `lib/automation/providers/mock-direct-provider.ts` |
| 브라우저 실행 | 실제 Playwright(Chromium)로 `/demo/booking-simulator`를 열고 클릭 | 없음 — `lib/automation/mock-booking-site/store.ts`를 직접 함수 호출 |
| 실행 가능 런타임 | Node.js `child_process`를 지원하는 런타임만(§5 이전 문서, 이번 세션에 재확인) | 모든 런타임(Cloudflare Workers 포함) — `playwright`를 아예 import하지 않는다 |
| 실패 시 코드 | `RUNTIME_NOT_SUPPORTED`(신규 코드, 이번에 추가) | 해당 없음(항상 로드 가능) |
| 용도 | Playwright 계약 자체를 검증(실제 브라우저 자동화가 "정말 가능하다"는 증거) | 어떤 런타임에서도 안정적으로 같은 시나리오(candidate 1 매진/2 3회차/3 5회차)를 재현하는 시연용 Provider |
| Production | `isRealProductionEnvironment()`가 무조건 차단 | 동일하게 무조건 차단 |

`getSeatAutomationProvider()`(`lib/automation/provider.ts`)는 `mock-browser`가 선택됐을 때만 `playwright`를 담은 파일을 **동적 import**하며, 그 import 자체가 실패하면(§1-2에서 실제로 재현한 것과 같은 런타임 비호환) `RUNTIME_NOT_SUPPORTED` `AutomationError`로 변환해 반환한다 — 처리되지 않은 크래시가 아니라 다른 Provider 오류와 동일하게 호출자가 처리할 수 있는 오류가 된다. `provider-status` API는 이제 `runtimeSupported` 필드로 이 사실을 사전에(작업을 실제로 실행해보지 않고도) 알려준다(§7 참고).

## 4. 공개 시연 경로 (`/demo/booking-automation`)

`lib/auth`/`lib/watch`/`lib/reservation`/`lib/automation`을 전혀 import하지 않는 완전히 독립된 클라이언트 전용 모듈(`lib/automation-demo/**`, `components/automation-demo/**`, `app/demo/booking-automation`)로 구현했다 — v0.6 Demo Showcase(`lib/demo/**`)와 정확히 같은 격리 원칙이다. 상태는 `sessionStorage`에만 저장되며, `fetch`/`XMLHttpRequest`/`WebSocket`을 전혀 호출하지 않는다(정적 검사: `scripts/verify-automation-demo.cjs`).

- 조건(출발/도착/날짜/희망 시간대) 입력 → 후보 3편 중 2개 이상 선택 → 1~5초 간격 선택 → "자동 감시 시작"을 누르면, 이후 모든 전이(좌석 확인 → 좌석 발견 → 자동 구매클릭 → 자동 예약 → 결제 대기)가 타이머로 자동 진행된다. **"결제 완료"만 사용자가 직접 눌러야 한다**(자세한 전이는 `lib/automation-demo/state-machine.ts`).
- candidate-1은 항상 매진, candidate-2는 (선택된 후보 라운드로빈 기준) 자신의 3번째 확인에서 일반실 1석, candidate-3은 5번째 확인에서 특실 1석 — RailFlow 실제 Mock 예매 사이트와 동일한 숫자(문서·시연상 일관성일 뿐, 코드 의존성은 없음).
- 새로고침해도 `sessionStorage`에서 상태(예약번호·결제기한·경과 시간)가 그대로 복원된다.
- `자동예약` 탭(`components/automation/automation-jobs.tsx`)에 "로그인 없이 자동 좌석조회·예약 매크로 시연 보기" 링크를 추가했다.

## 6. Production 차단 근거 (변경 없음, 재확인)

`lib/automation/feature-flags.ts`의 `isRealProductionEnvironment()`는 `VERCEL_ENV === "production"`으로만 판정하며, 이번 라운드에서 추가한 `mock-direct` Provider도 `isAutomationProviderUsable()`의 동일한 게이트(`ENABLE_SEAT_AUTOMATION_JOBS && !isRealProductionEnvironment()`)를 그대로 통과해야 한다 — 임의의 환경변수 조작으로 우회할 수 없다(코드에 하드코딩된 조건). `docs/V0.7-AUTOMATION-BOUNDARY.md` §4를 그대로 따른다.

## 8. 확인 필요로 남기는 항목

- **Vercel Preview가 `/api/automation-jobs/**`를 실제로 어느 런타임(Node.js Serverless Function vs Edge Function)으로 서비스하는지.** 이 세션은 `*.vercel.app`으로의 아웃바운드 네트워크가 차단되어 있어 실제 Preview에 대해 직접 확인하지 못했다. Node.js 런타임이면 `mock-browser`도 이론상 동작할 수 있지만(단, Vercel 서버리스 함수가 번들에 포함된 Chromium 바이너리를 실제로 실행할 수 있는지는 별도 확인이 필요 — 실행 파일 크기 제한, 실행 권한 등), Edge 런타임이면 `RUNTIME_NOT_SUPPORTED`로 정직하게 실패한다(크래시하지 않음은 이미 코드로 보장).
- 위와 같은 이유로 **Preview에서 `mock-browser`를 실제로 켰을 때의 동작**도 직접 확인하지 못했다. `mock-direct`는 런타임에 의존하지 않으므로 Preview에서 안정적으로 동작할 것으로 예상하지만, 이 역시 Preview 자체에 대한 직접 확인(네트워크 차단으로 불가)은 아니다 — 로컬에서 동일 코드 경로로 확인한 결과(§1-3, §5)로 대체했다.
- Preview에서 로그인이 막혀 있다는 사실(§1-1)은 코드 분석(NODE_ENV 판정 로직)으로 확인한 것이며, 실제 Preview URL에 회원가입 요청을 보내 503을 직접 관찰하지는 못했다(네트워크 차단, 이전 라운드부터 동일).
