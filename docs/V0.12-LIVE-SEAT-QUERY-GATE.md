# V0.12 — 실제 좌석 조회·예약 착수 가능 여부 판정 (화면 조작 방식 포함)

작성일: 2026-10-01. 판정 기준 시각의 저장소 상태는 §2에 적었다.

이 문서는 "실제 좌석 조회·예약을 지금 구현할 수 있는가"에 대한 판정만 담는다.
새 Provider·새 Stub·새 시뮬레이터·새 상태 기계를 만들지 않았다. 코드 변경은 0줄이다.

---

## 0. 결론

**실제 좌석 조회 미완료. 실제 예약 미검증.** 실제 열차 한 편의 좌석 상태를 읽은 결과가
없고, 예약을 실행한 적도 없다.

착수할 수 없다. 다만 막는 것은 하나가 아니라 **네 가지이고, 네 가지의 성질이 서로 다르다.**
이전 라운드(`V0.11-OFFICIAL-PROVIDER-GATE.md` §10, PR #18에 있으며 아직 병합되지 않았다)는
이 중 일부를 섞어서 "닫혔다"고 썼다. 여기서 분리한다.

| 장애 | 성질 | 누가 풀 수 있는가 | 현재 상태 |
|---|---|---|---|
| A. 허용된 좌석 상태 요청 경로가 없다 | 외부 사실 | 운영 주체·판매대행(승인) | 확인됨 — Gate 1~4 전부 미충족 |
| B. 화면 조작 방식이 저장소 지침과 충돌한다 | **우리 결정** | 사용자 | 확인됨 — 세 곳에 명시, 한 곳은 코드로 강제 |
| C. 화면 조작 방식을 실행할 환경이 없다 | 환경 사실 | 사용자(새 환경 제공 시) | 확인됨 — 보유한 3개 환경 모두 요건 미달 |
| D. 개발 환경에서 외부 호스트로 나갈 수 없다 | 설정 | 사용자(환경 설정) | 확인됨 — 오늘 재확인, 변화 없음 |

중요한 것은 **A·B·C·D가 서로를 풀어 주지 않는다**는 점이다. D를 열어도 A는 그대로이고,
B를 바꿔도 C는 그대로다. §3-5에 조합별로 적었다.

이 판정은 **"모든 화면 자동화가 기술적으로 불가능하다"는 뜻이 아니다.** 기술 문제로 막힌 것은
A·C뿐이고, C는 환경 문제이지 기술적 불가능이 아니다. B는 기술 문제가 아니라 결정이다.

### 2-4. 오늘 직접 확인한 것 — 장애 D

개발 환경에서 외부 호스트로 나갈 수 없다. 오늘 공공데이터포털 호스트 2곳으로
HTTPS 연결을 시도했고 둘 다 연결 자체가 성립하지 않았다(HTTP 코드 `000`, 프록시가 CONNECT 거부).

| 호스트 | 결과 |
|---|---|
| `apis.data.go.kr` | `000` — 연결 거부 |
| `www.data.go.kr` | `000` — 연결 거부 |

**철도 운영 주체의 예매 화면에는 요청을 보내지 않았다.** 이미 접근 제한이 관찰된 경로이고,
도구·호스트·IP를 바꿔 다시 시도하지 않기로 한 범위에 들어간다(§8).

확인한 호스트를 공공데이터포털로 고른 이유는 두 가지다. 첫째, 예매 화면이 아니라 정부
개방데이터 창구이므로 접근 제한이 관찰된 적이 없다. 둘째, 이 호스트가 열렸는지 아닌지가
장애 A의 후보 조사(개방데이터 목록 확인)와 기존 TAGO 시간표 Provider 실조회 검증
가능 여부를 동시에 결정한다.

결과적으로 **둘 다 불가능하다.** 이 환경에서는 개방데이터 목록조차 열어 볼 수 없다.
`V0.11` §10-1에 적은 대로 이것은 사용자가 환경의 Network access 설정에서 바꿀 수 있는
항목이다. 다만 §3-5에 적은 대로, 이것이 열려도 좌석 조회는 되지 않는다.

## 3. 네 개의 장애

### 3-1. 장애 A — 허용된 좌석 상태 요청 경로가 없다

`V0.11-OFFICIAL-PROVIDER-GATE.md` §3의 후보 판정을 반복 조사하지 않았다. 결론만 옮긴다.

| Gate | 필요한 것 | 상태 |
|---|---|---|
| 1 | 좌석 상태를 주는 endpoint와 요청·응답 명세 | 미충족 |
| 2 | 우리에게 발급된 자격증명 | 미충족 |
| 3 | 응답 필드의 의미(무엇이 "예약 가능"인지) | 미충족 |
| 4 | 그 용도로 쓰는 것에 대한 명시적 허용 | 미충족 |

후보 중 유일하게 "좌석 상태를 데이터로 받는 주체가 실재한다"가 확인된 것은 파트너·판매대행
경로였고, 그 경로의 이용 조건은 **잠정 정보**에 머물렀다. 공공데이터포털
「열차운행정보」는 좌석 항목이 없어 **근거상 지원하지 않음**이다. 시간표와 좌석 잔여는
끝까지 분리한다(`CLAUDE.md` 목표 3).

### 3-2. 장애 B — 화면 조작 방식은 저장소 지침과 충돌한다

사용자 요청은 화면 조작 방식을 **검토 대상에 넣으라**는 것이었다. 검토했다(§4). 그런데
착수에는 다음 세 곳의 개정이 필요하다. **임의로 지우지 않았다.** 정확한 위치와 문구를 적는다.

| 위치 | 현재 문구 | 착수에 필요한 변경 |
|---|---|---|
| `CLAUDE.md` › 「실제 연동에 대한 원칙 (v0.9)」 › 「하지 않는 것」 | "**공식 예매 화면을 브라우저로 조작하는 방식도 여기에 포함된다**(`docs/adr/0003-abandon-browser-agent.md`). 이 목록은 `scripts/verify-autobook.cjs`로 코드에서 강제한다." | 이 한 문단의 철회 또는 범위 한정(예: "접근 제한이 관찰된 운영 주체·화면에 한정한다") |
| `docs/adr/0003-abandon-browser-agent.md` › 결정 1·2 | "되살리거나 우회하지 않는다", "Windows Agent 전체를 제품 코드에서 제외한다" | 결정을 뒤집는 새 ADR. 기존 ADR을 고쳐 쓰지 않고 상태를 `대체됨`으로 바꾸는 방식 |
| `scripts/verify-autobook.cjs` | `FORBIDDEN_TOKENS`(예매 화면 호스트 문자열, 폐기된 Agent 식별자 12개) + "서버형 자동예약에 브라우저 자동화가 없다" 검사(`lib/autobook` 안에서 `chromium`·`playwright`·`page.goto` 등 금지) | 해당 검사 2건의 수정. 44개 검사 중 2개 |

이 세 곳은 **같은 하나의 결정**을 세 겹으로 적어 둔 것이다. 하나만 바꾸면 검증이 깨지고,
검증만 바꾸면 기록과 어긋난다. 그래서 이것은 코드 작업이 아니라 **사용자가 내릴 결정**이다.

같은 지침의 다른 항목들은 이 결정과 무관하게 유지한다. CAPTCHA·대기열·탐지 회피,
User-Agent·IP·계정·세션 로테이션, 비공개 API 추측, 앱 트래픽 가로채기, 차단 응답의 성공 위장,
결제 자동화, 비밀번호·OTP·쿠키 저장 — **어느 것도 이 문서에서 완화하지 않았다.**

### 3-3. 장애 C — 화면 조작 방식을 실행할 환경이 없다

장애 B가 풀렸다고 **가정해도** 남는 문제다. 화면 방식에는 세 가지 요건이 동시에 필요하다.

1. **접근** — 브라우저가 해당 화면에 실제로 닿는다.
2. **사용자 직접 로그인** — 사용자가 자기 손으로 로그인·추가 인증을 끝낸다. 비밀번호·OTP를
   우리가 받지 않고, 쿠키를 추출하지 않는다(`CLAUDE.md` 개발 원칙).
3. **사용자 PC를 꺼도 동작** — 사용자 요청 §5의 최종 목표.

보유한 실행 환경 3개를 요건별로 대조하면 다음과 같다.

| 실행 환경 | 1. 접근 | 2. 사용자 직접 로그인 | 3. PC 꺼도 동작 | 판정 |
|---|---|---|---|---|
| 이 개발 컨테이너 (Chromium·Playwright 설치돼 있음) | ✗ 장애 D | ✗ 이 컨테이너의 브라우저 화면을 사용자에게 보여주고 입력을 받을 경로가 없다 | ✗ 비활성 시 회수되는 임시 컨테이너 | 3개 모두 미달 |
| 사용자 Windows PC | 관찰상 제한됨(§2-3) | ○ v0.8에서 실제로 됐다 | ✗ PC를 켜 둬야 한다 | 1·3 미달. 되살리지 않기로 한 경로 |
| 현재 배포 환경 (Vercel / Cloudflare Workers) | 미확인 | ✗ 사용자가 그 브라우저 화면을 볼 방법이 없다 | ○ | 2 미달 |

위 세 환경에서는 요건 2와 3이 동시에 성립하지 않는다. 로그인을 사용자가 직접 해야 하는데,
그 세션이 살아 있는 브라우저는 사용자가 조작할 수 있는 곳에 있어야 한다. 사용자 PC를 꺼도
돌아가려면 그 브라우저는 서버에 있어야 하고, 위 세 환경에서는 서버 브라우저를 사용자가
조작할 방법이 없다. 이 벽을 넘기는 흔한 방법이 **쿠키·세션 토큰을 서버로 옮기는 것**인데,
그것은 `CLAUDE.md`가 금지한 항목이고 이 문서에서 완화하지 않았다.

> **정정 (2026-10-02).** 이 절의 초판은 요건 2와 3이 "구조적으로 충돌한다"고 썼다. 그것은
> 과한 표현이었다. 쿠키를 꺼내지 않고도 둘을 함께 만족시키는 구조가 있다 — 서버에 있는
> 브라우저를 사용자가 원격으로 직접 조작하는 방식이다. §11에 따로 적었다. 결론(지금 착수
> 불가)은 바뀌지 않지만 근거가 달라지므로 분리해 둔다.

### 3-4. 장애 D — 개발 환경 네트워크

§2-4에 확인 결과를 적었다. 사용자가 환경 설정에서 바꿀 수 있다.

### 3-5. 섞지 않는다 — 무엇이 무엇을 풀지 않는가

| 가정 | 그러면 되는 것 | 그래도 안 되는 것 |
|---|---|---|
| D만 열린다 | 개방데이터 목록 확인, 기존 TAGO **시간표** Provider 실조회 검증 | 좌석 조회(A 미해결). 시간표를 좌석으로 쓰지 않는다 |
| B만 바뀐다 | 화면 방식 구현에 착수할 자격 | 실행 환경이 없다(C). 접근 제한 관찰도 그대로다 |
| B와 D가 모두 풀린다 | 이 컨테이너에서 화면을 열어 구조를 관찰하는 것 | 사용자 직접 로그인 불가(C-2), 컨테이너 회수(C-3). 그리고 데이터센터 IP의 자동화 접근이라는, 제한이 관찰된 조건과 같다 |
| A가 풀린다 | **좌석 조회·예약 구현 착수.** B·C·D 모두 불필요해진다 | 없다 |

표의 마지막 줄이 핵심이다. **A가 유일한 병목이고, A를 풀면 나머지 셋이 전부 무의미해진다.**
반대로 B·C·D를 아무리 조합해도 A를 대신하지 못한다.

## 4. 화면 조작 방식 검토

사용자 지시대로, 공식 API를 확보하지 못했다는 사실을 "모든 화면 자동화가 불가능하다"로
해석하지 않고 따로 검토했다.

### 4-1. 화면 방식이 성립하려면 필요한 것

사용자 요청 §2가 열거한 것을 그대로 쓴다. 현재 확보: **0/4.**

| 필요한 것 | 현재 | 왜 없는가 |
|---|---|---|
| 실제 화면 구조(선택자) | 없음 | 화면을 관찰한 적이 없다. 추측으로 채우면 잘못된 칸을 읽어 잘못된 열차를 예약한다 |
| 실제 표시 문구 | 없음 | "예약 가능"·"매진"·"예약대기"가 각각 어떤 문구로 나오는지 모른다 |
| 조작 흐름 | 없음 | 조회→선택→예약 사이에 어떤 화면과 확인 단계가 끼는지 모른다 |
| 예약 결과 확인 방법 | 없음 | 예약내역 화면의 주소·구조·표시 문구를 모른다. 버튼 클릭 성공과 예약 성공을 구분할 기준이 없다 |

### 4-2. 왜 관찰로 채울 수 없는가

이 4개는 **화면을 열어 보면** 채울 수 있다. 문제는 열어 볼 방법이다.

- 이 컨테이너에서 연다 → 장애 D로 닿지 않는다. 열린다 해도 데이터센터 IP에서 자동화 도구로
  예매 화면에 접근하는 것이고, 그것이 제한이 관찰된 조건과 같다.
- 사용자가 직접 열어 화면을 기록해 준다 → **기기가 없어서 안 되는 것이 아니다.** 사용자는
  Windows PC를 함께 쓴다(§10 정정). 하지 않는 이유는 두 가지다. v0.8에서 같은 절차를 이미
  거쳤고 그때 접근이 제한됐으며, 사용자가 그 절차를 다시 반복시키지 말라고 했다. 즉 이것은
  **기기 제약이 아니라 결정과 관찰**이다.
- 공개 문서로 대체한다 → 선택자와 표시 문구를 공식 문서로 공개하는 운영 주체는 없다.

즉 화면 방식은 지침(B)·환경(C) 이전에 **관찰 근거 자체가 0**이고, 관찰을 하려면 B·C·D를 모두
먼저 넘어야 한다. 순서가 뒤집히지 않는다.

### 4-3. 이전 라운드 판단의 정정

`V0.11` §10-3은 "사용자 PC 브라우저 자동화" 후보를 **"폐기된 Agent 경로이고 접근 제한이 이미
관찰됐다"**는 한 칸으로 닫았다. 이것은 두 가지를 섞은 것이다.

- **결정**(폐기했다) — 사용자가 바꿀 수 있다. 외부 사실이 아니다.
- **관찰**(제한됐다) — SRT 예매 화면 1곳·headed 자동화·사용자 PC라는 조건에 한정된 사실이다.

분리하면 이렇게 된다. 결정은 바꿀 수 있고, 관찰은 다른 운영 주체까지 일반화되지 않는다.
그런데도 **지금 착수할 수 없는 이유는 장애 C(실행 환경)와 §4-1(관찰 근거 0)이며, 이 둘은
결정을 바꿔도 남는다.** 결론은 같지만 근거가 다르고, 근거가 다르면 다음에 할 일이 달라진다.

하나 더 정정한다. 다른 운영 주체의 화면으로 바꿔 시도하는 것은 §4-1·§4-2를 넘지 못하고,
동시에 "제한을 피하려고 대상을 바꾸는 것"과 구분이 어렵다. 그래서 하지 않았다.

자리만 만드는 것은 사용자가 금지한 "기반 코드 추가"에 해당한다.

## 6. 예약 흐름 — 지금 확정할 수 있는 것과 못 하는 것

사용자 요청 §4의 흐름(조건 재확인 → 좌석 상태 확인 → 예약 동작 → 예약 결과 확인 → 결제 대기 →
나머지 후보 중단)을 기준으로 나눈다.

### 6-1. 이미 구현되고 검증된 것 — 다시 만들지 않는다

| 요구 | 어디서 보장되는가 |
|---|---|
| 동시 Worker·중복 클릭으로 예약이 둘 생기지 않는다 | 원자적 `claimNext`(`FOR UPDATE SKIP LOCKED`) + 펜싱 토큰 + 예약 멱등키 DB UNIQUE 제약. 동시 Worker 20개 테스트로 확인 |
| 결과 불명확 시 재예약하지 않는다 | `AMBIGUOUS_RESULT` 는 종료 상태. 예약 요청 후에는 `findExistingReservation` 만 부르고 `createReservation` 을 다시 부르지 않는다 |
| 조건 불일치 시 대체하지 않는다 | 조건은 날짜·구간·인원·좌석등급으로 작업에 고정되고 Worker가 바꾸지 않는다 |
| 결제·자동 취소를 실행하지 않는다 | 결제 경로가 코드에 없다. 상태는 `PAYMENT_PENDING` 에서 멈춘다 |
| 강제 중단 | `AUTOBOOK_KILL_SWITCH` 가 모든 판단보다 앞선다 |

### 6-2. 확정할 수 없는 것

| 요구 | 왜 못 하는가 |
|---|---|
| 버튼 클릭 성공과 예약 성공의 구분 기준 | 예약 결과가 어디에 어떻게 표시되는지 모른다(§4-1) |
| 예약내역에서 존재와 조건을 확인하는 방법 | 같음 |
| **결제기한을 실제 화면에서 읽기** | 읽을 화면이 없다. Mock 값으로 채우지 않는다 — 그래서 이번에 아무 값도 넣지 않았다 |
| 타임아웃·프로세스 종료 시 수동 확인 상태 전환의 안내 문구 | 사용자가 무엇을 어디서 확인해야 하는지 쓸 수 없다 |

### 6-3. 실제 예약 테스트 승인 양식 (제시만. 실행하지 않았다)

착수 가능해지면 실제 예약 전에 아래를 채워 사용자 승인을 받는다. 이번에는 채울 수 없다.

- 대상 날짜:
- 구간(출발역 → 도착역):
- 열차번호·출발시각:
- 인원:
- 좌석등급:
- 실행 범위: **최대 1건.** 성공·실패 어느 쪽이든 추가 시도 없음
- 결제: 실행하지 않음. 사용자가 공식 서비스에서 직접
- 중단 조건: 조건 불일치, 추가 인증 요구, 접근 제한 응답, 화면 구조 변경

## 7. 반복 감시 주기 — 정할 근거가 없다

사용자 요청 §5는 "확인된 이용 조건·요청 제한을 따른다"와 "시뮬레이터의 1~5초 주기를
재사용하지 않는다"를 함께 요구했다.

현재 **허용 주기와 일일 요청 한도를 알려 주는 공식 근거가 없다.** 그래서 주기를 정하지
않았다. 임의로 "30초"나 "1분"을 적는 것은 숫자만 점잖아 보이는 추측이고, 1~5초를 그대로
쓰는 것과 근거의 양이 같다.

이 값은 장애 A가 풀릴 때 **같은 답변 안에서 함께 받는다.** 문의문 01의 8번 항목이 그것을
묻는다("허용된 주기와 일일 요청 한도"). 주기는 별도 조사 대상이 아니라 Gate 1의 일부다.

접근 제한·속도 제한 응답에서 자동 재시도를 멈추는 동작, 중단·만료·예약 성공 이후 조회를
멈추는 동작, 화면 갱신 주기와 실제 조회 주기의 분리는 이미 구현돼 있다(§6-1, `rate-limit.ts`,
`CLAIMABLE_STATUSES`).

## 8. 하지 않은 것

- 철도 운영 주체의 예매 화면·예약 시스템에 요청을 보내지 않았다. 조회도, 로그인도, 예약도.
- 접근 제한이 관찰된 경로를 도구·호스트·IP·계정을 바꿔 다시 시도하지 않았다.
- 폐기된 Windows Agent를 이름·설정만 바꿔 되살리지 않았다. 관련 코드를 다시 넣지 않았다.
- 비공개 endpoint를 추측해 코드나 문서에 넣지 않았다.
- 새 Mock Provider·새 시뮬레이터·새 Stub을 만들지 않았다.
- 확인되지 않은 선택자·표시 문구·결제기한을 placeholder로 넣지 않았다.
- `CLAUDE.md` 의 보안 원칙(쿠키·비밀번호·OTP, 탐지 회피, 결제 자동화)을 완화하거나 삭제하지
  않았다. 충돌 지점만 §3-2에 적었다.
- v0.8 때의 설치·화면 기록 절차를 사용자에게 다시 요구하지 않았다.
- 운영 환경변수·Vercel 설정·다른 PR을 건드리지 않았다. PR #18도 그대로 두었다.
- 유료 서비스에 가입하거나 운영 DB에 적용하지 않았다.

## 9. 다음에 필요한 행동 — 한 가지

**사용자가 `docs/inquiries/01-korail-booking-operator.md`(PR #18) 를 코레일 담당 창구로 발송한다.**

이유는 §3-5의 마지막 줄이다. A가 유일한 병목이고, 환경 설정(D)을 열거나 결정(B)을 바꾸는
것은 A를 대신하지 못한다.

이전 라운드(PR #18 `docs/inquiries/README.md`)는 KayRail 운영자(05)를 우선순위 1로 적었다.
**이것을 01로 바꾼다.** KayRail은 좌석 상태를 받아 쓰는 당사자이지만, 우리에게 그 경로를
허용해 줄 수 있는 주체로 볼 근거가 없다. 사용자도 KayRail 협업으로 목표를 바꾸지 말라고 했다.
05는 보내도 되지만 01이 먼저다.

### 9-1. 과장하지 않는다 (2026-10-02 정정)

초판은 두 가지를 단정했다. 둘 다 근거가 없어 철회한다.

| 초판의 단정 | 왜 철회하는가 | 바꿔 쓸 표현 |
|---|---|---|
| "문의가 **유일한** 방법이다" | 확인하지 못한 경로가 남아 있다. 파트너·판매대행 경로의 이용 조건은 **잠정 정보**이고(§3-1), 개방데이터 목록은 이 환경에서 열어 보지도 못했다(§2-4). 검색에 안 나온 것을 "없음"으로 판정하지 않는다 | 문의는 **지금 우리가 실행할 수 있는 것 중 가장 직접적인** 행동이다. 유일한 방법이라는 근거는 없다 |
| "01의 답변에서 Gate 1·2·4와 허용 주기를 **한 번에 받을 수 있다**" | 문의문이 그것들을 **묻는다**는 사실과, 답변이 그것들을 **준다**는 사실은 다르다. 답변 내용은 우리가 정할 수 없다. 답을 받아 본 적도 없다 | 문의문은 그 항목들을 **묻는다.** 어디까지 답을 받을지는 알 수 없고, 답변이 와야 안다 |

"제공되지 않는다"는 답변도 결론이다. 그 경우 이 기능은 **공식·승인 경로가 생길 때까지 중단
상태로 유지한다.**

발송 전 확인: 문의문에 계정·비밀번호·카드정보가 없다. 현재 문안에 없다.

## 11. 원격 브라우저 구조 — 요건 2·3 충돌에 대한 정정 (2026-10-02 추가)

사용자가 지적한 내용이 맞다. §3-3의 초판 표현("구조적으로 충돌한다")을 정정한다.

### 11-1. 무엇이 틀렸나

**서버에 있는 브라우저를 사용자가 원격으로 직접 조작하는 구조는 기술적으로 가능하다.**
브라우저는 서버에서 계속 돌고, 사용자에게는 그 화면이 전송되고, 사용자의 입력이 그 브라우저로
전달된다. 사용자는 자기 손으로 로그인·추가 인증을 끝내고, 세션은 그 서버 브라우저 안에
남는다. 사용자가 자기 기기를 꺼도 서버 브라우저는 계속 떠 있다.

즉 요건 2(사용자 직접 로그인)와 요건 3(PC 꺼도 동작)이 **동시에 성립할 수 있다.** 초판은
"서버 브라우저는 사용자가 로그인할 수 없다"를 전제로 깔았는데, 그 전제가 우리가 가진 세
환경에만 해당하는 것이었고 일반 사실이 아니었다.

### 11-2. 쿠키 추출·이전과 브라우저 내부 인증 상태 유지는 다르다

이 구분이 핵심이다. `CLAUDE.md` 가 금지하는 것은 전자다.

| | 쿠키 추출·이전 (금지) | 브라우저 내부 인증 상태 유지 (금지 항목 아님) |
|---|---|---|
| 인증정보를 누가 들고 있나 | 우리 코드가 꺼내서 저장·전송한다 | 브라우저가 자기 쿠키 저장소에 그대로 들고 있다 |
| 우리가 읽는가 | 읽는다 | 읽지 않는다. 꺼내는 코드가 없다 |
| 비밀번호·OTP | 우리 입력폼을 거치는 설계로 번지기 쉽다 | 사용자가 공식 로그인 화면에 직접 입력한다 |
| 세션이 다른 곳으로 옮겨지는가 | 옮겨진다 | 옮겨지지 않는다. 처음 로그인한 브라우저에 남는다 |

후자는 사용자가 자기 브라우저에 로그인한 상태를 유지하는 것과 성질이 같다. 다른 점은 그
브라우저가 사용자 기기가 아니라 서버에 있다는 것뿐이다. **이것은 금지 항목에 해당하지
않는다.**

### 11-3. 그래도 지금 착수할 수 없는 이유

요건 2·3 충돌이 해소돼도 다음은 그대로 남는다.

| 남는 장애 | 왜 남는가 |
|---|---|
| **B. 지침 충돌** | 그 서버 브라우저가 하는 일이 바로 "공식 예매 화면을 브라우저로 조작하는 것"이다. 브라우저가 사용자 PC에 있든 서버에 있든 **기법이 같다.** §3-2의 세 곳 개정이 그대로 필요하다 |
| **접근 제한 관찰** | ADR 0003의 관찰이 그대로 적용된다. 오히려 데이터센터 IP에서 상시 구동되므로 사용자 PC보다 눈에 띄기 쉽다. 이것을 줄이려고 IP·지문·간격을 손대는 것이 바로 금지된 탐지 회피다 |
| **§4-1 관찰 근거 0/4** | 선택자·표시 문구·조작 흐름·예약 결과 확인 방법은 여전히 없다. 원격 브라우저는 "열어 볼 수단"일 뿐 근거를 주지 않는다 |
| **인프라 승인** | 상시 브라우저 + 화면 전송은 현재 배포 환경(Cloudflare Workers / Vercel 서버리스)에서 돌지 않는다. 별도 유료 인프라가 필요하고, 이는 §5·§7의 **별도 승인 대상**이다. 승인 없이 만들지 않았다 |
| **용도 제한** | 사용자도 같은 단서를 달았다 — 이것을 **접근 제한 회피 수단으로 쓰지 않는다.** 접근이 제한된 뒤 원격 브라우저로 바꿔 다시 접근하는 것은 호스트·IP를 바꿔 재시도하는 것과 같다 |

### 11-4. 정정 후 결론

- §3-3 표의 "요건 2·3 동시 충족 불가"는 **우리가 가진 세 실행 환경에 한정된 사실**이다.
  일반 사실이 아니다. 이 점을 정정했다.
- 그러나 **병목은 바뀌지 않는다.** 원격 브라우저는 장애 C의 일부를 풀 수 있지만 장애 A를
  풀지 못하고, 장애 B를 오히려 정면으로 건드린다. §3-5의 결론("A가 유일한 병목")은 그대로다.
- 따라서 이 구조를 지금 만들지 않았다. 만들려면 사용자의 두 가지 결정이 **먼저** 필요하다:
  §3-2 세 곳의 지침 개정, 그리고 상시 브라우저 인프라 승인.

### 11-5. KayRail 캡처

이번 요청은 "사용자가 제공한 KayRail 캡처를 참고한다"고 했으나, **이 세션에 캡처가 전달되지
않았다.** 저장소의 `docs/screenshots/` 에도 없다(`pr13-candidate-card` 만 있다). 그래서 화면
구성은 요청 본문의 §6 항목 서술만 근거로 작업했다. 캡처를 참고했다고 적지 않는다.

덧붙여, 설령 캡처가 있어도 그것은 **KayRail 화면의 구성**이고 §4-1이 요구하는 **공식 예매
화면의 선택자·표시 문구**가 아니다. 두 가지를 섞지 않는다.

## 12. PR #19 코드 검토 반영 (2026-10-02 추가)

### 12-1. 결함 설명 정정 — TAGO 결과가 "예약 가능/매진"으로 표시됐다는 주장을 철회한다

PR #19의 CHANGELOG·커밋 메시지·보고는 "공공데이터(TAGO) 열차 카드가 `availability` 값으로
'예약 가능'·'매진'을 적고 있었다"고 썼다. **이 주장을 철회한다.**

사실관계는 이렇다.

| 항목 | 확인된 내용 |
|---|---|
| TAGO Provider 가 넣는 값 | `lib/rail/tago-provider.ts` 가 `availability: "unknown"` 을 넣는다 — 좌석 항목이 없으므로 다른 값이 될 수 없다 |
| 수정 전 화면이 그 값을 표시한 문구 | `"좌석 확인 필요"` — `"예약 가능"` 도 `"매진"` 도 아니다 |
| 정상 TAGO 결과가 "예약 가능/매진"으로 표시된 재현 | **없다.** 재현하지 못했고, 재현 근거 없이 결함으로 적었다 |

따라서 이번 수정은 **버그 수정이 아니라 두 가지 보완**이다.

1. **출처별 좌석 표시 분리.** 수정 전에는 실제 열차와 데모 열차가 같은 `availability` 분기를
   공유했다. 그래서 데모의 `"예약 가능"`·`"매진"` 이 실제 좌석 상태와 같은 모양으로 나왔다.
   이제 출처(`source`)로 나누고, 데모에는 `"가상"` 과 `MOCK` 을 붙인다.
2. **문구 명확화.** `"좌석 확인 필요"` 는 "조회했는데 불확실하다" 로 읽힌다. 실제로는 **조회한
   적이 없다.** 그래서 `"좌석 미조회"` 로 바꿨다.

### 12-2. 금지 세 곳이 각각 무엇을 막는가

§3-2의 표를 "무엇을 막는지" 기준으로 다시 적는다. 셋은 겹치지만 같지 않다.

| 위치 | 성질 | 무엇을 막는가 | 어기면 무슨 일이 생기는가 |
|---|---|---|---|
| `CLAUDE.md` 「하지 않는 것」 | **프로젝트 내부 결정**(규범) | 공식 예매 화면을 브라우저로 조작하는 **설계 방향 자체** | 아무 일도 자동으로 생기지 않는다. 사람이 읽고 판단하는 문서다 |
| `docs/adr/0003-abandon-browser-agent.md` | **결정의 경위 기록** | 결정을 "설정값"으로 되돌리는 것. 되살릴 때 무엇을 뒤집는지 명시하게 만든다 | 역시 자동으로 막히지 않는다. 다만 뒤집은 기록이 남지 않으면 같은 실수를 반복한다 |
| `scripts/verify-autobook.cjs` | **코드에서 강제** | `lib/autobook` 안의 브라우저 구동(`chromium`·`playwright`·`page.goto` 등)과 폐기된 Agent 식별자 12개 | 검사가 FAIL 한다. 즉 되살리려면 이 검사를 **같은 PR에서 눈에 보이게 손대야** 한다 |

### 12-3. 내부 결정과 외부 관찰을 섞지 않는다

| | 프로젝트 내부 결정 | 실제 사이트에서 관찰된 접근 제한 |
|---|---|---|
| 무엇 | 공식 예매 화면을 브라우저로 조작하지 않는다 | SRT 예매 화면 + headed 자동화 + 사용자 Windows PC 조합에서 접속이 제한됐다 |
| 근거 | `CLAUDE.md`, ADR 0003 결정 1·2 | ADR 0003 「확인된 사실」 — 사용자 제공 증거 |
| 범위 | 프로젝트 전체 | **관찰된 조합 1건.** 다른 운영 주체·다른 화면까지 일반화된 근거는 없다 |
| 바꿀 수 있는가 | 사용자가 바꿀 수 있다 | 우리가 바꿀 수 없다 |
| 이용약관상 금지인가 | 해당 없음 | **미확인.** 약관 원문을 대조하지 못했다 |

이 구분이 흐려지면 두 방향으로 틀린다. 내부 결정을 "외부에서 확정적으로 금지한 것"으로
보고하거나(지침 충돌을 기술적 불가능으로 바꿔 보고하는 것), 관찰 1건을 "모든 화면 자동화가
막혔다"로 넓히는 것이다. 둘 다 하지 않는다.

### 12-4. 이번 UI 보완에서 하지 않은 것

- 금지 검사를 삭제·완화하지 않았다. `scripts/verify-autobook.cjs` 는 44 → 47 → 48 개로
  **늘렸다.** `FORBIDDEN_TOKENS` 와 브라우저 자동화 금지 검사는 손대지 않았다.
- 접근 제한이 관찰된 경로를 다시 실행하지 않았다. 철도 운영 주체로 나간 요청은 0건이다.
- 이번 수정으로 **실제 좌석 조회·실제 예약이 구현되지 않았다.** 옮겨진 것은 사용자가 고른
  조건이고, 등록 경로는 그대로 막혀 있다.
