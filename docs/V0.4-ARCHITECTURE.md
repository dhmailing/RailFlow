# RailFlow v0.4 — 안전한 자동예약 기반 아키텍처

## 0. 이 문서의 성격

이 PR은 **실제 예약을 구현하지 않는다.** 여기서 만든 것은 실제 Provider를 나중에 안전하게 연결할 수 있는 공통 기반(타입, 상태 모델, Queue/Worker 추상화, API, UI, 테스트)이다. 화면과 API가 반환하는 모든 결과에는 `simulation: true`가 포함되며, Mock임을 명확히 표시한다.

공식 API·계약·서면 허용 없이는 Live Provider를 활성화할 수 없다. 코레일-SR 통합(`코레일+`, 2026-09-01) 관련 공식 셀프서비스 실시간 잔여좌석·예약·결제 API는 이 시점까지 확인되지 않았다(PR #6 `docs/V0.4-INTEGRATION-RESEARCH.md` 참조, 병합 대기 중).

## 1. Provider 인터페이스 분리

v0.3은 시간표 조회 하나만 다뤘다. v0.4는 "시간표를 본다"와 "좌석을 확보한다"를 서로 다른 능력으로 분리했다.

```ts
// lib/rail/types.ts (기존, 이름만 명확화)
interface RailScheduleProvider {
  readonly mode: "demo" | "live";
  readonly sourceLabel: string;
  searchTrains(condition: TrainSearchCondition): Promise<TrainResult[]>;
}

// lib/reservation/types.ts (신규)
interface RailReservationProvider {
  readonly name: "mock" | "official";
  capabilities(): ProviderCapabilities;
  checkAvailability(job: ReservationJob): Promise<AvailabilityResult>;
  reserve(job: ReservationJob, candidateId: string): Promise<ReservationResult>;
  getReservation(job: ReservationJob): Promise<ReservationStatus>;
  cancel(job: ReservationJob): Promise<CancelResult>;
}
```

| 구현 | 파일 | 역할 |
| --- | --- | --- |
| `createTagoRailProvider` | `lib/rail/tago-provider.ts` | 기존 TAGO 시간표·운임 조회. 변경 없음(반환 타입만 `RailScheduleProvider`로 명명). |
| `mockRailProvider` | `lib/rail/mock-provider.ts` | 기존 데모 시간표. 변경 없음. |
| `mockReservationProvider` | `lib/reservation/mock-reservation-provider.ts` | `TrainCandidate.mockScenario`로만 결과가 결정되는 가짜 좌석·예약. 외부 요청 없음. |
| `officialReservationProviderStub` | `lib/reservation/official-reservation-provider-stub.ts` | 모든 메서드가 즉시 `OFFICIAL_INTEGRATION_REQUIRED`를 던진다. 네트워크 요청 없음. |

예약 Provider는 TAGO를 호출하지 않고 `DATA_GO_KR_SERVICE_KEY`를 참조하지 않는다. 시간표 조회와 좌석 확보는 서로 다른 신뢰 경계를 가진 별개 기능이다.

## 2. 예약 작업 상태 모델 (`lib/reservation/state-machine.ts`)

```
DRAFT → SCHEDULED → WATCHING ⇄ RATE_LIMITED / AUTH_REQUIRED
                        ↓
                    RESERVING → HELD → PAYMENT_PENDING → COMPLETED
                        ↓
                   (실패 시 WATCHING로 복귀, 도중 Provider 전환 시 PROVIDER_CHANGED)
어느 비종료 상태에서든 → CANCELLED
어느 비종료 상태에서든(COMPLETED 제외) → EXPIRED (expiresAt 경과)
```

- 종료 상태: `COMPLETED`, `CANCELLED`, `EXPIRED`, `FAILED`. 종료 상태에서는 어떤 전이도 허용하지 않는다(`assertTransition`이 `INVALID_TRANSITION`을 던진다).
- 만료 가드: `assertNotExpired(job)`은 `expiresAt`이 지난 비종료 작업이 `WATCHING`/`RESERVING` 등으로 다시 진행하는 것을 막는다. Worker는 매 단계 시작 시 이를 호출한다.
- 중복 방지: `lib/reservation/job-store.ts`의 `createJob`이 `userId·departureId·arrivalId·date·passengers`가 같은 **비종료** 작업이 있으면 `DUPLICATE_JOB`을 던진다. 취소·만료·완료된 작업은 같은 조건의 새 작업을 막지 않는다.
- 후보 중단 규칙: 여러 후보(`TrainCandidate[]`)가 있어도 상태는 작업 단위다. 한 후보가 확보되어 `HELD`로 전이하면 작업 전체가 `HELD`로 넘어가므로, Worker는 더 이상 다른 후보를 확인하지 않는다. 별도의 "다른 후보 취소" 로직이 필요 없다.
- 시간 표기: 저장(`ReservationJob`의 모든 시각 필드)은 ISO 8601 UTC 문자열이다. 화면은 `Asia/Seoul`로 변환해 표시한다(`components/reservation-jobs.tsx`).

## 3. Queue / Worker 추상화

`lib/reservation/queue.ts`(메시지 저장)와 `lib/reservation/worker.ts`(메시지 처리)는 별도 모듈로 분리했다. **이번 PR의 구현은 프로세스 메모리 기반이며 테스트·데모 전용이다.** Vercel Serverless 함수는 요청이 끝나면 프로세스가 재사용된다는 보장이 없고, 인스턴스 간 메모리를 공유하지 않으며, 함수 실행 시간에 상한이 있다. 그래서 이번 구조는 "긴 백그라운드 감시"를 요청 하나에 묶지 않고, 매 API 호출이 큐에 메시지를 넣고 그 자리에서 한 스텝만 배수(drain)하는 방식으로 만들었다(`worker.runJobOnce`).

- **kill switch**: `ENABLE_RESERVATION_JOBS=false`이면 `worker.drainOnce`/`runJobOnce`가 즉시 `JOBS_DISABLED`를 던진다. 개별 작업을 하나씩 멈출 필요 없이 전체를 즉시 정지시킬 수 있다.
- **멱등키**: `queue.enqueue({ jobId, userId, idempotencyKey })`는 같은 `idempotencyKey`가 이미 들어온 적이 있으면 큐에 다시 넣지 않고 `"duplicate"`를 반환한다. API에서 동일한 재시도 요청이 두 번 들어와도 작업이 두 번 진행되지 않는다.
- **동시 실행 잠금**: `worker.ts`의 `locksByJobId`는 같은 `jobId`에 대한 동시 처리를 막는다. 실제 큐(SQS 등)의 가시성 타임아웃(visibility timeout)에 해당하는 역할을 인메모리로 흉내낸 것이다.
- **프로세스 재시작 가정**: 이 구현은 재시작하면 큐와 잠금이 모두 사라진다. 실제 운영에는 맞지 않으며, 아래 ADR에서 대안을 비교한다.

## 4. 기능 플래그 (fail-closed)

| 이름 | 값 | 기본/취급 |
| --- | --- | --- |
| `RAIL_SCHEDULE_PROVIDER` | `tago` \| `mock` | 기본 `tago`. v0.3 검색 API 자체는 그대로 두고, `provider-status` 응답과 향후 통합용으로만 사용. |
| `RAIL_RESERVATION_PROVIDER` | `disabled` \| `mock` \| `official` | 값이 없거나 인식할 수 없으면 항상 `disabled`. |
| `ENABLE_RESERVATION_JOBS` | `true`/`false` | 기본 `false`. Worker의 kill switch. |
| `ENABLE_MOCK_SIMULATION` | `true`/`false` | 기본 `false`. §5의 시뮬레이션 간격 가드 중 하나. |
| `ALLOW_LIVE_RESERVATION` | (무시됨) | **코드가 값을 읽지 않는다.** `lib/reservation/feature-flags.ts`의 `isLiveReservationAllowed()`는 항상 `false`를 반환하도록 하드코딩했다. 이번 PR에서 실제 예약을 허용하는 경로는 존재하지 않는다. |

설정이 누락되면 항상 비활성화 쪽으로 떨어진다(`readEnv`가 빈 문자열이면 `disabled`/`false`로 처리).

## 5. `1~5초 Mock 작업 시뮬레이션 간격`의 격리

`lib/reservation/simulation-guard.ts`의 `assertSimulationAllowed`는 다음을 **서버에서** 모두 만족해야만 통과한다.

```
intervalSeconds ∈ {1,2,3,4,5} (정수)
AND NODE_ENV !== "production"
AND provider === "mock"
AND ENABLE_MOCK_SIMULATION === true
```

- 클릭 간격·요청 간격이 아니다. 값은 `/api/reservations/[id]/simulate`가 한 번의 Worker 스텝을 실행할지 말지 결정하는 조건일 뿐이며, 실제 외부 URL로 요청을 보내지 않는다(Mock Provider는 애초에 `fetch`를 호출하지 않는다).
- UI(`components/reservation-jobs.tsx`)는 `process.env.NODE_ENV !== "production"`이고 `provider-status`가 `mockSimulationEnabled: true`를 반환할 때만 1~5초 버튼을 렌더링한다. 하지만 이것은 편의를 위한 것일 뿐, 실제 차단은 항상 서버 쪽 `assertSimulationAllowed`가 수행한다 — UI를 우회해 직접 API를 호출해도 조건을 만족하지 못하면 `SIMULATION_INTERVAL_NOT_ALLOWED`가 반환된다.
- `scripts/verify-reservation.cjs`가 1~5초 허용, 0/6/2.5/문자열/음수 거부, `NODE_ENV=production`에서 항상 거부, `provider!=="mock"`에서 거부, `ENABLE_MOCK_SIMULATION=false`에서 거부를 모두 검증한다.

## 6. API

모든 라우트는 `export const dynamic = "force-dynamic"`이며 Zod로 입력을 검증한다. 인증이 아직 없으므로 `userId`는 `^demo-[a-zA-Z0-9_-]{1,40}$` 형식만 허용해 v0.3처럼 "데모 범위"임을 명시한다(`lib/reservation/http.ts`의 `DEMO_USER_ID_PATTERN`).

| 메서드/경로 | 기능 | 실패 |
| --- | --- | --- |
| `POST /api/reservations` | 작업 생성 | 429 요청 제한, 503 `JOBS_DISABLED`(비활성화), 400 입력 오류, 409 `DUPLICATE_JOB` |
| `GET /api/reservations?userId=` | 목록 조회 | 400 잘못된 `userId` |
| `GET /api/reservations/[id]?userId=` | 상세 조회 | 404 `NOT_FOUND`(다른 사용자 소유 포함) |
| `POST /api/reservations/[id]/cancel` | 취소 | 404, 409 `INVALID_TRANSITION`(이미 종료된 작업) |
| `POST /api/reservations/[id]/simulate` | Worker 한 스텝 실행(+선택적 시뮬레이션 간격) | 403 `SIMULATION_INTERVAL_NOT_ALLOWED`, 503 `JOBS_DISABLED` |
| `GET /api/reservations/provider-status` | 두 Provider의 활성 상태·capability·플래그 조회(비밀값 없음) | - |

## 7. UI

`app/page.tsx`의 기존 `자동예약` 탭(로컬스토리지 기반 v0.3 UX)은 그대로 유지했다. 그 아래에 `components/reservation-jobs.tsx`를 새로 추가해 서버의 v0.4 작업을 별도 영역("Mock 자동예약 작업 (v0.4 서버 기반 미리보기)")으로 보여준다. 항상 `MOCK` 배지와 "실제 예약이 이루어지지 않습니다" 안내를 표시하고, `RAIL_RESERVATION_PROVIDER=disabled`이거나 `ENABLE_RESERVATION_JOBS=false`이면(운영 기본값) 폼 대신 비활성화 안내만 보여준다.

## 8. 의도적으로 구현하지 않은 것

- 실제 코레일/SR/코레일+ 계정 로그인, 결제, 발권.
- 매크로 탐지 회피, 요청/클릭 간격 무작위화, User-Agent/IP/세션 로테이션.
- 비공개 API 역공학, 화면 자동조작(AccessibilityService/좌표클릭/OCR).
- CAPTCHA·2단계 인증·대기열 우회.
- 실제 사용자 인증(로그인) 체계 — `userId`는 데모 스코프 문자열이며, 이번 PR은 이를 신뢰 가능한 인증으로 위장하지 않는다.
- 영속 저장소(PostgreSQL/Redis 등) — 아래 ADR 참조. 서버 재시작 시 모든 Mock 작업이 사라진다.
