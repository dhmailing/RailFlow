# RailFlow v0.4 — 안전한 자동예약 기반 아키텍처

## 0. 이 문서의 성격

이 PR은 **실제 예약을 구현하지 않는다.** 여기서 만든 것은 실제 Provider를 나중에 안전하게 연결할 수 있는 공통 기반(타입, 상태 모델, Queue/Worker 추상화, API, UI, 테스트)이다. `ReservationJob` 자체가 `simulation: boolean` 필드를 가지며(`lib/reservation/job-store.ts`의 `createJob`이 설정), 작업 생성이 "mock" Provider로만 허용되므로(§6) 이번 PR에서 만들어지는 모든 작업은 `simulation: true`다. `{ job }`을 반환하는 모든 API 응답과 화면이 이 필드를 그대로 사용하므로, 타입·저장소·API·UI가 같은 계약을 공유한다.

공식 API·계약·서면 허용 없이는 Live Provider를 활성화할 수 없다. 코레일-SR 통합(`코레일+`, 2026-09-01) 관련 공식 셀프서비스 실시간 잔여좌석·예약·결제 API는 이 시점까지 확인되지 않았다(PR #6 `docs/V0.4-INTEGRATION-RESEARCH.md` 참조, 병합 대기 중).

## 1. Provider 인터페이스 분리

v0.3은 시간표 조회 하나만 다뤘다. v0.4는 "시간표를 본다"와 "좌석을 확보한다"를 서로 다른 능력으로 분리했다.

```ts
// lib/rail/types.ts (기존, 이름만 명확화)
interface RailScheduleProvider {
  readonly mode: "demo" | "live";
  readonly sourceLabel: string;
  searchTrains(condition: TrainSearchCondition): Promise<TrainResult[]>;
}

// lib/reservation/types.ts (신규)
interface RailReservationProvider {
  readonly name: "mock" | "official";
  capabilities(): ProviderCapabilities;
  checkAvailability(job: ReservationJob): Promise<AvailabilityResult>;
  reserve(job: ReservationJob, candidateId: string): Promise<ReservationResult>;
  getReservation(job: ReservationJob): Promise<ReservationStatus>;
  cancel(job: ReservationJob): Promise<CancelResult>;
}
```

| 구현 | 파일 | 역할 |
| --- | --- | --- |
| `createTagoRailProvider` | `lib/rail/tago-provider.ts` | 기존 TAGO 시간표·운임 조회. 변경 없음(반환 타입만 `RailScheduleProvider`로 명명). |
| `mockRailProvider` | `lib/rail/mock-provider.ts` | 기존 데모 시간표. 변경 없음. |
| `mockReservationProvider` | `lib/reservation/mock-reservation-provider.ts` | `TrainCandidate.mockScenario`로만 결과가 결정되는 가짜 좌석·예약. 외부 요청 없음. |
| `officialReservationProviderStub` | `lib/reservation/official-reservation-provider-stub.ts` | 모든 메서드가 즉시 `OFFICIAL_INTEGRATION_REQUIRED`를 던진다. 네트워크 요청 없음. |

예약 Provider는 TAGO를 호출하지 않고 `DATA_GO_KR_SERVICE_KEY`를 참조하지 않는다. 시간표 조회와 좌석 확보는 서로 다른 신뢰 경계를 가진 별개 기능이다.

## 2. 예약 작업 상태 모델 (`lib/reservation/state-machine.ts`)

```
DRAFT → SCHEDULED → WATCHING ⇄ RATE_LIMITED / AUTH_REQUIRED
                        ↓
                    RESERVING → HELD → PAYMENT_PENDING → COMPLETED
                        ↓
                   (실패 시 WATCHING로 복귀)
모든 비종료 상태(PAYMENT_PENDING 포함)에서 Provider 전환 시 → PROVIDER_CHANGED → FAILED
어느 비종료 상태에서든 → CANCELLED
PAYMENT_PENDING을 제외한 모든 비종료 상태에서 → EXPIRED (expiresAt 경과, 실제로 저장된다)
```

- 종료 상태: `COMPLETED`, `CANCELLED`, `EXPIRED`, `FAILED`. 종료 상태에서는 어떤 전이도 허용하지 않는다(`assertTransition`이 `INVALID_TRANSITION`을 던진다).
- **만료는 실제로 저장된 상태다.** `state-machine.ts`의 `hasExpired(job)`은 `expiresAt` 경과 여부만 판정하는 순수 함수이고, `worker.ts`의 `runStep`이 매 단계 시작 시 이를 호출해 경과했으면 즉시 `jobStore.transitionJob(..., "EXPIRED", ...)`으로 **영속 전이**시키고 그 저장된 작업을 반환한다(예외를 던지고 끝내지 않는다). 이미 `EXPIRED`인 작업을 다시 실행해도 Provider를 호출하지 않고 상태·history가 그대로 반환된다.
- `expiresAt`(감시/조회 마감)과 `holdExpiresAt`(좌석 확보 후 결제 마감)은 서로 다른 필드다. `HELD`로 전이할 때 Provider의 `ReservationResult.holdExpiresAt`을 `ReservationJob.holdExpiresAt`에 저장하고, `HELD→PAYMENT_PENDING` 전이는 이 값을 건드리지 않는다. **`PAYMENT_PENDING` 상태는 감시 마감(`expiresAt`)으로 만료시키지 않는다** — `holdExpiresAt` 기반 결제 만료 처리는 이번 PR 범위에서 구현하지 않았다(§8).
- 중복 방지: `lib/reservation/job-store.ts`의 `createJob`이 `userId·departureId·arrivalId·date·passengers`가 같은 **비종료** 작업이 있으면 `DUPLICATE_JOB`을 던진다. 취소·만료·완료된 작업은 같은 조건의 새 작업을 막지 않는다.
- 후보 중단 규칙: 여러 후보(`TrainCandidate[]`)가 있어도 상태는 작업 단위다. 한 후보가 확보되어 `HELD`로 전이하면 작업 전체가 `HELD`로 넘어가므로, Worker는 더 이상 다른 후보를 확인하지 않는다. 별도의 "다른 후보 취소" 로직이 필요 없다.
- Provider 전환: Worker는 매 단계에서 `RAIL_RESERVATION_PROVIDER`가 작업 생성 시점의 `job.provider`와 다른지 가장 먼저 확인한다(만료 확인 다음, 상태별 로직보다 먼저). `PAYMENT_PENDING`을 포함한 모든 비종료 상태에서 동일하게 `PROVIDER_CHANGED`로 전이할 수 있다 — 상태별로 허용 여부가 갈리지 않는다.
- 시간 표기: 저장(`ReservationJob`의 모든 시각 필드)은 ISO 8601 UTC 문자열이다. 화면은 `Asia/Seoul`로 변환해 표시한다(`components/reservation-jobs.tsx`).

## 3. Queue / Worker 추상화

`lib/reservation/queue.ts`(메시지 저장)와 `lib/reservation/worker.ts`(메시지 처리)는 별도 모듈로 분리했다. **이번 PR의 구현은 프로세스 메모리 기반이며 테스트·데모 전용이다.** Vercel Serverless 함수는 요청이 끝나면 프로세스가 재사용된다는 보장이 없고, 인스턴스 간 메모리를 공유하지 않으며, 함수 실행 시간에 상한이 있다. 그래서 이번 구조는 "긴 백그라운드 감시"를 요청 하나에 묶지 않고, 매 API 호출이 큐에 메시지를 넣고 그 자리에서 한 스텝만 배수(drain)하는 방식으로 만들었다(`worker.runJobOnce`).

- **kill switch**: `ENABLE_RESERVATION_JOBS=false`이면 `worker.drainOnce`/`runJobOnce`가 즉시 `JOBS_DISABLED`를 던진다. 개별 작업을 하나씩 멈출 필요 없이 전체를 즉시 정지시킬 수 있다.
- **멱등키는 작업 단위로 격리된다**: `queue.enqueue`는 클라이언트가 보낸 `idempotencyKey`를 그대로 저장하지 않고 `userId::jobId::idempotencyKey` 복합키로 저장한다. 같은 작업에 대한 같은 키의 재시도만 `"duplicate"`로 처리되어 재실행되지 않는다. 서로 다른 사용자·작업이 우연히 같은 원본 키 문자열을 보내도 서로를 가리지 않고 각각 정상 처리된다.
- **동시 실행 잠금**: `worker.ts`의 `locksByJobId`는 같은 `jobId`에 대한 동시 처리를 막는다. 실제 큐(SQS 등)의 가시성 타임아웃(visibility timeout)에 해당하는 역할을 인메모리로 흉내낸 것이다.
- **프로세스 재시작 가정**: 이 구현은 재시작하면 큐와 잠금이 모두 사라진다. 실제 운영에는 맞지 않으며, 아래 ADR에서 대안을 비교한다.

## 4. 기능 플래그 (fail-closed)

| 이름 | 값 | 기본/취급 |
| --- | --- | --- |
| `RAIL_SCHEDULE_PROVIDER` | `tago` \| `mock` | 기본 `tago`. v0.3 검색 API 자체는 그대로 두고, `provider-status` 응답과 향후 통합용으로만 사용. |
| `RAIL_RESERVATION_PROVIDER` | `disabled` \| `mock` \| `official` | 값이 없거나 인식할 수 없으면 항상 `disabled`. |
| `ENABLE_RESERVATION_JOBS` | `true`/`false` | 기본 `false`. Worker의 kill switch. |
| `ENABLE_MOCK_SIMULATION` | `true`/`false` | 기본 `false`. §5의 시뮬레이션 간격 가드 중 하나. |
| `ALLOW_LIVE_RESERVATION` | (무시됨) | **코드가 값을 읽지 않는다.** `lib/reservation/feature-flags.ts`의 `isLiveReservationAllowed()`는 항상 `false`를 반환하도록 하드코딩했다. 이번 PR에서 실제 예약을 허용하는 경로는 존재하지 않는다. |

설정이 누락되면 항상 비활성화 쪽으로 떨어진다(`readEnv`가 빈 문자열이면 `disabled`/`false`로 처리).

이 4개 플래그와는 별개로, 사용자 인증이 아직 없다는 이유만으로 **Demo 예약 작업 API(§6) 전체는 `NODE_ENV==="production"`이면 플래그 값과 무관하게 항상 막힌다**(`lib/reservation/http.ts`의 `isProductionEnvironment`/`productionBlockedResponse`). 위 플래그들이 실수로 운영에 켜져도 이 블록이 별도로 막는다.

## 5. `Mock 작업 시뮬레이션 간격`(검증값 1~5)의 격리

이름과 달리 **실제로 기다리거나 반복 실행되지 않는다.** 값은 `/api/reservations/[id]/simulate`가 Worker 한 스텝을 즉시 실행할지 말지 결정하는 검증값일 뿐이다 — N초 뒤에 실행되지도, N초마다 반복되지도 않는다. UI 버튼 라벨도 "N초 시뮬레이션"이 아니라 "검증값 N · 한 단계 실행"으로 표기해 실제 동작을 과장하지 않는다.

`lib/reservation/simulation-guard.ts`의 `assertSimulationAllowed`는 다음을 **서버에서** 모두 만족해야만 통과한다.

```
intervalSeconds ∈ {1,2,3,4,5} (정수)
AND NODE_ENV !== "production"
AND provider === "mock"
AND ENABLE_MOCK_SIMULATION === true
```

- `simulationIntervalSeconds`는 `/api/reservations/[id]/simulate` 요청 본문의 **필수** 필드다(선택 필드가 아니다). 이 필드가 있을 때만 가드를 호출하는 분기는 존재하지 않는다 — 모든 요청이 값을 파싱한 뒤 예외 없이 `assertSimulationAllowed`를 통과해야만 `runJobOnce`가 호출된다. 필드가 없거나, 0/6/소수/문자열이거나, `NODE_ENV==="production"`이거나, 작업의 Provider가 `mock`이 아니거나, `ENABLE_MOCK_SIMULATION=false`이면 Worker는 전혀 호출되지 않고 작업의 상태·history·attempts는 그대로 남는다.
- 값은 실제 외부 URL로 요청을 보내지 않는다(Mock Provider는 애초에 `fetch`를 호출하지 않는다).
- UI(`components/reservation-jobs.tsx`)는 개발 환경이고 `provider-status`가 `mockSimulationEnabled: true`를 반환할 때만 버튼을 렌더링하며, 운영 빌드(`NODE_ENV==="production"`)에서는 이 패널 전체가 폼·버튼 없이 비활성화 안내만 보여준다(§7). 하지만 이것은 편의를 위한 것일 뿐, 실제 차단은 항상 서버 쪽 `assertSimulationAllowed`와 §4의 production 블록이 수행한다 — UI를 우회해 직접 API를 호출해도 조건을 만족하지 못하면 `SIMULATION_INTERVAL_NOT_ALLOWED`가, production이면 `JOBS_DISABLED`가 반환된다.
- `scripts/verify-reservation.cjs`가 1~5초 허용, 0/6/2.5/문자열/누락 거부, `NODE_ENV=production`에서 (필드 유무와 무관하게) 항상 거부하고 작업이 전혀 바뀌지 않음, `provider!=="mock"`에서 거부, `ENABLE_MOCK_SIMULATION=false`에서 거부를 모두 route 단위로 검증한다.

## 6. API

모든 라우트는 `export const dynamic = "force-dynamic"`이며 Zod로 입력을 검증한다. 인증이 아직 없으므로 `userId`는 `^demo-[a-zA-Z0-9_-]{1,40}$` 형식만 허용해 v0.3처럼 "데모 범위"임을 명시한다(`lib/reservation/http.ts`의 `DEMO_USER_ID_PATTERN`). **`provider-status`를 제외한 아래 라우트는 모두 `NODE_ENV==="production"`이면 다른 검증보다 먼저 503 `JOBS_DISABLED`로 거부된다**(§4).

| 메서드/경로 | 기능 | 실패 |
| --- | --- | --- |
| `POST /api/reservations` | 작업 생성(Provider가 `mock`일 때만) | 503 production 블록, 429 요청 제한, 503 `JOBS_DISABLED`(비활성화), 503 `OFFICIAL_INTEGRATION_REQUIRED`(Provider가 `official`), 400 입력 오류, 409 `DUPLICATE_JOB` |
| `GET /api/reservations?userId=` | 목록 조회 | 503 production 블록, 400 잘못된 `userId` |
| `GET /api/reservations/[id]?userId=` | 상세 조회 | 503 production 블록, 404 `NOT_FOUND`(다른 사용자 소유 포함) |
| `POST /api/reservations/[id]/cancel` | 취소 | 503 production 블록, 404, 409 `INVALID_TRANSITION`(이미 종료된 작업) |
| `POST /api/reservations/[id]/simulate` | Worker 한 스텝 실행(`simulationIntervalSeconds` 필수) | 503 production 블록, 403 `SIMULATION_INTERVAL_NOT_ALLOWED`, 503 `JOBS_DISABLED`, 400 필드 누락/형식 오류 |
| `GET /api/reservations/provider-status` | 두 Provider의 활성 상태·capability·플래그 조회(비밀값 없음). production에서도 항상 응답한다 | - |

`official` Provider는 Stub이므로 애초에 작업을 생성할 수 없다(`POST /api/reservations`가 `RAIL_RESERVATION_PROVIDER=official`이면 생성 단계에서 차단). 따라서 `WATCHING` 상태까지 진행된 뒤 `checkAvailability`가 반복적으로 `OFFICIAL_INTEGRATION_REQUIRED`를 기록하며 멈춰 있는 작업은 만들어지지 않는다.

## 7. UI

`app/page.tsx`의 기존 `자동예약` 탭(로컬스토리지 기반 v0.3 UX)은 그대로 유지했다. 그 아래에 `components/reservation-jobs.tsx`를 새로 추가해 서버의 v0.4 작업을 별도 영역("Mock 자동예약 작업 (v0.4 서버 기반 미리보기)")으로 보여준다. 항상 `MOCK` 배지와 "실제 예약이 이루어지지 않습니다" 안내를 표시하고, 개별 작업 카드에도 `job.simulation`이 true일 때 `MOCK` 배지를 붙인다.

`process.env.NODE_ENV==="production"`이면 이 패널은 provider-status를 조회하지도 않고 곧바로 "개발용 Mock 기능이며 실제 예약이 아니다"라는 비활성화 안내만 보여준다(폼·버튼 전부 렌더링하지 않음). 개발 환경에서도 `RAIL_RESERVATION_PROVIDER=disabled`이거나 `ENABLE_RESERVATION_JOBS=false`이면 같은 방식으로 비활성화 안내만 보여준다.

## 8. 의도적으로 구현하지 않은 것

- 실제 코레일/SR/코레일+ 계정 로그인, 결제, 발권.
- 매크로 탐지 회피, 요청/클릭 간격 무작위화, User-Agent/IP/세션 로테이션.
- 비공개 API 역공학, 화면 자동조작(AccessibilityService/좌표클릭/OCR).
- CAPTCHA·2단계 인증·대기열 우회.
- 실제 사용자 인증(로그인) 체계 — `userId`는 데모 스코프 문자열이며, 이번 PR은 이를 신뢰 가능한 인증으로 위장하지 않는다. 인증이 없는 동안에는 §4/§6의 production 블록이 그 대체 안전장치다. 실제 인증이 생기면 이 블록을 그 인증·인가 체계로 교체해야 한다(코드 주석에 TODO로 남김, `lib/reservation/http.ts`).
- `holdExpiresAt`(좌석 확보 후 결제 마감) 기반 `PAYMENT_PENDING` 자동 만료 — Provider 결과의 `holdExpiresAt`을 저장은 하지만, 이를 근거로 작업을 자동 만료시키는 로직은 이번 PR에 없다.
- 영속 저장소(PostgreSQL/Redis 등) — 아래 ADR 참조. 서버 재시작 시 모든 Mock 작업이 사라진다.
