# RailFlow v0.3 작업·검증 기록

## 배포 상태

작업 버전은 v0.3. 현재 공개 주소의 v0.2는 교체하지 않았다. 사용자가 요구한 새 키로 실제 조회 및 최종 화면 검증 조건을 충족한 뒤 배포한다.

공개 주소: https://railflow.dhmailing0310.chatgpt.site

## 화면 원인·조치

날짜/시간 입력의 내재 폭과 2열 카드, 긴 역 이름과 버튼의 단일 행 배치가 좁은 화면에서 충돌할 수 있었다. 입력 width/max-width/min-width를 명시하고 480px 미만에서는 날짜/시간을 세로 배치, 640px 미만에서는 역 선택을 세로 배치했다. 결과 카드와 헤더 정보는 필요한 위치에서 줄바꿈한다. 기존 색상/디자인을 유지했다. 내용을 감추는 overflow 처리는 해결책으로 사용하지 않았다.

## 검증 결과

- TypeScript, ESLint, 프로덕션 빌드 통과(최종 저장 전 재실행).
- Chrome 브라우저의 같은 출처 iframe을 사용한 폭 검사: 320/375/768/820/1024/1180/1440px에서 문서 scrollWidth가 clientWidth를 초과하지 않았다. 작은 폭은 브라우저 스크롤바 15px를 제외한 실제 내부 폭으로도 통과했다.
- 데모 3개 결과 카드와 긴 역 이름 울산(통도사) 표시 확인. 320px 설정 화면도 가로 넘침 없음.
- 역 선택창 클릭으로 목록 열림, 부분 검색, 마우스 선택, 방향키+Enter 선택 확인.
- 날짜만 변경한 뒤 09:30 유지, 초기화 후 00:00 확인. 첫 로딩 00:00 확인.
- 인증키 미설정 상태에서 사용자 안내 및 검색 비활성 상태 확인.
- 브라우저 콘솔에서 관찰된 오류는 검증 브라우저 확장 프로그램의 메타데이터 전송 오류였다. 앱 전체 세션에 오류가 전혀 없다는 보증으로 간주하지 않는다.
- iPad Safari 실기기/실제 터치 검증은 미실행. Chrome의 태블릿 폭 검증과 구별해야 한다.

## 모의 API 검증

테스트용 합성 코드와 가짜 키만 사용하며 인터넷 요청은 하지 않는다. 실제 인증 성공 증거가 아니다.

- 6개 역 목록 동시 2회 조회 → 고유 도시 4건의 외부 요청으로 병합.
- 목록 캐시가 따뜻한 상태에서 동일 검색 동시 2회 → 시간표 요청 1건.
- 동일 조건 재조회 → 시간표 요청 0건.
- 조건 키: 모드·출발 코드·도착 코드·날짜·시간. 운임은 성인 1인 기준이므로 인원은 캐시 구분에서 제외.
- 캐시 60초, 최대 200개, 성공 응답만 저장. 도시/역 목록은 24시간. 메모리 캐시는 Worker 인스턴스마다 분리되며 영속/전역 캐시가 아니다.
- 모의 30ms 외부 지연 기준 측정: 최초 35ms, 캐시 1ms. 실제 TAGO 응답시간 및 v0.2 대비 속도 개선률로 인용하면 안 된다.
- 코드·날짜 전달, 시간 필터, 운임 매핑, 동일 역/잘못된 날짜 차단, 이름-코드 불일치 차단 확인.
- 인증/429/형식 오류/timeout/네트워크 오류/결과 없음 구별. 오류 캐시 안 됨.
- timeout 10초, 네트워크 TypeError에만 1회 재시도. 인증·429·timeout 재시도 없음. 클라이언트 전체 검색 제한 25초.
- 브라우저 검색은 조건 변경/초기화/새 요청 시 AbortController로 취소. 서버에서 이미 공유 중인 외부 조회는 다른 사용자를 위해 완료될 수 있다.

## 성능의 남은 검증

기존 v0.2 페이지 JS 청크는 198,982 bytes였다. 검색형 Combobox 도입 후 추가 코드가 필요하며, 설정 분리와 인원 선택 간소화를 적용한 중간 빌드의 페이지 청크는 214,618 bytes였다. 분리된 공유 청크도 있어 이 단일 청크만으로 전체 초기 전송량을 비교하면 안 된다. 초기 JS 감소나 실제 초기 렌더링 개선은 아직 입증하지 못했다. 서비스 워커의 첫 HTML 중복 요청은 제거했다.

실제 TAGO 대기시간, 수정 전후 동일 환경의 렌더링 시간, 브라우저에서 지연 응답 중 연속 검색 취소 측정은 후속 검증 대상이다.

## 보안·재개 조건

- 노출된 키는 이번 작업에서 사용하지 않았다. Sites의 다음 배포용 DATA_GO_KR_SERVICE_KEY를 제거했다(환경 설정 revision 2).

- 새 키는 서버 Secret DATA_GO_KR_SERVICE_KEY에만 등록한다. 채팅·코드·README·로그에 키 값을 쓰지 않는다.
- 새 키 등록 후 실제 동탄→울산 및 서울→부산 조회와 공식 코드 목록 검증, Safari 검증을 마친 뒤 기존 주소에 배포한다.

## 이어받기 세션 추가 검증 (2026-09-19, Claude)

인계서(RailFlow_Claude_Handoff_v0.3.md)와 첨부 소스(RailFlow_Source_v0.3.zip)를 기준으로 저장소에 v0.3 코드를 반영하고, 위 "미확인" 항목 중 코드 실행 환경에서 확인 가능한 부분을 추가로 점검했다. 코드는 변경하지 않았다(정적 검토 결과 수정이 필요한 결함을 발견하지 못함).

### 환경 재현

- Node v22.22.2, pnpm 11.25.0 확인. `pnpm install --frozen-lockfile`, `pnpm exec tsc --noEmit`, `pnpm lint`, `node scripts/verify-rail.cjs`, `pnpm build` 모두 재실행하여 통과를 재확인했다. 잠금파일·버전은 변경하지 않았다.
- `node scripts/verify-rail.cjs` 결과는 기존 보고와 동일(`stationRequests:4`, `concurrentSearchRequests:1`, `cachedSearchRequests:0`, `realApiTest:"NOT RUN — fresh secret required"`). 이 스크립트는 여전히 실제 네트워크를 사용하지 않는 모의 테스트다.

### 실제 키 없이 가능한 코드 정확성 점검 (신규)

새 Secret 없이도 실 조회 실패 원인이 될 수 있는 두 항목을 코드 검토와 공개 자료 교차 확인으로 점검했다. **이 결과는 실제 키로 호출해 성공한 것이 아니라, 코드가 알려진 TAGO API 규격과 일치하는지 확인한 간접 검증이다.**

- `lib/rail/stations.ts`의 cityCode(동탄·광명 31, 울산(통도사) 26, 수서·서울 11, 부산 21)는 공개된 TAGO TrainInfoService 사용 사례(복수의 독립적인 온라인 자료)에서 확인되는 도시 코드 체계(11 서울·21 부산·22 대구·23 인천·24 광주·25 대전·26 울산, 31 경기·32 강원…)와 일치했다. data.go.kr 원본 문서는 프록시 정책상 직접 열람하지 못해(egress 차단) 2차 자료로만 교차 확인했으므로 확정이 아니라 "개연성 높음"으로 분류한다.
- `app/api/trains/search/route.ts`의 `departureId`/`arrivalId` 검증(`NAT[A-Z0-9]+` 접두 요구)이 실제 운영 코드와 맞지 않으면 실 모드에서 모든 검색이 400으로 막히는 결함이 될 수 있어 점검했다. 공개된 API 사용 예시에서 실제 nodeid가 `NAT010000` 형태로 `NAT` 접두를 사용하는 것을 확인했다. 마찬가지로 2차 자료 기반이며, 새 키로 `/api/trains/stations?mode=live` 응답을 직접 확인하기 전까지는 최종 확정이 아니다.
- 위 두 항목 모두 결함이 발견되지 않아 코드를 수정하지 않았다. 새 Secret 등록 후 실제 응답에서 이 값들이 일치하는지는 여전히 사용자(또는 배포 담당자)의 확인이 필요하다.

### 실제 브라우저 통합 검증 (신규, Playwright + Chromium)

기존 검증은 Chrome 동일 출처 iframe의 폭 검사에 한정되어 있었다. 이번에는 로컬 프로덕션 빌드(`pnpm build` 결과를 `pnpm start`로 Cloudflare Worker 로컬 프리뷰 실행)를 대상으로 Playwright(Chromium, 프로젝트 의존성에는 추가하지 않고 임시 검증 환경에서만 사용)로 실제 브라우저 동작을 확인했다. **Chromium 기반이며 실제 iPad Safari 검증을 대체하지 않는다.**

- iPad Air 뷰포트(820×1180, deviceScaleFactor 2, iPadOS Safari User-Agent, 터치 활성화)에서 `document.documentElement.scrollWidth`가 `clientWidth`를 넘지 않음을 확인(가로 스크롤 없음).
- 역 선택 Combobox에 키보드로 "동탄"/"부산"을 입력 → 방향키+Enter로 선택 → 실제 DOM 입력값이 각각 반영됨을 확인(데모 모드).
- 데모 모드에서 열차 검색 실행 후 결과 카드가 실제로 렌더링됨을 확인.
- Playwright의 요청 인터셉트로 `/api/trains/search` 응답에 인위적 3초 지연을 주입한 상태에서, 검색 시작 직후 출발일을 변경하면 "열차 확인 중" 스피너 상태가 즉시 해제되고(클라이언트 AbortController 동작), 지연 시간이 다 지나도 스피너가 멈춰 있지 않으며, 연속 조건 변경에도 서버로 나간 검색 요청이 누적되지 않음(요청 수 ≤3)을 확인했다. 이는 실제 TAGO 응답 지연이 아니라 인위적으로 주입한 지연이며, 실제 외부망 지연·iPad Safari 환경에서의 통합 검증을 대체하지 않는다.
- 콘솔 오류는 없었다. 단, 실 모드(키 미설정) 초기 진입 시 `/api/trains/stations` 503 응답이 브라우저 네트워크 로그에 오류로 기록되는데, 이는 키 미설정을 알리는 설계된 동작이며 애플리케이션 예외가 아니다.

### 프로덕션 빌드 실측치 (신규, v0.3 단독 기준선)

Cloudflare Worker 로컬 프리뷰(`pnpm start`, loopback)에서 Playwright로 최초 페이지 로드를 측정했다. **v0.2 소스가 첨부되지 않아 동일 조건 비교는 여전히 불가능하며, 아래는 v0.3의 현재 실측 기준선일 뿐이다. 루프백(localhost) 측정이라 실제 네트워크 지연은 포함되지 않는다.**

- DOMContentLoaded 154ms, load 212ms(루프백 기준).
- 최초 로드 응답 총 바이트(비압축) 852,332B, 그중 JS 644,308B.
- 개별 청크(비압축/ gzip): `page-*.js` 214,838B / 69,375B(gzip), `index-*.js`(공유 벤더) 194,039B / 55,829B, `framework-*.js`(React 런타임) 190,152B / 59,001B, CSS 167,961B, `switch-*.js` 44,091B / 14,770B. `rail-settings-*.js`(설정 화면)는 6,165B로 별도 지연 로딩 청크로 분리되어 있음을 확인(설정 지연 로딩이 실제로 동작).
- `switch-*.js`로 명명된 공유 청크의 실제 내용을 확인한 결과, Switch 컴포넌트 자체가 아니라 `lib/utils.ts`의 `cn()`이 사용하는 `tailwind-merge`의 전체 Tailwind 클래스 그룹 설정 데이터였다. 이는 shadcn 스타일 컴포넌트 전반에서 쓰이는 구조적 비용이며, "기존 디자인 유지·라이브러리 전면 교체 금지" 조건상 이번 세션에서는 제거하지 않았다. 초기 JS를 더 줄이려면 `tailwind-merge`를 부분적으로만 쓰거나 경량 대안으로 좁혀 적용하는 방안을 별도 과제로 검토할 것을 제안한다(디자인/클래스 충돌 위험이 있어 신중한 검증이 필요).
- 위 수치는 "초기 JS 감소" 자체를 달성했다는 근거가 아니라, v0.3의 현재 상태를 정확히 기록한 것이다.

### 갱신된 미확인 목록

아래 항목은 이번 세션에서도 여전히 확인하지 못했다. 이유를 구체적으로 남긴다.

- **새 Secret으로 TAGO 실제 인증·역 코드·동탄→울산·서울→부산 조회 성공**: 코드 정적 검토·공개 자료 교차 확인으로 개연성은 높였으나, 실제 키로 호출한 성공 사례는 아니다. 채팅으로 키를 요청하지 않았고, 이번 세션에는 배포된 Secret 접근 권한도 없다. 새 키를 호스팅 Secret에 등록한 뒤 `/api/trains/stations?mode=live`와 `/api/trains/search`(동탄→울산(통도사), 서울→부산) 응답을 직접 확인해야 한다.
- **iPad Safari 실기기·실제 터치·텍스트 확대**: 이번 세션은 Chromium + iPad UA/뷰포트 모사로 대체 검증했다. 실제 WebKit 렌더링, 핀치 확대, 스와이프 제스처, iOS 키보드 동작과는 다를 수 있다. 이 환경에서는 실제 iPad 기기에 접근할 수 없어 자동화가 불가능하다. 배포 후 사용자가 iPad Safari에서 직접 확인해야 한다(확인 항목: 역 선택 Combobox 터치 열림·검색·선택, 출발일/시간 입력, 검색·초기화·역 교환 버튼 터치 반응, 좁은 화면에서 가로 스크롤 발생 여부, 설정 텍스트 확대 시 레이아웃 붕괴 여부).
- **실제 외부 지연 상황에서 연속 검색 취소·timeout UX**: 인위적 3초 지연으로 클라이언트 취소·중복 요청 방지 동작은 확인했다(위 참조). 다만 실제 TAGO 응답 지연이나 25초 클라이언트 타임아웃 임계값 자체는 재현하지 않았다(테스트 시간이 과도하게 길어짐).
- **v0.2/v0.3 동일 조건의 첫 렌더링·초기 전송량·실제 API 대기시간 비교**: v0.2 전체 소스가 첨부되지 않아 여전히 불가능하다. v0.3 단독 실측치만 위에 기록했다.
- **새 키 발급/기존 키 폐기 완료 여부**: 사용자의 공공데이터포털 조치 사항이며 코드/저장소에서 확인할 수 없다.

## 실행 검증 2차 세션 — 실제 결함 2건 발견·수정 (2026-09-19, Claude)

이전 절의 "정적 검토, 코드 변경 없음" 수준에서 더 나아가, 로컬 프로덕션 빌드(Cloudflare Worker `pnpm start`)를 실제로 띄우고 Playwright(Chromium)로 사용자 동작을 그대로 재현했다. 그 결과 정적 검토로는 드러나지 않던 실제 결함 2건을 발견해 수정하고, 수정 후 전체 파이프라인과 25개 브라우저 시나리오를 재검증했다.

### 발견·수정한 결함

1. **역 재선택 시 텍스트가 이어붙는 문제 (app/page.tsx)**: 출발역/도착역을 한 번 선택한 뒤 같은 입력창을 클릭해 다른 역으로 바꾸려 하면, 클릭 시 커서가 기존 텍스트 끝에 위치해 새로 입력한 글자가 기존 값 뒤에 이어붙었다(예: "동탄" 선택 후 "부산"을 입력하면 "동탄부산"이 되어 일치하는 역이 없음). 방향키+Enter로 확정해도 일치 항목이 없어 값이 반영되지 않고, 이후 다른 입력란으로 포커스가 옮겨가면 원래 값("동탄")으로 조용히 되돌아가 사용자는 변경이 실패한 이유를 알 수 없었다. `main :is(section, article, input, button, select) { max-width:100% }` 같은 레이아웃 문제가 아니라 클릭 시 커서 위치 문제였다. `ComboboxInput`에 `onClick` 핸들러를 추가해 클릭 시 입력값 전체를 선택(select)하도록 수정했다(브라우저가 mouseup 시점에 클릭 위치로 커서를 재배치하는 것보다 이후에 실행되는 `onClick`에서 처리해야 확실히 적용됨을 확인했다. `onFocus`만으로는 이미 포커스가 있는 입력창을 다시 클릭할 때 focus 이벤트 자체가 재발생하지 않아 효과가 없었다). 키보드 Tab 이동 등 클릭이 아닌 방식의 포커스 진입을 위해 `onFocus` 핸들러도 함께 유지했다.
2. **320px·375px 폭에서 토스트 알림이 화면 밖으로 16px 넘침 (app/globals.css)**: 검색/오류 토스트(`sonner` 라이브러리, `position="top-center"`)가 600px 미만 화면에서 `left:16px; right:16px; width:100%`를 동시에 지정받는데, CSS 사양(CSS2.1 10.3.7)상 `left`와 `width`가 함께 지정되면 `right`는 무시되므로 실제 폭이 `100vw`가 되어 왼쪽 16px 오프셋만큼 오른쪽으로 넘쳤다. `sonner` 2.0.8 자체의 스타일시트 문제이며 RailFlow 코드의 버그는 아니다. 라이브러리를 교체하거나 수정하지 않고, `app/globals.css`에 600px 미만에서만 적용되는 `[data-sonner-toaster] { width: calc(100% - 32px) !important; }` 재정의 1줄을 추가해 해결했다(디자인·색상 변경 없음, 문서 가로 스크롤 자체는 이전에도 발생하지 않았고 — `position:fixed` 요소는 브라우저의 document 스크롤 폭 계산에 들어가지 않음 — 화면에 보이는 토스트 카드 자체가 뷰포트 밖으로 살짝 잘려 보이는 시각적 문제였다).

두 결함 모두 `docs/V0.3-validation.md`의 기존 "검증 결과"(Chrome iframe 폭 검사, 마우스/키보드 선택 확인)만으로는 발견되지 않았다. 기존 검사는 각각 "빈 입력창에 처음 선택하는 경우"와 "정적 레이아웃 스냅샷"만 다뤘고, "이미 선택된 값을 다른 값으로 바꾸는 경우"와 "토스트가 실제로 떠 있는 상태의 요소별 뷰포트 침범 여부"는 다루지 않았다.

로컬 프로덕션 빌드(`pnpm build` → `pnpm start`, Cloudflare Worker 로컬 프리뷰, `http://127.0.0.1:8787`)를 대상으로 Playwright(Chromium)를 재실행했다. 25개 시나리오 전부 통과했다.

- **첫 화면**: 출발역/도착역 placeholder("출발역 선택"/"도착역 선택") 정확히 표시. 초기 로드 시 `/api/trains/search` 요청 0건(역 목록만 조회). 검색 버튼은 역 미선택 상태에서 비활성.

- **오류 처리**: `/api/trains/search`를 인증 실패(503, TAGO_AUTH) 응답으로 가로채 브라우저 화면에 실제 오류 문구와 "다시 시도" 버튼이 뜨는지 확인. 인증키 미설정 상태에서 실제 모드(demo 전환 안 함) 진입 시 "실제 조회 연결을 준비 중입니다" 안내만 뜨고 데모 열차 번호(KTX 331 등)가 절대 섞여 나오지 않음을 확인(실패 시 데모로 자동 대체되지 않음).

### 성능 측정 (실제 서버, 캐시 MISS/HIT 비교)

로컬 프로덕션 서버에 동일 조건(서울→부산, demo 모드)으로 `curl` 직접 호출을 반복했다. 응답의 `server-timing` 헤더로 캐시 상태를 직접 확인했다(추정이 아님).

| 호출 순서 | server-timing | 응답시간(time_total) |
|---|---|---|
| 1회차 | cache;desc=MISS | 5.3ms |
| 2회차(동일 조건) | cache;desc=HIT | 3.8ms |
| 3회차(동일 조건) | cache;desc=HIT | 3.7ms |

데모(mock) provider는 인위적 지연이 없어 MISS/HIT 간 절대 시간 차이가 크지 않다. 캐시가 실제로 요청을 재계산 없이 반환하는지(HIT/MISS 구분)를 확인하는 것이 이 측정의 목적이며, **실제 TAGO 외부 호출 지연 상황에서의 캐시 이득은 여전히 측정하지 못했다**(오프라인 모의 테스트 `scripts/verify-rail.cjs`는 30ms 인위 지연 기준으로 최초 36ms/캐시 1ms를 별도로 보고한다 — 이 역시 모의 값이다).

동일 서버에 60초 이내 14회 연속 요청을 보내 호출 제한(분당 12회)이 실제로 작동함을 확인했다(누적 호출 수가 12회를 넘는 시점부터 429 응답 시작. 정확한 임계 회차는 같은 60초 창 내 이전 테스트 호출과 합산되므로 매회 달라질 수 있으나, 429가 실제로 발생하는 것 자체를 확인했다).

## 공개 주소 404 장애 진단 — 코드 결함 아님, 배포 공백 확인 (2026-09-19, 3차)

사용자가 공개 주소(`https://railflow.dhmailing0310.chatgpt.site`)에서 직접 확인한 결과: `/api/trains/status`는 정상 응답하지만 `/api/trains/stations?mode=live`는 **404**를 반환했다. 이 세션의 네트워크 정책상 해당 도메인에 직접 접근할 수 없어(egress 정책 차단, 아래 참고) 사용자의 관찰을 이 세션에서 재현하지는 못했지만, 로컬 소스를 기준으로 원인을 추적했다.

### 확인 절차와 결과

1. **소스에 세 라우트 모두 존재**: `app/api/trains/status/route.ts`, `app/api/trains/stations/route.ts`, `app/api/trains/search/route.ts` 전부 저장소에 있다.
2. **로컬 개발 서버(`pnpm dev`) 직접 호출**:
   - `GET /api/trains/status` → `200 {"mode":"live","configured":false,"sourceLabel":"실제 조회 연결 준비 중","seatAvailability":false}`
   - `GET /api/trains/stations?mode=live`(키 미설정) → **503** `{"error":{"code":"NOT_CONFIGURED","message":"실제 조회 연결을 준비 중입니다..."}}` — **404가 아니다.**
   - `GET /api/trains/stations?mode=demo` → `200`, 공식 데모 6개 역 목록 반환.
   - `GET /api/trains/search?...&mode=demo`(위 데모 목록의 `departureId`/`arrivalId` 그대로 사용) → `200`, 열차 목록 정상 반환.
   - `GET /api/trains/search?...&mode=live`(키 미설정) → **503**(`NOT_CONFIGURED`), 마찬가지로 404 아님.
3. **프로덕션 빌드로 동일 검증 반복**: `pnpm build` 결과 라우트 표에 `/api/trains/search`, `/api/trains/stations`, `/api/trains/status` 세 개 모두 포함. `pnpm build && pnpm start`(Cloudflare Worker 로컬 프리뷰)로 위 4개 호출을 모두 재확인 — 동일하게 200/503만 나오고 404는 한 번도 발생하지 않았다.
4. **프런트엔드 요청 경로 확인**: `app/page.tsx`는 `/api/trains/stations?mode=...`, `/api/trains/search?...` 형태의 **상대 경로**만 사용한다(`grep` 결과 절대 URL·다른 호스트 하드코딩 없음). 데모 목록에서 받은 `departureId`/`arrivalId`(공식 코드)가 그대로 검색 요청 파라미터로 전달됨을 네트워크 요청에서 직접 확인했다(이번 세션 앞부분의 Playwright 검증과 동일).
5. **재검증**: 위 확인 후 `tsc --noEmit`, `eslint`, `scripts/verify-rail.cjs`, `pnpm build` 전부 재실행해 통과를 재확인했다. **소스 코드는 수정하지 않았다** — 결함이 없었기 때문이다.

### 결론

`/api/trains/stations`가 로컬·프로덕션 빌드 어디서도 404를 내지 않고, 키 미설정 상태에서도 항상 503(명확한 안내 메시지 포함)으로 응답하는 것으로 보아, **공개 주소의 404는 이 저장소의 v0.3 소스 결함이 아니라 배포 공백 때문이다.** 즉 공개 주소는 여전히 v0.2를 실행 중이며, v0.2에는 애초에 `/api/trains/stations` 라우트 자체가 없었을 가능성이 높다(v0.2는 `RailProvider`를 검색 흐름에 직접 연결했을 뿐 별도 역 목록 API를 신설한 것은 v0.3의 변경사항이다 — CHANGELOG.md 참고). 라우트가 아예 존재하지 않는 서버는 "설정 안 됨"이 아니라 "그런 경로 없음"으로 응답하므로 404가 나오는 것이 논리적으로 일관된다.

**GitHub에 v0.3 소스가 있는 것과 ChatGPT Sites 공개 주소에 v0.3이 배포된 것은 서로 다른 사실이다.** 이 PR을 병합해도 공개 주소는 자동으로 갱신되지 않는다(§12 참고, Sites는 별도 관리 Git). 이 세션은 Sites 배포 도구/권한이 없어 실제 배포는 여전히 Codex(또는 Sites 배포 담당자)의 몫이다.
