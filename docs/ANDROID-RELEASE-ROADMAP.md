# RailFlow Android 실제 출시 로드맵 (v0.7 기준)

이 문서는 `docs/ANDROID-ROADMAP.md`(v0.4, 기술 스택·전체 그림)와 `docs/ANDROID-MVP-PLAN.md`(v0.5, PWA 준비 상태 점검)를 대체하지 않는다. 이 둘을 이미 읽었다는 전제로, v0.7 "자동 좌석조회·예약 매크로 시뮬레이터"가 새로 던진 질문에 답한다: **실제로 동작하는 자동 예약 매크로를 Android 사용자에게 내놓으려면, 지금부터 무엇이 더 필요한가.**

## 1. 지금 있는 것과 없는 것 (v0.7 기준 재확인)

| 구분 | 상태 |
| --- | --- |
| 조건 등록 → 자동 감시 → 좌석발견 → 자동클릭 → 자동예약 흐름 | RailFlow 자신의 Mock 예매 사이트 대상으로만 동작(구현됨) |
| 실제 코레일/SRT 좌석 조회·클릭·예약 | 없음(Stub만 존재, §3) |
| 실제 결제 | 없음(사용자가 코레일+ 등 공식 채널에서 직접 결제, 이 앱은 "결제 완료" 확인만 기록) |
| Android 네이티브 앱 | 없음(PWA만 존재, ANDROID-MVP-PLAN.md 참고) |
| 서버 영속 저장소(계정/작업) | 없음(인메모리, 재시작 시 소실) |

## 2. 자동화가 "시뮬레이터"에서 "실제"가 되기 위한 승인 조건

v0.7의 `mock-browser` Provider가 실제 코레일/SRT를 대상으로 하는 `official` Provider로 바뀌는 순간, 이 프로젝트가 지금까지 지켜온 원칙(비공개 API 금지, CAPTCHA/속도제한 우회 금지, 계정정보 미저장)을 실제 위험이 있는 상황에서 지켜야 한다. 따라서 이 전환은 아래 조건이 **모두** 충족된 뒤에만 진행한다.

1. **공식 연동 경로 확인**: 코레일/SR이 공개한 공식 API 또는 명시적으로 허용한 제휴/파트너 연동 방식이 존재해야 한다. 비공개 API를 역공학해 흉내 내는 것은 이 조건을 충족하지 않는다(금지 원칙 §7과 동일).
2. **이용약관/로봇배제표준 검토**: 공식 API가 있어도 그 이용약관이 이런 형태의 자동 예약 매크로를 허용하는지 법무 검토가 선행되어야 한다.
3. **계정 연동 보안 모델 확정**: 사용자의 코레일 계정 자격증명을 어떻게 다룰지(예: OAuth형 위임 인증이 있다면 그것만 사용, 없다면 이 기능 자체를 보류) 결정해야 한다. 아이디/비밀번호를 직접 입력받아 저장하는 방식은 채택하지 않는다(현재 원칙 유지).
4. **결제 책임 분리 유지**: `official` Provider가 실제로 붙어도 이 앱이 카드 정보를 저장하거나 자동 결제를 수행하지 않는다는 원칙(v0.4부터 유지)은 그대로 유지한다 — 승인 조건이 아니라 절대 불변 원칙이다.
5. **레이트리밋/오류 대응 정책 문서화**: 공식 API의 호출 한도, 오류 코드, 차단 정책을 문서화하고 `AutomationErrorCode`에 반영해야 한다.
6. **Playwright 기반 브라우저 자동화 여부 재검토**: 공식 API가 있다면 브라우저 자동화(Playwright) 자체가 불필요해질 가능성이 높다 — REST/GraphQL 호출로 대체하는 것이 탐지회피 논란과 사이트 구조 변경 취약성을 모두 없앤다. 공식 API가 없고 여전히 화면 자동화가 필요한 상황이라면, 그 자체가 위 1번 조건을 충족하지 못했다는 신호다.

이 조건 중 하나라도 충족되지 않으면, RailFlow는 `official` Provider를 계속 Stub(`OFFICIAL_INTEGRATION_REQUIRED`)으로 유지한다.

## 3. Playwright 자동화의 실행 환경 제약 (Android 출시 계획에 미치는 영향)

`docs/V0.7-AUTOMATION-BOUNDARY.md` §5에서 확인했듯, 이 저장소의 Cloudflare Workers 배포 경로(`pnpm build`)는 실제 브라우저 프로세스를 띄울 수 없는 런타임이다. 이것이 Android 출시 계획에 의미하는 것:

- Android 앱(또는 그 서버 백엔드)이 실제 자동 예약 매크로를 서버에서 상시 실행하려면, 그 서버는 **Playwright(또는 동급 브라우저 자동화)가 실제로 구동 가능한 런타임**(일반 Node.js 서버, 컨테이너, 또는 서버리스라면 Node.js 런타임이면서 별도 브라우저 바이너리/컨테이너를 붙일 수 있는 구성)이어야 한다. 순수 Edge/Workers 런타임으로는 이 기능을 서버에서 상시 구동할 수 없다.
- 앞서 §2의 조건이 충족되어 공식 API 연동으로 전환된다면 이 제약은 사라진다(REST 호출은 어떤 런타임에서도 가능하다) — 즉 "브라우저 자동화 의존"과 "실행 인프라 선택"이 서로 묶여 있다는 점을 배포 인프라를 정할 때 함께 고려해야 한다.
- 지금 확인하지 못한 것(확인 필요): 이 PR이 생성하는 Vercel Preview가 자동화 API 라우트(`/api/automation-jobs/**`)를 Node.js 런타임과 Edge 런타임 중 어느 쪽으로 실행하는지. Next.js는 라우트별로 `runtime` 설정을 명시하지 않으면 기본값을 따르므로, 이 PR은 그 기본값을 직접 확인하지 않았다.

## 4. 실제 Android 출시 전 남은 작업 (v0.4/v0.5/v0.6/v0.7 항목 통합, 우선순위 순)

1. 영속 저장소(PostgreSQL, ADR 0001/0002 기존 설계) 실제 연결 — 계정·감시작업·자동화작업이 서버 재시작에도 유지되어야 앱을 신뢰할 수 있다.
2. 실제 알림 Adapter(FCM 최소 1개) 연결 — 지금은 InMemory Adapter뿐이다.
3. §2의 승인 조건 중 최소 "공식 연동 경로 확인"이 완료되기 전까지는, Android 네이티브 앱이 나오더라도 자동예약 탭은 "RailFlow 자체 Mock 시뮬레이터에서만 동작" 상태를 유지한다 — 승인되지 않은 상태에서 네이티브 앱만 먼저 낸다고 해서 이 제약이 없어지지 않는다.
4. Android 프로젝트 자체 착수(Kotlin + Jetpack Compose, ANDROID-ROADMAP.md §2~§3 그대로) — 서버 인증·영속화가 선행된 뒤.
5. Play Console 등록, 개인정보처리방침·계정삭제 심사 대응(ANDROID-MVP-PLAN.md §7~§8), 비공개 테스트 12명·14일 요건 충족.
6. §2 조건이 모두 충족된 뒤에만 `official` Provider 실 구현 착수 — 이 시점부터 실제 자동 예약이 카드 결제·계정 보안·레이트리밋 측면에서 실사용자에게 안전한지 별도 보안 검토를 거친다.

## 5. 확인 필요로 남기는 항목

- Vercel Preview에서 `/api/automation-jobs/**`가 실행되는 런타임(Node.js vs Edge).
- `pnpm exec next build`(→ `vercel-build`) 산출물이 실제 Vercel 배포에서 어느 런타임으로 서비스되는지.
- Cloudflare Workers 배포(`pnpm build`) 경로가 실제로 이 프로젝트의 공개 서비스 대상인지, 혹은 별도 용도(로컬 프리뷰/다른 배포 채널)인지 — 이번 PR 범위에서 확정하지 않았다.
