# 실제 잔여좌석 조회·예약 연동 가능성 조사

최초 2026-09-22 · **개정 3판 2026-09-23** · 대상: RailFlow 실제 좌석 조회·예약

## 0. 결론

**승인받은 TAGO 열차정보 서비스의 명세(상세기능·출력 항목) 원문 확보 필요.**

문제는 인증키나 활용신청이 아니다. 그건 이미 끝났다(§1). 남은 것은 **이미 승인받아 쓰고 있는
서비스가 좌석 정보를 제공하는지**를 명세로 확인하는 일이다. 이 한 가지가 확인되면 후보 A의
적합성 판단이 끝난다.

실제 좌석 조회는 구현하지 않았고 코드도 추가하지 않았다. fail-closed 기본값도 그대로다.

## 1. 이미 확보된 것 (되돌아가지 않을 사실)

| 항목 | 내용 | 확인 수준 |
|---|---|---|
| 서비스 | 국토교통부_(TAGO)_열차정보 | **사용자 제공 증거** |
| 처리상태 | 승인 | **사용자 제공 증거** |
| 활용기간 | 2026-09-19 ~ 2028-09-19 | **사용자 제공 증거** |
| Endpoint | `https://apis.data.go.kr/1613000/TrainInfo` | **사용자 제공 증거** + 저장소 코드와 일치(**확인됨**) |
| 일반 인증키 | 발급 완료, 운영 환경에 등록됨 | **사용자 제공 증거** |
| 운영 조회 성공 | 운영 RailFlow에서 실제 역 목록·시간표·운임이 반환되는 화면을 사용자가 공유 | **사용자 제공 증거** |

→ **활용신청·키 발급을 다시 요청하지 않는다.** 인증키 원문은 이 문서·로그·커밋 어디에도 싣지 않는다.

**운영 환경의 키와 조사 환경의 키는 별개다.** 이 조사 세션의 환경변수로는 키에 접근할 수 없지만,
그것은 조사 환경의 제약이지 프로젝트가 키를 갖고 있지 않다는 뜻이 아니다.

## 2. 2판에서 정정한 내용

| 2판 서술 | 정정 |
|---|---|
| "`DATA_GO_KR_SERVICE_KEY`가 설정되어 있지 않다" | → **현재 조사 환경에서 키 설정을 확인하지 못함.** 사용자는 TAGO 승인·키 발급 및 이전 운영 조회 성공 증거를 제공했다 |
| "이 프로젝트는 TAGO 실호출을 한 번도 라이브로 검증한 적이 없다" | → `verify-rail.cjs`는 **오프라인 모의 테스트라 라이브 호출의 증거가 아니다**. 별도로 사용자가 운영 응답 화면을 제공했으며, **이번 조사 세션에서의 직접 라이브 검증만 미실시**다 |
| 자료 1(TAGO 항목 확인)로 "후보 A 판정이 끝난다" | → **해당 TAGO 서비스의 적합성만** 판단할 수 있다. 다른 공개 API의 존재 여부까지 결론 내릴 수 없다 |
| "좌석 항목이 있으면 곧바로 실증 착수 가능" | → 좌석 항목의 **의미·갱신 주기·호출 권한·이용 조건**을 확인한 뒤 단건 조회 실증 여부를 판단한다 |
| 폐기·대체 공지가 현재 엔드포인트에 걸릴 수 있다는 취지의 서술 | → **해소됨. 현재 엔드포인트는 폐기 대상이 아니라 그 대체본이다**(§3) |

(1판 정정 내역은 2판 §1에 있었고, 그 내용은 아래 §7 표에 통합했다.)

## 3. 폐기·대체 공지 건 — 해소

2판은 검색에서 발견한 "TAGO OPEN API 호출중지·대체서비스" 공지를 **현재 엔드포인트의 위험 요소**로
남겨 뒀다. 저장소 이력으로 확인한 결과 이는 사실과 다르다.

커밋 `224b9d0`(2026-09-19, "Point TAGO provider at the current (2026-03) replacement endpoint")의 기록:

- 문제의 공지는 `NOTICE_0000000002723`, **2022-08-25 게시**, 구 서비스 호출중지일 **2022-09-01**.
- 그 공지의 대상은 **구 "국토교통부_열차정보"**(경로 `.../1613000/TrainInfoService`, 오퍼레이션
  소문자 시작)였다.
- 대체본이 **현 "국토교통부_(TAGO)_열차정보"**(데이터 ID 15098552, 최종수정 2026-03-06)이며,
  경로는 `.../1613000/TrainInfo`, 오퍼레이션은 대문자 시작이다.
- RailFlow는 2026-09-19에 구 경로에서 **현 경로로 이미 이전을 마쳤다**. 당시 사용자가
  data.go.kr의 공지와 서비스 페이지를 직접 대조해 확인했다.

→ **구 `TrainInfoService`와 현 `TrainInfo`를 구분한다. 현재 사용 중인 엔드포인트가 폐기됐다고
추정하지 않는다.** (확인 수준: 저장소 커밋 기록 **확인됨** + 당시 사용자 대조 **사용자 제공 증거**)

## 4. 이번 작업의 핵심 질문 — 현재 상태

승인받은 TrainInfo 서비스가 무엇을 제공하는지. 항목을 섞지 않고 따로 판단한다.

| 질문 | 현재 상태 |
|---|---|
| 운행시간표·운임 | **제공함** — 운영 화면에서 시간표·운임이 반환됨(사용자 제공 증거). 우리 구현도 `depplandtime`/`arrplandtime`/`traingradename`/`adultcharge`/`trainno`를 읽음(확인됨) |
| 좌석 총수 또는 차량 정원 | **미확인** |
| 현재 판매 가능한 잔여좌석 수 | **미확인** |
| 일반실·특실 예약 가능/매진 상태 | **미확인** |
| 예약 생성 | **미확인** |
| 예약내역 조회·취소 | **미확인** |

주의할 구분:

- **총 좌석 수 ≠ 현재 예약 가능한 잔여좌석 수.** 전자가 있어도 후자를 대체하지 못한다.
- **좌석 조회 지원 ≠ 예약 생성 지원.** 둘은 따로 확인한다.
- **우리 코드가 5개 필드만 읽는다 ≠ API가 5개 필드만 반환한다.** 우리 구현의 동작일 뿐,
  응답 항목 전체 목록은 **미확인**이다. 화면에 좌석이 안 보이는 것도 우리가 `availability:
  "unknown"`을 고정으로 넣기 때문이며, API에 좌석 항목이 없다는 증거가 아니다.

## 9. 실제 예약 단계 설계에 필요한 확인 항목

연동 방식이 정해지기 전이라 **전부 미확인**이다. 명세 확보 시 이 순서로 확인한다.

| 항목 | 확인할 내용 |
|---|---|
| 예약 생성 vs 최종 구매·결제 | 좌석을 잡아두는 단계와 결제로 확정하는 단계의 분리 여부, 각각의 API와 상태값 |
| 예약 성공 식별자 | 성공 응답의 식별자와 유효 범위 |
| 응답 유실 시 확인 | 요청은 갔으나 응답을 못 받았을 때 예약내역을 재조회할 수단. 없으면 중복예약 방지 설계가 성립하지 않음 |
| 재시도·중복 방지 | 멱등키 지원 여부. 없으면 "재조회 후 판단"이 유일한 안전책 |
| 결제기한의 출처 | 실제 정책값과 응답 포함 여부. **현재 시뮬레이터의 10분은 RailFlow 자체 Mock 값이며 실제 정책값이 아니다** |
| 성공 후 다른 후보 중단 | 클라이언트 책임. 시뮬레이터에 이미 구현됨 |
| 사용자 중지 시 처리 중 요청 | 취소 수단과 시한. 없으면 "이미 나간 요청은 되돌릴 수 없음"을 UI에 명시 |

**실행 주체**: 현재 RailFlow의 자동화는 **브라우저가 열려 있는 동안 반복 호출하는 방식**이며,
공개 시연과 서버 기반 작업 양쪽 모두 그렇다. 이를 "상시 서버 감시"로 표현하지 않는다.
화면을 닫아도 이어지는 감시가 필요하면 별도의 상시 실행 주체가 필요하지만, **그것이 반드시
유료 인프라여야 한다고 단정하지 않는다** — 사용자 소유 상시 구동 기기, Android 백그라운드 실행,
기존 보유 서버 등 선택지가 있고, 연동 방식과 허용 호출 빈도가 정해진 뒤 판단한다.

## 10. 확인 수준 분류 기준

- **확인됨** — 이 세션에서 저장소 코드·이력을 직접 열람해 확인.
- **사용자 제공 증거** — 사용자가 화면·기록으로 제공. 이 세션에서 재현하지 않았다.

- **미확인** — 확인하지 못함. *존재하지 않음을 뜻하지 않는다.*
