# 실제 잔여좌석 조회·예약 연동 가능성 조사

작성일: 2026-09-22 · 대상: RailFlow 2단계(실제 좌석 조회·예약)

## 0. 결론

**사용 가능한 연동 수단을 확인하지 못했다.** 실제 잔여좌석 조회를 구현하지 않았고, 코드 변경도 하지 않았다.

"확인하지 못했다"는 "존재하지 않는다"와 다르다. 이번 조사에서는 **공식 명세 원문을 단 한 건도 직접 열람하지 못했다** — 이 세션의 네트워크 정책이 한국 철도·공공데이터·언론 도메인 전체를 차단하고 있기 때문이다(§1). 따라서 아래 내용 중 외부 사실은 전부 검색 결과 요약 수준의 **잠정 정보**이며, 이를 근거로 "가능"이나 "불가능"을 단정하지 않는다.

확인된 범위에서의 판단:

- 실시간 잔여좌석을 제공하는 **공개 개발자 API는 찾지 못했다**(잠정). 현재 RailFlow가 쓰는 TAGO 열차정보는 시간표·운임만 제공한다(이건 직접확인).
- 코레일 소비자 웹·앱 자동화는 **운영자가 명시적으로 차단하는 대상**이다(잠정, 복수 보도 일치). 우회는 프로젝트 지침과 이번 작업 지침 양쪽에서 금지되므로 이 경로는 선택지에서 제외한다.
- **제휴·판매대행 채널은 존재 정황이 있으나**(코레일이 외부 플랫폼에 승차권을 유통), 개인 개발자가 신청할 수 있는지·명세가 무엇인지는 공개 자료로 확인되지 않았다. 이것이 유일하게 남아 있는 미확인 경로다.

## 1. 이번 조사의 한계 (먼저 밝힘)

이 세션의 egress 프록시가 아래 도메인에 대해 CONNECT 403을 반환한다. 재시도하거나 우회하지 않았다.

| 도메인 | 결과 | 원래 확인하려던 것 |
|---|---|---|
| `www.data.go.kr` | 403 차단 | TAGO·코레일 데이터셋 명세(응답 항목 전체) |
| `apis.data.go.kr` | 403 차단 | 실제 API 호출(키가 있어도 불가) |
| `info.korail.com` | 403 차단 | 코레일 공공데이터 개방 목록, 매크로 차단 공지 원문 |
| `openapis.korail.com` | 403 차단 | 코레일 오픈API 제공 서비스 목록·신청 절차 |
| `data.kric.go.kr` | 403 차단 | 레일포털 오픈API 신청 절차 |
| `www.letskorail.com`, `etk.srail.kr` | 403 차단 | 이용약관, 예매 화면 구조 |
| 주요 언론사·`korea.kr`·`en.wikipedia.org` | 403 차단 | 통합/매크로 차단 보도 원문 |

**결과적으로 이번 조사에서 직접 열람(원문 확인)한 자료는 이 저장소의 코드뿐이다.** 외부 사실은 모두 검색 엔진이 돌려준 제목·요약 수준이다.

추가로: `DATA_GO_KR_SERVICE_KEY`가 이 세션에 설정되어 있지 않다. 키가 있더라도 `apis.data.go.kr`가 차단되어 실제 호출은 불가능했다.

## 3. 방식별 근거

### 3.1 공개 개발자 API

**[직접확인]** 현재 RailFlow의 시간표 Provider(`lib/rail/tago-provider.ts`)는
`https://apis.data.go.kr/1613000/TrainInfo`의 `GetStrtpntAlocFndTrainInfo`,
`GetCtyAcctoTrainSttnList` 오퍼레이션을 호출하고, 응답에서 다음 5개 필드만 읽는다:
`depplandtime`, `arrplandtime`, `traingradename`, `adultcharge`, `trainno`.
좌석 관련 필드는 읽지 않으며, 모든 결과에 `availability: "unknown"`을 넣는다
(`scripts/verify-rail.cjs`의 픽스처도 같은 5개 필드만 사용).
즉 **이 프로젝트가 실제로 쓰고 검증해 온 범위에서 TAGO 열차정보는 시간표·운임만 제공한다.**

한계: 우리 코드가 5개 필드만 쓴다는 것이 "API가 5개 필드만 반환한다"는 증명은 아니다.
공식 응답 항목 전체 목록은 `www.data.go.kr` 차단으로 확인하지 못했다.

**[잠정 — 검색 요약]** 검색 결과에서 실시간 잔여좌석을 제공하는 공공데이터 데이터셋은 나타나지 않았다.
조회된 철도 관련 데이터셋은 시간표·운행계획·운임표·승하차 통계 계열이었다.
한 검색 요약은 TAGO가 "잔여석"을 제공한다고 서술했으나, 같은 검색의 다른 결과 및 위 직접확인과
배치되므로 **신뢰하지 않는다**(원문 미열람).

**[잠정]** 코레일 자체 오픈API 포털(`openapis.korail.com`)에서 확인된 서비스 이름은
"승차권 진위확인 조회", "여객열차 운행계획", "간선열차 역별 승하차 통계" 계열이다.
**좌석 조회·예약 서비스는 나타나지 않았다.**

### 3.2 제휴·판매대행

**[잠정]** 코레일이 2018년부터 트립닷컴을 시작으로 위챗·알리페이 등 외부 플랫폼으로
승차권 판매 채널을 확대했다는 서술이 검색 결과에 있다. 이는 **제휴 유통 채널이 제도적으로
존재한다**는 정황이다.

그러나 다음은 전부 **미확인**이다: 신청 창구, 자격 요건(법인/개인), 계약 절차, 제공되는 API 명세,
좌석 조회 포함 여부, 호출 제한, 테스트 환경 제공 여부.
공개 문서를 찾지 못했고, 코레일 도메인이 차단되어 확인할 수 없었다.

→ **이 경로가 2단계를 진행할 수 있는 유일한 미확인 후보다.** §7의 문의문으로 확인해야 한다.

### 3.3 운영자가 허용한 웹·앱 자동화 → 제외

**[잠정 — 복수 보도 일치]** 코레일이 매크로 탐지 솔루션을 도입(보도 기준 "지난 7월",
보도 시점 2025-10-01/2025-10-08)해 하루 평균 약 1만 6천 건의 매크로 접근을 차단하고 있으며,
접속 패턴·구매 행태를 실시간 분석해 **로그인과 승차권 조회 단계부터 사전 차단**한다는 보도가
복수 매체에서 일치한다(뉴시스 2025-10-01, ZDNet 2025-10-08, 팍스경제TV 등. 원문 미열람).

즉 소비자 웹·앱에 대한 자동 조회·예매는 **운영자가 명시적으로 차단 대상으로 규정한 행위**다.
여기서 동작하게 만들려면 탐지 회피가 필요한데, 이는

- `CLAUDE.md`: "비공개 API를 추측하거나 CAPTCHA, 봇 차단, 속도 제한을 우회하지 않는다"
- 이번 작업 지침: "탐지 회피, CAPTCHA·대기열·속도제한 우회, 차단 회피용 IP·계정 전환은 구현하거나 해결책으로 제안하지 않는다"

양쪽에 정면으로 어긋난다. → **이 경로는 선택지에서 제외한다.**

**참고(채택 아님)** GitHub에 `letskorail` 파이썬 래퍼, `js-korail-macro` 등 비공식 자동화
프로젝트가 존재한다. 이들은 비공개 모바일 API를 직접 호출하는 방식이며,
(a) 프로젝트 지침이 금지하는 "비공개 API 추측"에 해당하고,
(b) 존재한다는 사실이 사용 허용의 근거가 아니며,
(c) 아래 §4의 시스템 변경 이후에도 동작한다는 보장이 없다.
기술 참고자료로만 언급하고 채택하지 않는다.

### 3.4 사용자 직접 조작

현재 RailFlow가 이미 취하는 방식(공식 예매처 안내). 실제 좌석 확보는 사용자가 공식 창구에서 수행한다.
이 경로는 유지하되, "자동 예약"을 대체하지는 못한다.

## 4. 조사 중 발견한 시스템 변경 (잠정, 그러나 중요)

**[잠정 — 복수 보도 일치]** 검색 결과에서 다음이 반복적으로 나타났다.

- 코레일·SR의 고속철도 **운영 통합이 2026-09-01자**로 시행.
- KTX·SRT 통합 예매 앱 **"코레일+"가 2026-08-03 출시**(기존 코레일톡 기반 개편).
- 통합 이후 운임 인하·좌석 공급 증가 등 변화 서술.

원문을 열람하지 못해 확정하지 않는다. 다만 사실이라면 2단계에 직접적인 영향이 있다:

1. 사용자가 지정한 **동탄 → 울산(통도사)** 구간은 종래 SRT 계열 구간이므로, 통합 이후
   열차 종별·예매 창구·식별 체계가 달라졌을 수 있다.
2. 통합 전에 작성된 모든 비공식 래퍼·문서는 **최신 상태가 아닐 가능성이 높다.**
3. 연동 문의 시점으로는 오히려 적절하다 — 통합 직후 체계가 정리되는 시기다.

→ **이 항목은 문의로 가장 먼저 확인해야 한다.** 과거 문서의 앱 명칭·통합 여부·결제기한 값을
그대로 전제하지 않는다(예: 기존 시뮬레이터의 "결제기한 10분"은 RailFlow 자체 Mock 값이며
실제 정책값이 아니다).

## 5. 지금 실행 가능한 범위

| 항목 | 가능 여부 |
|---|---|
| 실제 잔여좌석 조회 구현 | **불가** — 확인된 명세·권한 없음 |
| 확인된 명세 기반 Provider 코드 작성 | **불가** — 좌석 API 명세를 확보하지 못함. 추측 endpoint·응답 구조를 만들어 넣지 않는다 |
| 실제 예약 생성 | **불가**(이번 범위에서도 애초에 제외) |
| TAGO 시간표 실조회 검증 | **이 세션에서는 불가** — 키 미설정 + `apis.data.go.kr` 차단. 사용자 환경에서는 키 등록 후 가능 |
| 좌석 Provider 인터페이스 분리 | 이미 되어 있음 — `SEAT_AVAILABILITY_PROVIDER=disabled`가 기본값이며 모든 감시 작업이 `PROVIDER_UNAVAILABLE`로 정직하게 표시됨 |

기존 fail-closed 기본값은 그대로 두었다. 이번 작업에서 `CLAUDE.md`, 기능 차단 플래그,
운영 환경변수를 변경하지 않았고 새 유료 인프라도 만들지 않았다.

## 7. 실제 예약 단계를 위해 확인해야 할 설계 항목

연동 수단이 확보되기 전이라도, 예약 구현 시 반드시 답이 있어야 하는 항목을 정리한다.
현재는 **전부 미확인**이며, 문의·명세 확보 시 이 순서로 확인한다.

| 항목 | 확인해야 할 내용 |
|---|---|
| 조건 ↔ 예약 요청 대응 | 사용자가 지정한 날짜·구간·시간대·인원·좌석등급이 예약 요청의 어떤 파라미터로 1:1 대응되는지. 부분 충족(예: 인원 중 일부만 좌석 확보) 시 동작 |
| 예약 성공 식별자 | 성공 응답의 식별자 필드, 그 식별자로 예약내역을 재조회하는 별도 API 존재 여부 |
| 응답 유실 시 중복 방지 | 요청은 도달했으나 응답을 못 받은 경우, 멱등키 지원 여부. 없다면 "예약내역 재조회 후 판단"이 유일한 수단이므로 재조회 API가 필수 |
| 재시도 가능/불가 오류 | 어떤 오류코드가 안전한 재시도 대상이고, 어떤 코드가 즉시 중단 대상인지. **결과가 불명확하면 재예약하지 않고 확인 대기 상태로 둔다**(현재 시뮬레이터가 이미 채택한 원칙) |
| 결제기한·예약 만료 | 실제 결제기한 정책값과 그 값이 응답으로 내려오는지. **Mock의 10분을 실제값으로 쓰지 않는다** |
| 성공 후 다른 후보 중단 | 한 후보 예약 성공 시 나머지 감시를 멈추는 것은 클라이언트 책임. 이미 시뮬레이터에 구현됨 |
| 사용자 중지 시 처리 중 예약 | 중지 시점에 예약 요청이 처리 중이면, 취소 API 유무와 그 시한. 취소 수단이 없다면 "중지해도 이미 나간 요청은 되돌릴 수 없음"을 UI에 명시해야 함 |

또한 **서버 상시 감시는 아직 존재하지 않는다**는 점을 재확인한다. 현재 자동화(공개 시연과
서버 기반 작업 양쪽)는 브라우저가 반복 호출할 때만 진행되며, 앱을 닫으면 멈춘다.
실제 예약 단계에서 "닫아도 감시"가 필요하다면 별도의 상시 실행 주체가 있어야 한다
(반드시 유료 서비스여야 한다는 뜻은 아니다 — 사용자 소유 기기·상시 구동 서버 등 선택지가 있고,
어떤 방식이 적절한지는 연동 수단이 정해진 뒤에 판단한다).

## 8. 문의문 초안 (전송하지 않음)

### 8-1. 코레일 — 승차권 조회·예매 연동 문의

> 제목: 승차권 잔여좌석 조회 및 예매 연동(Open API/제휴) 가능 여부 문의
>
> 안녕하십니까.
> 개인 개발자로서 KTX 승차권 조회·예매를 연동하는 애플리케이션 개발을 검토 중이며,
> 공식적으로 허용되는 연동 방식을 확인하고자 문의드립니다.
>
> 1. 열차별 **잔여좌석 조회**가 가능한 공식 API가 제공되는지, 제공된다면 신청 방법과 자격 요건
> 2. **승차권 예약·발권**이 가능한 연동(제휴·판매대행 포함)이 있는지, 있다면 신청 절차와 대상
>    (개인 개발자 신청 가능 여부 포함)
> 3. 위 API가 제공되는 경우 인증 방식, 호출 제한, 테스트 환경 제공 여부
> 4. 2026년 9월 1일 코레일·SR 고속철도 운영 통합 이후 연동 체계에 변경이 있는지
> 5. 공식 연동이 불가한 경우, 웹·앱 화면을 이용한 자동 조회가 이용약관상 허용되는 범위
>
> ※ 탐지 회피나 차단 우회를 전제한 개발은 계획하고 있지 않으며,
>    공식적으로 허용되는 방식만 사용하려 합니다.

### 8-2. SR(수서고속철도) — 동일 취지

> 제목: SRT 잔여좌석 조회·예매 연동 가능 여부 문의
>
> (8-1과 동일 문항. 추가로) 2026년 9월 1일 운영 통합 이후 SRT 구간 연동 문의는
> 코레일과 SR 중 어디로 접수해야 하는지 안내 부탁드립니다.

### 8-3. 공공데이터포털 — 데이터셋 확인

> 제목: 열차 잔여좌석 정보 제공 데이터셋 존재 여부 문의
>
> 국토교통부(TAGO) 열차정보(데이터셋 15098552) 및 한국철도공사 열차운행정보(15125762)의
> 응답 항목에 **잔여좌석 정보가 포함되는지** 확인 부탁드립니다.
> 포함되지 않는다면, 열차 잔여좌석을 제공하는 다른 공공데이터 API가 있는지 안내 부탁드립니다.
