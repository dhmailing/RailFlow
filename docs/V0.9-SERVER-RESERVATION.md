# v0.9 서버형 자동예약 기반

목표: **서버형 취소표 감시 → 좌석 확보 → 사용자 직접 결제** 구조의 기반을
완성하고, 허용된 실제 Provider가 없으면 정직하게 fail-closed 를 유지하는 것.

> **현재 상태: 기반 완성, 실제 연동 없음.**
> 실제 좌석 조회·예약은 **0건**이다. 공식·승인된 연동 경로를 확인하지
> 못했기 때문이다([조사 결과](./V0.9-KORAIL-INTEGRATION-RESEARCH.md)).

## 2. 사용자 흐름과 현재 도달 지점

```
1. TAGO 시간표에서 후보 열차 선택          ✅ 동작 (v0.3부터)
2. 자동예약 작업 등록                      ❌ 실제 Provider 없음
3. 서버 Worker 감시 상태 표시              ⚙️ 기반 구현, 표시할 실제 작업 없음
4. 좌석 없으면 제한된 주기로 재시도        ⚙️ 기반 구현
5. 좌석 발견                               ❌ 실제 조회 연동 없음
6. 예약 보류(좌석 확보) 성공               ❌ 실제 예약 연동 없음
7. 긴급 알림 (푸시·이메일)                 ⚙️ Outbox 구현, 채널 어댑터는 메모리만
8. "코레일+에서 결제하기"                  ⚙️ 링크 자리 마련(실제 URL 없음)
9. 사용자가 공식 앱에서 직접 결제           — RailFlow가 하지 않는 부분
10. 결제 완료 확인                          ❌ 실제 조회 연동 없음
11. 나머지 후보 자동 중단                   ✅ 구현 + 테스트
```

화면(`components/autobook-panel.tsx`)은 이 표를 그대로 보여준다. 준비된
것에 체크, 안 된 것에 이유를 붙인다. **Mock 결과를 실제처럼 보여주지
않는다.**

## 3. 중복 예약을 막는 장치

이 설계에서 가장 중요한 부분이다. 취소표 경쟁은 본질적으로 경쟁 조건이고,
잘못 만들면 사용자에게 **예약이 두 건** 생긴다.

### 3-1. 원자적 claim + fencing token

```
Worker A ──claim──▶ token 1 ──▶ (멈춤)
Worker B ──claim──▶ token 2 ──▶ 예약 요청 ──▶ 확보
Worker A ──깨어남──▶ 쓰기 시도 ──▶ STALE_CLAIM 거부
```

- `claimNext` 는 원자적이다. 인메모리 구현은 `await` 없는 동기 구간으로,
  Postgres 는 `FOR UPDATE SKIP LOCKED` 로 보장한다.
- 모든 쓰기가 `fencingToken` 을 거친다. 토큰이 뒤처지면 거부된다.
- **되돌릴 수 없는 동작(예약 요청) 직전에 `renewClaim` 으로 다시 확인한다.**

테스트: 동시 Worker 10개 → 예약 요청 **1회**.

### 3-2. 멱등키

예약 요청에 `reservationIdempotencyKey` 가 함께 나간다. 같은 키로 두 번
호출돼도 예약은 하나여야 한다(Provider 계약).

### 3-3. 결과가 불명확할 때

```
createReservation() ──▶ AMBIGUOUS (응답 유실)
                          │
                          ├─ findExistingReservation() 으로 예약내역 재조회
                          │    ├─ 찾음  ──▶ RESERVATION_HELD
                          │    └─ 없음  ──▶ AMBIGUOUS_RESULT (종료, 사람이 확인)
                          │
                          └─ 재예약? ✗ 하지 않는다
```

상태 기계에 `RESERVATION_CLAIMING → SEAT_FOUND` 전이가 **없다.** 재시도로
돌아가는 길이 구조적으로 막혀 있다.

`AMBIGUOUS_RESULT` 는 **종료 상태**다. 자동으로 빠져나올 수 없다.

**예약 요청 도중 예외가 난 경우도 같게 다룬다.** 요청을 보낸 뒤 네트워크
오류나 타임아웃이 나면 그것도 "응답을 모른다"는 뜻이다. Worker 는 claim 시점의
상태가 아니라 **저장소에 실제로 쓰인 최신 상태**를 기준으로 판단하고, 요청을
보낸 뒤라면 감시로 되돌리지 않는다. 예약내역 재조회로 확정하거나
`AMBIGUOUS_RESULT` 로 멈춘다. 되돌리면 다음 주기에 같은 좌석을 다시 예약하려
들기 때문이다(`tests/autobook/worker.test.mjs` 가 이 회귀를 검사한다).

### 3-4. 예약 결과를 확인할 수 없는 Provider 로는 예약하지 않는다

`canVerifyReservation === false` 면 좌석을 찾아도 예약을 시도하지 않고
`PROVIDER_UNAVAILABLE` 로 멈춘다. "눌렀는지 모르겠다"를 만들지 않기 위해서다.

### 3-5. 사용자 취소도 함부로 받지 않는다

예약 요청을 이미 보낸 뒤(`RESERVATION_CLAIMING`)에는 취소가 곧바로
`CANCELLED` 가 되지 않는다. 예약이 생겼는지 확인하는 단계로 간다.

### 3-6. 하나가 확정되면 나머지는 즉시 중단

`stopOtherCandidates()` 가 확정 경로 전부에서 호출된다(정상 확보, 불명확
후 확인 성공).

## 4. 요청 제한과 중단 조건

v0.8의 교훈: **고정 주기를 지켰는데도 자동화로 판정됐다.** 빈도가 유일한
기준이 아니다.

- Provider별 정책(`lib/autobook/rate-limit.ts`). 현재 전부
  `basis: "conservative_default"` — 공식 수치를 확인하지 못했다는 뜻이다.
- 지수 백오프에 **상한이 있다.** 상한을 넘으면 재시도하지 않고 멈춘다.
- Provider가 알려준 `retryAfter` 를 존중하되 최소 간격 아래로는 안 간다.
- 다음 상태는 **즉시 중단**하고 우회하지 않는다:
  `AUTH_REQUIRED`(자동 재로그인 없음), `RATE_LIMITED`,
  `BLOCKED_BY_OPERATOR`(종료 상태), `AMBIGUOUS_RESULT`(종료 상태).
- **조회 실패를 매진으로 처리하지 않는다.** `UNKNOWN` 은 별도 경로다.

## 5. 계정과 비밀정보

**RailFlow는 코레일 계정 비밀번호를 입력받지도, 저장하지도 않는다.**

우선순위(지침 §6)와 현재 상태:

| 순위 | 방식 | 상태 |
|---|---|---|
| 1 | 공식 OAuth·파트너 토큰 | 발급 창구 **미확인** → 비활성 |
| 2 | 제한된 권한의 공식 API credential | 좌석·예약 포함 credential **미확인** → 비활성 |
| 3 | 사용자가 직접 갱신하는 단기 세션 | 공식 허용 근거 **미확인** → 비활성 |
| 4 | 위가 모두 없으면 **실제 Provider 미구현** | **현재 여기다** |

`lib/autobook/account-link.ts` 에는 비밀번호를 받는 함수 자체가 없다.
`METHOD_AVAILABILITY` 의 모든 항목이 `available: false` 이며, 각각 왜 막혔는지
문구를 갖고 있고 그대로 화면에 나간다.

Postgres 스키마의 `autobook_account_links` 에도 비밀번호 컬럼이 없다.
토큰 자체가 아니라 외부 보관소 참조(`secret_ref`)만 둔다.

**로그·알림·감사 이벤트에 credential·쿠키·토큰·세션 식별자가 들어가지
않는다.** 알림 payload 는 열차·구간·날짜·기한만 담으며, 예약번호 원문도
넣지 않는다(테스트로 고정).

## 6. 왜 작업 생성 API가 없는가

`app/api/autobook/status` 는 읽기 전용이고, 작업을 만드는 라우트는 만들지
않았다.

**지금 만들면 "설정만 바꾸면 도는" 경로가 생기기 때문이다.** 실제 Provider가
Stub 이고 저장소가 메모리인 상태에서 작업 생성 API를 열어 두면, 언젠가
플래그 하나가 바뀌었을 때 아무도 의도하지 않은 실제 요청이 나갈 수 있다.

작업 생성·진행 라우트는 다음 두 가지가 모두 갖춰진 뒤에 추가한다:
1. 승인된 Provider (명세 + 이용 권한)
2. Postgres 저장소 어댑터

## 7. 기존 모듈과의 관계

`lib/autobook/**` 는 `lib/reservation/**`(v0.4), `lib/watch/**`(v0.5),
`lib/automation/**`(v0.7)을 **import 하지 않는다**
(verify 스크립트가 검사한다). 패턴은 재사용하되 코드는 독립이다. 그래야
이 PR이 기존 상태 기계를 망가뜨릴 수 없다.

브라우저로 공식 예매 화면을 조작하는 방식은 별개로 폐기했고, 관련 코드는
저장소에 두지 않는다([ADR 0003](./adr/0003-abandon-browser-agent.md)).

## 8. 환경변수

전부 fail-closed 다. 없거나 이상하면 항상 비활성이다.

```
AUTOBOOK_PROVIDER=unavailable   # unavailable(기본) | mock-server | official-approved
AUTOBOOK_STORE=disabled         # disabled(기본) | memory | postgres
ENABLE_AUTOBOOK_JOBS=false      # 작업 생성·진행 kill switch
AUTOBOOK_KILL_SWITCH=off        # on 이면 모든 것보다 우선해 전부 중단
AUTOBOOK_WORKER_BATCH=1         # 한 번에 진행할 작업 수(상한 5)
```

- `mock-server` 는 `NODE_ENV=production` 에서 값과 무관하게 거부된다.
- `memory` 저장소도 운영에서 거부된다(Serverless 인스턴스마다 메모리가
  달라 "서버형"이 성립하지 않는다).
- `official-approved` 를 선택해도 Stub 이 동작하며
  `OFFICIAL_INTEGRATION_REQUIRED` 로 정직하게 거부한다.

**운영 Vercel 환경변수는 이번 작업에서 변경하지 않았다.**

## 8-1. 폐기된 브라우저 Agent 경계

`scripts/verify-autobook.cjs` 가 다음을 검사한다(회귀 방지).

- `agent/`, `lib/live/`, `tests/agent/` 경로가 저장소에 없다
- 폐기된 Agent 의 식별 토큰(공식 예매 호스트, Agent 프로토콜 상수, Agent 포트,
  폐기 안내 모듈명 등 — 목록은 스크립트의 `FORBIDDEN_TOKENS`)이 어떤 파일에도 없다
- `lib/autobook/**` 이 `agent/`, `lib/live/`, `lib/automation/` 을 import 하지
  않는다(절대·상대 경로 모두)
- 서버형 자동예약 경로에 브라우저 자동화(chromium·playwright 등)가 없다
- 자동예약 API 에 쓰기 메서드가 없다

배경은 [ADR 0003](./adr/0003-abandon-browser-agent.md).

## 9. 다음 착수 조건

1. **코레일 공식 "예약대기"가 사용자의 필요를 이미 해결하는지 먼저 판단**
   (조사 §6). 해결한다면 자동 조회를 만드는 것보다 그쪽 안내가 낫다.
2. 그래도 필요하다면: 공식·승인된 좌석 조회·예약 연동의 **요청·응답 명세와
   이용 권한** 확보
3. 계정 연결 방식(OAuth 또는 API credential) 확보
4. Postgres 저장소 어댑터 구현
5. 작업 생성·진행 API + UI 폼 추가
6. 외부 실사이트 테스트 전 **대상·요청 횟수·예약 가능성을 보고하고 사용자
   승인**
