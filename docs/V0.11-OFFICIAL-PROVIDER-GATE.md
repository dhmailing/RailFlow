## 0. 결론 — Gate 미충족. 읽기 전용 Provider를 구현하지 않았다

**네 개 Gate 중 하나도 충족하지 못했다.**

| Gate | 요건 | 결과 |
|---|---|---|
| 1 | 공식 요청 endpoint와 요청·응답 명세 | **미확인** |
| 2 | 정식 발급된 인증 방식 | **미확인** |
| 3 | 좌석 상태 필드의 공식 의미 | **미확인** |
| 4 | 그 방식의 이용 권한·허용 근거 | **미확인** |

따라서 `official-approved` Provider는 **Stub 그대로 유지**한다. 새 Provider도, 새 Mock·시뮬레이터도 만들지 않았다. 이번 작업의 코드 변경은 **0건**이며 문서만 추가했다.

### 왜 하나도 확정하지 못했는가 — 이 세션의 결정적 제약

**이 작업 환경의 네트워크 정책이 모든 공식 원문 호스트를 차단한다.** 2026-10-01 기준, 다음 11개 주소에 각각 1회 접근을 시도해 **전부 거부**됐다(프록시 CONNECT 거부, HTTP 응답 자체가 없음).

| `www.data.go.kr` | curl, WebFetch | 차단 (`EGRESS_BLOCKED`) |
| `info.korail.com` | curl, WebFetch | 차단 (`EGRESS_BLOCKED`) |
| `www.korail.com` | curl | 차단 |

따라서 **이 세션에서 읽은 공식 원문은 0건이다.** 아래에 적은 모든 외부 사실은 **검색 결과 요약**에서 온 것이며 `잠정 정보` 등급이다. 검색 요약을 Gate 1~4의 근거로 쓰지 않았다.

#### 중요 — 이전 판의 KayRail 서술은 순환 근거일 수 있다

v0.9 조사 문서(`V0.9-KORAIL-INTEGRATION-RESEARCH.md` §3)는 KayRail에 대해 "서버에서 자동예약이 진행되며 코레일 계정 연동이 필요하고 좌석 확보 후 사용자가 코레일+에서 직접 결제한다"고 적었고, 그 근거를 "공개 안내"로 표시했다. **그 문장의 실제 출처는 사용자가 화면에서 본 것을 전달한 내용이다** — 이 프로젝트가 KayRail의 공개 안내 본문을 직접 열어 확인한 적은 없다.

2026-10-01 재확인에서 드러난 것: KayRail을 검색하면 **검색 결과 1위가 이 저장소의 PR #15**이고, 요약문이 우리가 쓴 문장을 그대로 되돌려준다. 즉 지금 검색으로 얻는 "KayRail 설명"은 **우리 자신의 기록을 재인용한 것**일 수 있다. 독립 출처를 하나도 확보하지 못했다.

따라서 다음을 분리한다.

| 구분 | 상태 |
|---|---|
| 사용자가 KayRail 화면에서 **직접 본** 것(좌석 상태·자동예약 진행·시도 횟수·만료시간 표시) | **사용자 제공 증거** — 이 세션에서 재현하지 않았다 |
| KayRail의 **서버 구조·계정 처리·좌석 데이터 취득 방식** | **추정.** 확인된 바 없다. 자동예약 카드가 화면에 있다는 것이 실제 예약 성공이나 특정 서버 구조를 뜻하지 않는다 |
| KayRail이 쓰는 **연동 경로** | **미확인.** 알아내려 시도하지 않았다(앱 트래픽 가로채기·역공학·접근 제한 우회 없음) |
| KayRail이 작동한다는 사실 | 기술적 가능성의 근거일 뿐. **같은 방식의 이용이 허용된다는 뜻도, RailFlow에 권한이 있다는 뜻도 아니다** |

그 전에 **사용자가 할 수 있는 일이 있다**: `rail.kay.kr` 은 사용자의 브라우저에서는 열린다. 그 사이트의 **이용약관·개인정보처리방침·도움말**에 좌석 데이터를 어떻게 얻는지, 개발자 문의 창구가 있는지 적혀 있을 수 있다. 이 환경은 그 페이지를 열 수 없다. §5-5 참조.

### D-2. 그 밖에 공개 자료로 확인되는 허용된 연동 방식

**판정: 미확인.** 검색에 나오지 않은 것을 "없음"으로 판정하지 않는다.

### 4-3. 예약대기는 목표의 대체물이 아니다 (2026-10-01 정정)

**정정한다.** 이 문서의 이전 판은 예약대기 확인 결과를 가지고 "출발 2일 이내 구간을 포기한다"를 선택지로 제시했고, 그것을 먼저 확인하도록 권했다. **그 서술을 철회한다.** 두 가지를 섞은 잘못이었다.

**사용자 목표는 바뀌지 않았다**: 선택한 열차의 잔여좌석을 반복 조회하고, 좌석이 나오면 예약을 확보한 뒤 **사용자가 공식 앱에서 직접 결제**하는 것. 예약대기는 그 목표를 **대체하지 않는다.**

예약대기 확인이 쓰이는 범위는 하나다 — **사용자 요구가 공식 기능으로 어디까지 충족되는지 가늠하는 자료.** 그것이 Provider 착수 Gate를 충족시키지도, 목표를 축소할 근거가 되지도 않는다.

그리고 신청 기한(출발 2일 전) 자체가 **잠정 정보다.** 원문을 대조하지 못한 기한을 근거로 "그 구간은 포기"라는 결론을 내릴 수 없다. 설령 기한이 사실로 확인돼도, 그것은 "공식 기능이 거기까지 커버한다"는 뜻일 뿐 **RailFlow가 그 범위를 넘어선 기능을 만들면 안 된다는 뜻이 아니다.** 만들 수 있는지 여부는 Gate 1~4(명세·인증·필드 의미·이용 권한)로만 판정한다.

**혼동하지 말아야 할 네 가지를 분리한다.**

| 구분 | 이 문서에서의 역할 |
|---|---|
| 예약대기 화면 확인 | 사용자 요구가 공식 기능으로 얼마나 충족되는지 **평가 자료**. Gate 근거가 아니다 |
| API 명세·인증·이용 권한 | **Provider 착수의 유일한 근거**(Gate 1~4) |
| 이 조사 환경의 접속 차단 | 이 환경에서 확인할 수 없다는 **사실**. 서비스의 가능·불가능과 무관하다 |
| 서비스 자체의 기술적 불가능 | **별도 증거가 필요한 판단.** 지금 그런 증거는 없다 |

운영자의 매크로 탐지 운영(§3-E, 잠정)은 **브라우저 자동화 방식**에 대한 신호이며, 공식·승인된 연동 경로의 존재 여부와는 다른 문제다. 전자가 사실이어도 후자는 미확인으로 남는다.

## 5. 사용자 수동 확인 절차

이 세션은 공식 화면을 열 수 없다. 아래는 **사용자가 일반 브라우저·공식 앱에서** 직접 확인하는 절차다. 설치·터미널이 필요 없다.

> **비밀번호·OTP·쿠키는 요청하지 않는다.** 로그인이 필요하면 사용자가 직접 입력한다. 캡처에서 개인정보를 가려 주시면 된다.

### 5-1. 확인 1 — 동탄→울산(통도사)에 예약대기가 있는가

- **열어야 할 곳**: 코레일+ 앱 → 승차권 예매. (웹이 편하면 `letskorail.com` 또는 `korail.com` 의 승차권 예매 화면)
- **입력할 구간·날짜**: 출발 **동탄**, 도착 **울산(통도사)**, 날짜는 **매진이 날 만한 날**(주말 오전, 또는 연휴). 매진 열차가 보여야 판정이 된다
- **이 확인의 용도**: 공식 기능이 사용자 요구를 어디까지 덮는지 아는 **평가 자료**다. Gate 근거가 아니며, 목표를 줄일 근거도 아니다(§4-3)
- **확인할 버튼·문구**:
  - 매진된 열차 행에 **"예약대기"** 버튼이나 문구가 뜨는가
  - 그 버튼을 눌렀을 때(신청하지 않아도 됨) 안내 화면에 **신청 기한**과 **결제기한**이 어떻게 적혀 있는가
  - 로그인 없이도 버튼이 보이는가, 아니면 로그인 후에만 보이는가
- **가리고 캡처할 영역**: 아이디·이름·전화번호·결제수단·예약번호. 열차번호·시각·좌석 상태 문구는 그대로 보이게
- **캡처에서 판정할 항목**: 위 §4-1 표의 `미확인` 7개 항목 중 채워지는 것

### 5-2. 확인 2 — 출발 2일 이내에는 어떻게 보이는가

- **열어야 할 곳**: 같은 화면
- **입력할 구간·날짜**: 같은 구간, **내일 또는 모레** (= 출발 2일 이내)
- **확인할 버튼·문구**: 매진 열차에 **예약대기 버튼이 사라지는지**, 아니면 그대로 있는지. 사라진다면 어떤 안내 문구가 대신 뜨는지
- **판정할 항목**: §4-3의 "신청 기한" 쟁점. 이것이 이번 판단의 핵심이다

### 5-3. 확인 3 — 이용약관의 자동화 관련 조항

- **열어야 할 곳**: 코레일 홈페이지 하단 **이용약관**(및 있으면 **회원약관**)
- **확인할 문구**: "자동화", "매크로", "프로그램", "비정상적인 방법", "크롤링", "반복" 중 하나라도 들어간 조항
- **판정할 항목**: 그런 조항이 **있는지 없는지**, 있다면 어떤 행위를 금지하는지. **조항이 없다는 사실도 그대로 기록한다**(없음 = 허용이 아니다)

### 5-4. 확인 4 — 파트너·제휴 창구가 실재하는가 (문의 전 사전 확인)

- **열어야 할 곳**: 코레일 홈페이지의 **제휴·협력** 또는 **공공데이터 개방** 안내 페이지
- **확인할 문구**: 판매대리점·제휴·API 연동 **신청 창구**나 담당 부서·연락처
- **판정할 항목**: §6의 문의를 어디로 보낼지

### 5-5. 확인 5 — KayRail의 공개 안내 (2026-10-01 추가)

이 환경은 `rail.kay.kr` 을 열 수 없다. 사용자의 브라우저에서는 열린다.

- **열어야 할 곳**: `https://rail.kay.kr` → 페이지 하단 또는 메뉴의 **이용약관**, **개인정보처리방침**, **도움말/FAQ**, **공지/업데이트**
- **입력할 것**: 없다. **로그인하지 않아도 되는 페이지만** 본다. 계정 연결·예약은 하지 않는다
- **확인할 문구**:
  - 좌석 상태를 **어떻게 얻는다고** 설명하는지 (공식 API / 제휴 / 설명 없음)
  - **코레일 계정 연동**을 어떻게 설명하는지 — 비밀번호를 받는다고 적혀 있는지, 아니면 다른 방식이라고 적혀 있는지
  - 코레일·SR과의 **공식 제휴·승인**을 주장하는 문구가 있는지, 아니면 "비공식"이라고 밝히는지
  - **개발자·제휴·문의 창구**(이메일·폼·디스코드 등)가 있는지
- **가리고 캡처할 영역**: 본인 아이디·이름·전화번호·결제수단. 약관·방침 본문은 그대로
- **판정할 항목**: §3-C-2 표의 `미확인` 항목들, 그리고 §6 Gate 4(이용 권한)에 쓸 수 있는 문구가 있는지

> **비밀번호·OTP·쿠키는 요청하지 않는다.** 로그인이 필요한 페이지는 보지 않아도 된다.

## 6. Provider 착수 Gate — 판정 근거

| Gate | 요건 | 현재 | 왜 미충족인가 |
|---|---|---|---|
| 1 | 공식 요청 endpoint와 요청·응답 명세 | **미충족** | 좌석 상태를 주는 공식 endpoint를 하나도 확인하지 못했다. 공식 원문을 열지 못했다 |
| 2 | 정식 발급된 인증 방식 | **미충족** | TAGO 키는 시간표용이며 좌석조회 키가 아니다. OAuth·파트너 credential 발급 창구 미확인 |
| 3 | 좌석 상태 필드의 공식 의미 | **미충족** | 좌석 상태 필드를 주는 명세가 없으므로 그 의미도 없다 |
| 4 | 이용 권한·허용 근거 | **미충족** | 어느 후보도 허용 근거를 확인하지 못했다. 후보 E는 반대 방향 신호만 있다 |

**네 개 중 하나도 충족하지 못했으므로 Provider를 구현하지 않았다.**

이번 작업에서 지킨 선:

- 공식 웹 화면에 문구가 보인다는 것을 API 사용 권한의 근거로 쓰지 않았다
- 공식 앱이 호출하는 주소를 찾으려 하지 않았다 (앱 트래픽 가로채기·디컴파일·인증서 우회 없음)
- 다른 서비스(KayRail 등)의 통신 방식을 역공학하지 않았다
- 확인되지 않은 endpoint를 placeholder로 코드에 넣지 않았다
- 새 Mock Provider·시뮬레이터를 만들지 않았다
- 라이브 단건 조회를 하지 않았다 (대상 endpoint 자체가 없다)

## 8. 다음 단계 (2026-10-01 정정)

**정정한다.** 이전 판은 "§5-1·5-2를 먼저 확인하면 공식 기능으로 충분한가가 결정된다"고 썼다. 그것은 예약대기 확인을 목표 판정의 분기점으로 올려 놓은 과도한 서술이었다. **철회한다.**

목표(선택한 열차 반복 조회 → 좌석 확보 → 사용자 직접 결제)를 달성할 수 있는지는 **Gate 1~4로만** 판정한다. 그래서 다음 단계는 **Gate를 채우는 일**이다.

1. **운영자·제휴 창구에 문의한다** — `docs/inquiries/`. 좌석 상태를 **데이터로** 받을 수 있는 공식·승인된 경로가 있는지, 개인 자격으로 신청 가능한지. 이것이 Gate 1·2·4를 동시에 채우는 유일한 경로다
2. **§5-1·5-2(예약대기)와 §5-3(약관 조항)은 병행한다.** 전자는 공식 기능의 커버 범위를 아는 자료이고, 후자는 Gate 4의 일부다. **어느 쪽도 1번을 대신하지 않는다**
3. Gate 1~4가 **전부** 채워질 때만 읽기 전용 Provider를 착수한다
4. 그때까지 `AUTOBOOK_PROVIDER` 는 `unavailable` 로 유지한다

v0.9부터 v0.10까지 그릇(상태 기계·분산 락·멱등키·영속 저장소·Worker 진입점)은 만들어 두었다. **지금 비어 있는 것은 코드가 아니라 권한과 명세다** — 그래서 다음 작업이 문의와 확인이다. 이것은 "개발 순서가 틀렸다"는 뜻이 아니라, Gate가 열리면 바로 쓸 수 있는 상태라는 뜻이다.

## 10. 막힌 지점 분류 (2026-10-01 추가)

목표는 변하지 않았다 — **RailFlow가 선택한 구간·날짜·시간대·인원·좌석등급으로 실제 취소표를
반복 조회하고, 좌석 발견 시 예약을 생성해 결제 대기까지 진행한다. 결제는 사용자가 공식
서비스에서 직접 한다.**

이번 라운드의 산출물은 "실제 열차 한 편의 좌석 상태를 읽은 결과"였다. **읽지 못했다.**
아래는 그 이유를 다섯 축으로 나눈 것이다. 축을 섞지 않는 것이 이 표의 목적이다.

### 10-1. 다섯 가지 원인 분류

| # | 원인 | 상태 | 증거 |
|---|---|---|---|
| 1 | **개발 환경의 외부 네트워크 차단** | **확인됨 — 그리고 사용자가 바꿀 수 있는 설정이다** | 이 컨테이너의 egress 정책이 철도·공공데이터 호스트를 거부(프록시 CONNECT 거부). 환경 설정의 **Network access → 허용 도메인**에서 변경 가능 |
| 2 | **철도 사이트가 표시한 접근 제한·자동화 차단** | **확인됨 — 단, 범위가 한정된다** | `docs/adr/0003-abandon-browser-agent.md`. 관찰 대상은 **SRT 예매 화면 + 화면이 보이는 Playwright**였고, 관찰 위치는 **사용자의 Windows PC**였다. 조회만 해도 제한됐고 빈도를 낮춰도 달라지지 않았다 |
| 3 | **로그인·세션 만료** | **미확인** | 2번에서 접속 자체가 제한돼 세션 유지 여부를 시험할 단계에 이르지 못했다. 세션이 원인이라는 증거는 없다 |
| 4 | **잘못된 주소·선택자·화면 파싱** | **미확인** | 선택자·파서를 실제 화면으로 채운 적이 없다. 2번 때문에 화면을 확보하지 못했다. 파싱 오류가 원인이라는 증거는 없다 |
| 5 | **프로젝트 내부 비활성 플래그** | **확인됨 — 의도된 상태** | 런타임 조회 결과: `provider: "unavailable"`, `store: "disabled"`, `jobsEnabled: false`, `liveReservationPossible: false`. `official-approved` Stub 의 capability 3개 전부 `false`, 계정 연결 3개 방식 전부 `available: false` |

### 10-2. 축을 섞지 않기 위한 명시

- **1번을 2번으로 단정하지 않는다.** 이 컨테이너가 사이트에 닿지 못하는 것은 **이 환경의
  설정**이며, 사이트가 우리를 차단한다는 증거가 아니다.
- **반대 방향도 단정하지 않는다.** 1번을 해제해도 2번이 해결되지 않는다. 방화벽을 열면
  연결은 시도할 수 있지만, 운영자가 허용하는 요청 경로가 생기는 것은 아니다.
- **2번의 범위를 과대 적용하지 않는다.** 관찰된 것은 *SRT 화면 + 브라우저 자동화*다.
  ADR 0003 이 이를 "브라우저 자동화 도구로 공식 화면에 접근한 것 자체가 탐지 대상"이라고
  일반화해 적은 것은 한 호스트의 관찰을 넘어선 서술이다. 다만 **그 일반화를 좁혀도 결정은
  바뀌지 않는다** — 브라우저 자동화를 되살리지 않는다는 결정은 유지된다.
- **3·4번을 원인으로 쓰지 않는다.** 증거가 없다. 미확인으로 남긴다.

### 10-3. 실행 환경 후보 검토 — 전부 열려 있지 않다

사용자가 "공식 API 외에 일반적인 예매 화면 자동화도 검토 대상"이라고 했으므로, 공식 API가
없다는 이유로 검토를 끊지 않고 네 가지를 끝까지 따져 봤다.

| 후보 | 판정 | 이유 |
|---|---|---|
| **이 컨테이너에서 단건 조회** | **지금 불가** | 네트워크 차단(1번). 설정으로 해제 가능하지만, 해제해도 **호출할 주소와 응답 필드 의미가 없다**(Gate 1·3). 주소를 추측하면 비공개 endpoint 추측이 된다 |
| **사용자 PC에서 브라우저 자동화** | **하지 않는다** | 이것이 바로 폐기된 Agent 경로다. 이름·설정만 바꿔 되살리지 않는다. 접근 제한이 이미 확인된 경로에 재시도하지 않으며, 실행 위치·브라우저·IP·계정을 바꿔 제한을 피하지 않는다 |
| **통합 이후 코레일 화면 + 브라우저 자동화** | **하지 않는다** | 호스트는 다르지만 기법이 같고, 통합 이후 운영 주체도 같다. 운영자가 로그인·조회 단계에서 매크로를 차단한다는 설명도 있다(잠정). 기법을 되살리는 것이므로 제외한다 |
| **공식·승인된 요청 경로로 단건 조회** | **조건 미충족** | Gate 1·2·4 미확인. 이것만이 남은 정당한 경로다 |

### 10-4. 그래서 막힌 지점은 하나다

**네트워크도, 세션도, 파서도, 플래그도 지금의 병목이 아니다.**

병목은 **"호출해도 되는 요청 경로가 한 건도 없다"**는 것이다. 구체적으로 Gate 1(요청
endpoint와 응답 명세)과 Gate 4(그 경로를 호출할 권한)다. 이 둘이 비어 있으면 방화벽을 열어도,
서버를 상시 실행해도, 코드를 더 만들어도 좌석 상태 한 건을 읽을 수 없다.

그래서 이번 라운드에 **새 Mock·마법사·Provider Stub·DB·Queue를 추가하지 않았다.** 기반
코드를 더 쌓는 것은 실제 연동 진척이 아니다.

### 10-5. 다음 단계에 필요한 조건 — 한 가지

**좌석 상태를 주는 요청 경로 1건을 정당한 출처에서 확보하는 것.** 그 한 건에 다음 세 가지가
함께 와야 한다.

1. 요청 주소와 요청·응답 형식
2. 응답의 좌석 상태 필드가 뜻하는 것 (매진 / 예약 가능 / 예약대기 / 상태 불명의 구분)
3. 그 경로를 RailFlow가 호출해도 된다는 근거

이 세 가지가 오는 순간 §4의 최소 Provider(날짜·구간·열차번호·출발시각·일반실·특실 원문 표시·
조회 시각만 읽는 단건 조회)를 바로 만들 수 있다. 그릇은 v0.9~v0.10에 이미 있다.

**확보 수단은 문의 하나뿐이다** — `docs/inquiries/`. 05(KayRail 운영자) → 04(판매대행·제휴)
순서를 권한다. 이것은 "KayRail 협업으로 목표를 바꾸는 것"이 아니다. 목표는 그대로 두고,
목표를 달성할 **권한과 명세를 받는 유일한 경로**가 문의라는 뜻이다.

### 10-6. 이번 라운드에 하지 않은 것

실제 좌석 조회 **0건**, 실제 예약 **0건**, 외부 철도 호스트 요청 **0회 성공**, 계정 연결·
로그인 **0회**, 쿠키·세션·비밀번호·OTP 수집 **0건**, 결제 자동화 **없음**, 접근 제한 우회
**없음**, 폐기 Agent 복원 **없음**, 코드 변경 **0건**, 운영 DB·Production 환경변수·유료
인프라 **변경 0건**.
