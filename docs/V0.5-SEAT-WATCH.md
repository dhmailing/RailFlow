# RailFlow v0.5 — 취소표 감시(Seat Watch) 기반 아키텍처

## 0. 이 문서의 성격

이 PR은 **실제 예약·결제·코레일 계정 로그인을 구현하지 않는다.** RailFlow는 좌석을 감시하고 알릴 뿐이며, 실제 예약은 사람이 코레일+에서 직접 완료한다. 공식 좌석정보 Provider가 아직 없으므로, 이번 PR의 모든 좌석 확인은 Production 기본값(`SEAT_AVAILABILITY_PROVIDER=disabled`)에서 `available: null` / `providerStatus: "unavailable"`을 반환하는 `unavailableSeatAvailabilityProvider`가 담당한다 — 실제 잔여좌석을 조회한 것처럼 보이는 화면이나 API 응답은 어디에도 없다.

v0.4의 시간표(`RailScheduleProvider`)·Mock 예약 작업(`RailReservationProvider`) 기반은 그대로 남아 있고 이번 PR에서 손대지 않았다(`scripts/verify-rail.cjs`, `scripts/verify-reservation.cjs` 모두 통과). v0.5는 그 옆에 완전히 새로운 인증 계층(`lib/auth/`)과 취소표 감시 계층(`lib/watch/`)을 추가한다.

## 1. 인증 계층 (`lib/auth/`)

외부 OAuth 프로젝트나 유료 인증 서비스를 새로 만들지 않기 위해, RailFlow 자체의 이메일+비밀번호 계정과 서버 세션을 구현했다.

- **비밀번호**: Node 내장 `crypto.scrypt`로 해시한다(`lib/auth/password.ts`). 새 npm 의존성이 없다. 로그인 시 계정이 없어도 더미 해시로 항상 실제 scrypt 연산을 한 번 수행해, "계정 없음"과 "비밀번호 틀림" 응답이 처리 시간 차이로 구분되지 않게 한다(`getDummyPasswordHash`).
- **세션**: 서명된 JWT가 아니라 **불투명(opaque) 서버 세션 토큰**이다(`crypto.randomBytes(32)`, 256비트). 세션 저장소(`AuthStore`)가 유일한 진실의 출처이므로, 로그아웃·계정 삭제·kill switch가 모두 "그 행 삭제"로 끝난다 — 블록리스트나 키 로테이션이 필요 없다. 로그인 성공 시 항상 새 세션을 발급한다(세션 고정 공격 방지). 선택 이유는 `docs/adr/0002-auth-storage-notification.md` 참고.
- **전달 방식**: httpOnly 쿠키(`railflow_session`, Production에서는 `__Host-railflow_session`)만 사용한다. 세션 토큰은 응답 JSON 본문에 절대 포함되지 않는다(`{user, expiresAt}`만 반환) — 쿠키가 유일한 전달 경로다. Android 등 네이티브 클라이언트를 위한 Bearer 토큰 인증은 이번 PR에 없다 — 회전·폐기·안전한 저장소를 포함한 별도 설계가 필요하며, 그 전까지는 이 웹 세션 쿠키를 그대로 재사용하지 않는다(`lib/auth/session.ts`, `docs/adr/0002`). 인증 응답에는 항상 `Cache-Control: no-store`를 붙인다.
- **CSRF/Origin 검증**: Production에서는 쿠키로 인증되는 모든 상태 변경 요청(회원가입/로그인/로그아웃/계정삭제/기기 등록/감시 작업 생성·취소·재감시·예매확인)에 대해 `Origin` 헤더를 배포 시점에 등록한 `APP_ORIGIN` 환경변수(정확한 `scheme://host[:port]`)와 비교하고, 없거나 다르면 403으로 거부한다(`lib/security/origin-guard.ts`). `APP_ORIGIN`이 없거나 형식이 잘못되면 Production의 모든 상태 변경 요청이 fail-closed로 거부된다 — `Host` 헤더는 프록시 설정에 따라 조작될 수 있어 더 이상 비교 기준으로 쓰지 않는다. 스킴(http/https)이 다르면 host가 같아도 다른 출처로 취급한다. Vercel Preview는 배포마다 URL이 달라 Production과 같은 `APP_ORIGIN`을 쓸 수 없으므로, Preview에서 실제 인증을 켜려면 그 환경 전용 값을 별도로 등록해야 한다. 개발/테스트 환경(`NODE_ENV≠production`)에서는 적용되지 않는다.
- **계정 삭제 재인증**: `DELETE /api/auth/account`는 현재 세션이 있다는 사실만으로 즉시 삭제하지 않고, 요청 본문에 현재 비밀번호를 다시 요구해 서버가 재검증한다 — 클라이언트 쪽 확인 대화상자는 보안 장치로 취급하지 않는다.
- **저장소**: `AUTH_STORE` 플래그(`disabled`(기본값)|`memory`|`postgres`)로 선택한다. `memory`는 `lib/auth/memory-store.ts`(프로세스 메모리, 재시작 시 소실)를 쓰지만 `NODE_ENV=production`에서는 이 값을 `memory`로 설정해도 항상 사용 불가로 취급돼 회원가입·로그인·계정삭제·인증 기반 API가 모두 503(`AUTH_STORE_DISABLED`)으로 거부된다 — Vercel Serverless는 인스턴스마다 별도 프로세스 메모리를 가져 실제 계정 시스템으로 쓸 수 없기 때문이다(`lib/auth/feature-flags.ts`). `postgres`는 선택 가능한 값일 뿐 이번 PR에는 실제 구현이 없다. `AuthStore` 인터페이스(`lib/auth/types.ts`)가 유일한 교체 지점이며, `lib/auth/store.ts`의 `getAuthStore()`만 바꾸면 Postgres 구현으로 교체된다(§ Postgres 스키마 참고).
- **API**: `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`, `GET /api/auth/status`(인증 불필요, 저장소 연결 여부만 노출), `DELETE /api/auth/account`(비밀번호 재확인 후 계정+감시 데이터 삭제).
- **v0.4와의 관계**: v0.4의 `demo-*` 사용자 ID 방식은 그대로 남아 있다(건드리지 않음). v0.5의 모든 신규 API는 처음부터 이 인증 계층만 사용하며 `demo-*` 스코프를 전혀 쓰지 않는다.

## 2. 취소표 감시 작업 상태 모델 (`lib/watch/state-machine.ts`)

```
REGISTERED → WATCHING ⇄ PROVIDER_UNAVAILABLE / RATE_LIMITED
                ↓
            SEAT_FOUND → COMPLETED (사용자가 "예매 완료"를 직접 확인)
                ↓
            WATCHING ("다시 감시": 예매가 안 됐거나 좌석이 사라짐)
어느 비종료 상태에서든 → CANCELLED
어느 비종료 상태에서든 → EXPIRED (watchUntil 경과, 실제로 저장됨)
```

- 종료 상태: `COMPLETED`, `CANCELLED`, `EXPIRED`, `FAILED`. v0.4 PR #7 검토에서 얻은 교훈을 그대로 적용해, 만료는 예외를 던지는 대신 Worker가 실제로 `EXPIRED`로 전이·저장한다(`hasExpired`는 순수 함수, 저장은 `worker.ts`가 담당).
- `PROVIDER_UNAVAILABLE`은 오류가 아니라 **정직한 상태**다: `SEAT_AVAILABILITY_PROVIDER=disabled`(Production 기본값)인 동안 모든 `WATCHING` 작업은 이 상태에 머무르고, Provider가 연결되면(`mock`으로 전환되면) 자동으로 `WATCHING`으로 돌아간다. 사용자는 공식 Provider가 없어도 감시 조건을 미리 등록할 수 있다 — 이것이 §1의 "PROVIDER_UNAVAILABLE 상태로 명확하게 보여줘" 요구사항이다.
- 여러 후보 열차 중 하나가 `SEAT_FOUND`가 되면 작업 전체가 `SEAT_FOUND`로 넘어가므로, Worker는 더 이상 다른 후보를 확인하지 않는다("성공 시 나머지 후보 중단"). 같은 사용자·날짜·구간·인원의 중복 작업은 애초에 하나만 허용되므로(`DUPLICATE_JOB`), 그 조건에서 "동시에 진행 중인 다른 작업"도 구조적으로 존재하지 않는다.
- `RATE_LIMITED`·`FAILED`는 상태 모델에는 정의돼 있지만, 실제 Provider가 없는 이번 PR에서는 도달할 경로가 없다(Mock Provider는 두 상태를 만들지 않는다) — 실제 Provider가 연결되면 비로소 의미를 가진다.
- `예매 완료`/`다시 감시`는 Worker 틱이 아니라 사용자 액션이다(`confirmBooking`/`resumeWatching`, `lib/watch/worker.ts`). 상태 머신이 두 번째 클릭을 `INVALID_TRANSITION`으로 막으므로 자연히 멱등적이다.

## 3. Provider 분리

```ts
// lib/watch/types.ts (신규)
interface SeatAvailabilityProvider {
  readonly name: "unavailable" | "mock";
  capabilities(): ProviderCapabilities;
  checkSeats(job: WatchJob): Promise<SeatCheckResult[]>;
}
interface BookingLaunchProvider {
  readonly name: string;
  launch(job: WatchJob, candidateId: string): Promise<BookingLaunchResult>;
}
```

| 구현 | 파일 | 역할 |
| --- | --- | --- |
| `unavailableSeatAvailabilityProvider` | `lib/watch/unavailable-seat-provider.ts` | **Production 기본값.** 모든 후보에 `available: null, providerStatus: "unavailable"`을 반환한다. 외부 요청 없음. |
| `mockSeatAvailabilityProvider` | `lib/watch/mock-seat-provider.ts` | 개발·테스트 전용. `TrainCandidate.mockScenario`로만 결과가 결정된다. 외부 요청 없음. |
| `koreailWebFallbackBookingLaunchProvider` | `lib/watch/booking-launch-provider.ts` | 공식적으로 확인된 딥링크가 없으므로 `deepLinkAvailable: false`를 항상 반환하고, 코레일 공식 웹 주소와 복사 가능한 여정 문구만 제공한다(§6). |

`RailScheduleProvider`(v0.3 시간표)·`RailReservationProvider`(v0.4 Mock 예약)와는 완전히 분리돼 있다 — Seat Availability Provider는 TAGO도, v0.4의 Mock 예약 로직도 호출하지 않는다.

## 4. Mock 취소표 시뮬레이션 흐름

§D의 8단계(등록 → 좌석 없음 → Mock 좌석 발생 → 알림 → 예매 화면 이동 버튼 활성화 → 예매 완료/실패 직접 기록 → 나머지 작업 중단 → 완료/만료)를 `scripts/verify-seat-watch.cjs`가 직접 구동해 끝까지 검증한다.

**검증값(1~5)의 정직성**: v0.4 PR #7의 최종 검토에서 문자열 `"1"`이 숫자로 오인되어 통과하던 버그가 발견됐다. 같은 실수를 반복하지 않도록, 이번 PR의 `simulationIntervalSeconds`에 해당하는 `tick` 필드는 API 스키마 단계부터 `z.number().int().min(1).max(5)`(문자열 분기 없음)이고, `lib/watch/simulation-guard.ts`의 `assertSimulationAllowed`도 `Number(tick)` 변환 없이 `typeof tick === "number"`를 직접 검사한다. 값은 실제로 기다리거나 반복 실행되지 않으며, Worker 한 스텝을 즉시 실행할지 결정하는 검증값일 뿐이다.

## 5. 알림 구조 (`lib/watch/notification/`)

- **채널**: `fcm`, `webpush`, `telegram`, `email` (`NotificationChannel`).
- **Device 소유권(`verified`)**: fcm/webpush 토큰은 브라우저·OS가 발급하므로 등록 즉시 `verified: true`로 취급하지만, email/telegram은 누구나 임의의 값을 입력할 수 있어 소유권 확인 절차(이번 PR에는 없음)가 끝나기 전까지 항상 `verified: false`다. `dispatchNotification`은 `verified`가 false인 동안 어댑터를 아예 호출하지 않고 `skipped_unverified`만 기록한다 — 확인되지 않은 수신처로는 실제 알림이 절대 나가지 않는다.
- **API/UI 노출**: Device API는 원문 `token`을 절대 반환하지 않는다. `DeviceSummary` DTO(`maskedDestination`만 포함)로만 응답한다 — 등록 직후 응답도 예외 없다(`lib/watch/store.ts`의 `toDeviceSummary`).
- **채널 일치 검증**: 감시 작업 생성 시 `notificationMethods[].channel`이 실제로 등록된 Device의 `channel`과 다르면 `NOTIFICATION_CHANNEL_MISMATCH`로 거부한다(`lib/watch/store.ts`의 `createWatchJob`).
- **Adapter**: 이번 PR은 외부 계정·실서비스 키를 요구하지 않는다(§E). `getNotificationAdapter(channel)`은 `NODE_ENV!=="production"`이면 `InMemoryNotificationAdapter`(프로세스 메모리에 저장, 네트워크 요청 없음)를, 그 외(특히 **항상** Production)에는 `NotConfiguredNotificationAdapter`(구조화된 `NOTIFICATION_NOT_CONFIGURED` 오류만 던지고 아무것도 보내지 않음)를 돌려준다.
- **멱등성·재시도·동시성(Outbox/Claim 모델, 검토 재반영)**: `lib/watch/store.ts`의 `notificationOutbox`는 `(userId, idempotencyKey)`마다 정확히 한 행만 갖는다. `dispatchNotification`(`lib/watch/notification/dispatch.ts`)은 어댑터를 부르기 **전에** `claimNotification()`으로 그 행의 소유권을 원자적으로 획득한 호출자만 실제로 발송한다 — 이전 구현("이미 성공했는지 확인 → 어댑터 호출(비동기 대기) → 저장")은 확인과 저장 사이의 대기 구간에서 두 Worker가 동시에 같은 알림을 처리하면 둘 다 확인을 통과해버릴 수 있는 경쟁 조건이 있었다. claim에 실패한 호출(`duplicate`: 이미 `delivered`/`skipped_unverified`로 끝남, `already_claimed`: 다른 호출자가 처리 중이거나 아직 재시도 시각이 아님)은 어댑터를 절대 호출하지 않고 기존 행을 그대로 반환한다. claim을 얻은 호출만 어댑터를 호출하고, 끝나면 `completeNotificationClaim()`으로 `delivered`/`failed`로 전이한다 — `failed`는 즉시 재시도 가능(`nextAttemptAt`), 처리 중인 claim은 `lockExpiresAt`(lease, 기본 30초)이 지나야 다른 호출자가 재획득할 수 있다(Worker가 중간에 죽는 경우 대비). `idempotencyKey`는 `${jobId}:${candidateId}:${eventType}:${channel}:${deviceId}:${watchCycle}` 형태로 구성한다(`lib/watch/worker.ts`의 `notifyAll`) — 여러 채널·여러 기기가 같은 이벤트에 대해 각자 한 번씩 알림을 받고, 오직 같은 채널·같은 기기·같은 감시 세대의 완전한 중복만 걸러진다. `WatchJob.watchCycle`은 "다시 감시"를 누를 때마다 1씩 증가하는 서버 생성 세대 카운터라서, 재감시 이후 같은 후보가 다시 발견되면 이전 세대와 겹치지 않는 새 알림이 나간다. 실제 Postgres 구현이 지켜야 할 SQL 패턴(`insert ... on conflict do nothing returning`, 조건부 재획득 `update`)은 `db/postgres/migrations/0001_init.sql`에 문서화했다.
- **이벤트**: `seat_found`, `watch_started`, `watch_expired`, `auth_required`, `provider_unavailable`, `duplicate_job_blocked`, `system_halted`, `booking_confirmation_requested`(타입만 정의, 이번 PR에서 실제로 발생시키는 것은 `seat_found`·`watch_expired` 두 가지뿐 — 나머지는 향후 확장 지점).

## 6. 코레일+ 이동 (`GET /api/watch-jobs/[id]/launch`)

공식적으로 확인된 코레일+ 딥링크 스킴이 없으므로(§F, PR #6 조사) `koreailWebFallbackBookingLaunchProvider`는 절대 딥링크를 지어내지 않는다. 응답은 항상 `deepLinkAvailable: false` + 코레일 공식 웹 주소(`https://www.korail.com/`) + 여정 조건 복사 문구(`copyText`)다. UI는 이 문구를 클립보드에 복사한 뒤 새 탭으로 공식 웹사이트를 연다. 예매 완료 여부는 절대 자동 추정하지 않으며, 사용자가 "예매 완료" 버튼을 눌러야만 작업이 `COMPLETED`로 바뀐다.

## 6-1. 후보 열차 식별자와 정합성 검증

`TrainCandidate.id`는 서버가 `crypto.randomUUID()`로 생성하는 값으로, `db/postgres`의 `watch_job_candidates.id`(uuid 컬럼)와 타입을 맞춘다 — 클라이언트는 이 값을 지정할 수 없다. 클라이언트는 대신 출처 쪽 식별자(v0.3/TAGO 검색 결과 등)를 `externalKey`로 보낸다. `lib/watch/candidate-validation.ts`의 `validateCandidates`가 감시 작업 생성 시 항상 다음을 검증한다: 같은 작업 안에서 `externalKey` 중복 금지, 도착시간이 출발시간보다 뒤여야 함, 후보의 출발일(Asia/Seoul 기준)이 작업의 `date`와 일치, 후보의 출발시각이 작업의 `timeRangeStart`~`timeRangeEnd` 범위 안에 있어야 함. 위반 시 `INVALID_CANDIDATE`로 거부한다.

## 7. 기능 플래그 (fail-closed)

| 이름 | 값 | 기본/취급 |
| --- | --- | --- |
| `SEAT_AVAILABILITY_PROVIDER` | `disabled` \| `mock` | 기본 `disabled`. 값이 없거나 인식할 수 없으면 항상 `disabled`. |
| `ENABLE_SEAT_WATCH_JOBS` | `true`/`false` | 기본 `false`. Worker의 kill switch. |
| `ENABLE_MOCK_SEAT_SIMULATION` | `true`/`false` | 기본 `false`. §4의 검증값 가드 조건 중 하나. |
| `AUTH_STORE` | `disabled`(기본값) \| `memory` \| `postgres` | Production에서는 `memory`를 지정해도 항상 사용 불가 취급(`isAuthStoreUsable`) — 회원가입·로그인·계정삭제·인증 기반 API가 503. |
| `WATCH_STORE` | `disabled`(기본값) \| `memory` \| `postgres` | `AUTH_STORE`와 독립적인 동일한 fail-closed 게이트. Production에서는 감시 작업 생성·기기 등록이 503(`WATCH_STORE_DISABLED`). |

인증(`requireAuth`)은 플래그와 별개로 **모든** watch-job/device 라우트에서 항상 요구된다 — Production 여부와 무관하다. **Mock 시뮬레이션 라우트만** `NODE_ENV==="production"`이면 다른 조건과 무관하게 즉시 503으로 거부된다(`lib/watch/http.ts`의 `isProductionEnvironment`/`productionSimulationBlockedResponse`). 감시 작업 생성·기기 등록은 `AUTH_STORE`와 별개로 `WATCH_STORE`가 usable하지 않으면(Production 기본값) 503으로 거부된다 — 위 §2의 "Provider 미연결이어도 감시 조건은 등록 가능"이라는 설계는 유지하되, 이제는 **영속 저장소가 실제로 연결된 뒤에만** 그 등록이 허용된다(이전에는 인메모리 저장소가 Production에서도 조용히 동작해, 재시작하면 사라지는 감시 작업을 실제로 저장된 것처럼 보여줄 위험이 있었다).

## 9. UI

`app/page.tsx`의 자동예약 탭은 `components/watch-jobs.tsx`로 전면 교체됐다(§4 화면 구성). 로그인하지 않은 사용자에게는 로그인 안내만 보여준다. 로그인 후에는 (1) 알림 수신처 등록, (2) 감시 작업 등록 폼, (3) 진행 중인 감시 목록, (4) 좌석 발생 카드 순으로 구성된다. 화면 상단에 "RailFlow는 승차권을 판매·결제하지 않는다", "실제 좌석·결제는 코레일+에서 확인해야 한다", Provider 미연결 시 "실시간 감시가 작동하지 않는다"는 안내가 항상 표시된다. `components/auth-panel.tsx`는 마이페이지 탭에 추가된 RailFlow 자체 계정 로그인/회원가입/로그아웃/계정삭제 UI다(코레일 계정과는 다른, 이 앱 자체의 계정임을 문구로 명시).

v0.3의 데모 자동예약(로컬스토리지 `reservations`)과 v0.4의 Mock 예약 작업 패널(`components/reservation-jobs.tsx`, `/api/reservations/**`)은 코드·테스트 모두 그대로 남아 있지만, 자동예약 탭에는 더 이상 렌더링되지 않는다(§4 "자동예약 탭을 다음 구조로 변경해라"에 따른 교체). `app/page.tsx`의 "바로예약/자동예약" 버튼(데모 열차용)은 이제 자동예약 탭으로 이동해 새 감시 등록 폼을 쓰라는 안내만 띄운다 — 예전처럼 로컬스토리지 목록에 조용히 추가하고 끝나지 않는다.

## 10. §6 보안 요구사항 대응

| 요구사항 | 구현 |
| --- | --- |
| 인증되지 않은 사용자의 작업 접근 차단 | 모든 watch-job/device 라우트가 `requireAuth` 필수 |
| 모든 조회·수정에서 사용자 소유권 검사 | `getWatchJob(id, userId)`가 다른 사용자의 작업을 `NOT_FOUND`로 취급(§ 아래) |
| 다른 사용자의 작업 ID 추측 접근 차단 | 위와 동일 — id는 맞지만 소유자가 다르면 "존재하지 않는 id"와 구분되지 않는 응답 |
| Rate Limit | 모든 POST 라우트에 `lib/security/rate-limit.ts`의 공유 in-memory 제한기 적용(개발/테스트 전용, § 남은 위험) |
| 입력값 검증 | 모든 라우트가 Zod 스키마로 파싱, 후보 열차는 `validateCandidates`로 추가 검증(§6-1) |
| 알림 수신처(Device) 안전한 노출 | API/UI는 원문 `token`을 절대 반환하지 않고 `maskedDestination`만 노출(`DeviceSummary`). 저장 자체는 이번 PR도 평문 메모리다 — Postgres 전환 시 저장 단의 암호화는 별도 과제(§ 남은 위험) |
| 알림 채널·기기·소유권 검증 | `notificationMethods[].channel`이 Device.channel과 다르면 거부, 소유권 미확인(`verified: false`) 수신처는 실제 발송 안 함 |
| 작업 생성·취소 감사 로그 | `AuditEvent`(`watch_job_created`/`_cancelled`/`_completed`, `user_signup`/`_login`/`_logout`/`_deleted`, `device_registered`), 계정 삭제 시 `userId` 가명처리(§8) |
| kill switch | `ENABLE_SEAT_WATCH_JOBS=false`, 그리고 `AUTH_STORE`/`WATCH_STORE`가 각각 독립적으로 Production을 차단 |
| Provider 장애 시 fail-closed | `SEAT_AVAILABILITY_PROVIDER` 미인식 값은 항상 `disabled` |
| 사용자 데이터 삭제 기능 | `DELETE /api/auth/account`, 비밀번호 재확인 필수(§1) |
| Production에서 Mock 기능 차단 | `POST /api/watch-jobs/[id]/simulate`가 Production에서 항상 503 |
| CSRF | Production에서 쿠키 인증 상태 변경 라우트 전체에 `APP_ORIGIN` 기반 전체 Origin 검증(`lib/security/origin-guard.ts`) 적용(Host 헤더 비교가 아님, 스킴까지 비교), 세션 쿠키는 `sameSite: "lax"` |
| 세션 토큰 노출 방지 | 로그인/회원가입 응답 JSON에 토큰을 담지 않는다 — httpOnly(+Production은 `__Host-`) 쿠키로만 전달 |

## 11. 의도적으로 구현하지 않은 것

- 실제 잔여좌석 조회(공식 Provider 미연결), 실제 예약·결제, 코레일 계정 자동 로그인.
- 매크로 탐지 회피, 요청 간격 무작위화, User-Agent/IP/프록시/계정 로테이션, 비공개 API 역공학, 화면 자동조작.
- FCM/WebPush/Telegram/Email 실제 발송(외부 계정·서비스 키 없음 — 모두 `NOT_CONFIGURED`로 fail-closed).
- 영속 저장소 연결(Postgres 스키마는 설계만, `db/postgres` 참고). `AUTH_STORE`/`WATCH_STORE`가 모두 기본값 `disabled`이며, `memory`로 설정해도 Production에서는 사용할 수 없다.
- 이메일·텔레그램 등 알림 수신처의 실제 소유권 확인 절차(현재는 등록 즉시 `unverified`로만 표시하고 발송을 막을 뿐, 확인 링크/봇 핸드셰이크 등은 없음).
- Android 네이티브 클라이언트를 위한 별도 토큰 인증 방식(Bearer 등) — 웹 세션 쿠키를 그대로 재사용하지 않기로 했고, 실제 설계는 향후 과제.
- 알림 수신처 저장 단의 암호화(§10 표의 남은 항목). 분산 Rate Limit(Redis/Upstash 등) — 현재는 dev/test 전용 in-memory 제한기뿐(`lib/security/rate-limit.ts`).
- Android 앱 자체(APK/Play 배포) — `docs/ANDROID-MVP-PLAN.md`는 계획 문서만이다.
- 코레일+ 딥링크(공식 확인 전까지 절대 만들지 않음).
