# v0.10 — PostgreSQL 영속 저장소와 Worker 실행 기반

작성일: 2026-09-28.

이 문서는 **"코드가 있다"와 "운영에서 돌고 있다"를 섞어 읽지 않기 위한** 것이다.
v0.10 에서 늘어난 것은 코드와 테스트이고, 운영에서 켜진 것은 없다.

---

## 1. 한 줄 요약

PostgreSQL 저장소 어댑터와 서버 Worker 실행 진입점을 **구현했고, 실제
PostgreSQL 16 에 붙여 계약을 검증했다.** 그러나 운영 DB 는 연결하지 않았고,
Worker 를 주기적으로 부르는 Cron·Queue 도 배포하지 않았다. **실제 좌석 조회·
예약·계정 연결은 여전히 미구현이다.**

---

## 3. 저장소 구현

`lib/autobook/postgres-store.ts` 가 `lib/autobook/store.ts` 의 계약을 구현한다.
메모리 구현과 **같은 계약**이며, 같은 시나리오를 양쪽에 돌린다
(`tests/autobook/store-conformance.mjs`).

### 3-1. 원자적 claim

```sql
WITH picked AS (
  SELECT id FROM autobook_jobs
   WHERE status = ANY($2::text[])
     AND (next_check_at IS NULL OR next_check_at <= $3::timestamptz)
     AND (claim_expires_at IS NULL OR claim_expires_at <= $3::timestamptz)
   ORDER BY next_check_at NULLS FIRST, created_at ASC
   FOR UPDATE SKIP LOCKED
   LIMIT 1
)
UPDATE autobook_jobs j
   SET claim_worker_id = $1,
       last_fencing_token = j.last_fencing_token + 1,
       claim_fencing_token = j.last_fencing_token + 1,
       ...
  FROM picked WHERE j.id = picked.id
RETURNING ...
```

고르는 것과 표시하는 것이 **한 문장 안에** 있다. 두 Worker 가 같은 순간에
불러도 그 사이에 끼어들 틈이 없다. `SKIP LOCKED` 덕분에 서로 기다리지도
않는다 — 작업이 여러 개면 Worker 들이 나눠 집는다.

### 3-2. fencing token

토큰은 `last_fencing_token + 1` 로 **단조 증가**한다. claim 을 놓아도
`last_fencing_token` 은 남으므로 다음 claim 이 더 큰 토큰을 받는다.

모든 claim 기반 쓰기는 이 조건을 단다.

```sql
WHERE id = $1 AND claim_worker_id = $2 AND claim_fencing_token = $3
```

토큰이 뒤처진 Worker 의 UPDATE 는 0행을 고치고, 저장소는 그것을
`STALE_CLAIM` 으로 돌려준다. 잠깐 멈췄다 깨어난 Worker 가 남의 작업을
덮어쓰지 못한다. `scripts/verify-autobook.cjs` 가 `updateJob`·`renewClaim`·
`releaseClaim` **각각**에 이 조건이 있는지 검사한다(한 곳만 보면 다른 함수가
검사를 대신 만족시켜 버린다).

### 3-3. 집을 수 없는 상태

집을 수 있는 상태 목록은 `lib/autobook/state-machine.ts` 의
`CLAIMABLE_STATUSES` 하나이며, 메모리 저장소와 PostgreSQL 저장소가 **같은
목록**을 본다. 다음이 빠져 있는 것은 의도적이다.

- `DRAFT` — 아직 등록되지 않은 작성 중 작업
- `RESERVATION_HELD` / `PAYMENT_PENDING` — 사용자의 결제를 기다린다
- **`RESERVATION_CLAIMING`** — 예약 요청이 이미 나갔다

마지막이 중요하다. v0.9 까지는 이 상태도 집을 수 있었다. 다시 집으면 Worker 가
같은 좌석을 또 노리는 경로가 열린다.

> **알려진 한계.** 예약 요청을 보낸 직후 Worker 프로세스가 통째로 죽으면
> 작업이 `RESERVATION_CLAIMING` 에 남는다. 요청 이후의 불확실성은 요청을 보낸
> Worker 가 예약내역 재조회로 끝내도록 돼 있지만(v0.9), 그 프로세스 자체가
> 사라지면 아무도 확정하지 못한다. 지금은 **사람이 확인해야 한다.** 자동
> 회수(reconciliation) 는 실제 Provider 가 생긴 뒤에 붙이는 것이 맞다 — 지금
> 만들면 확인할 예약내역이 없다.

### 3-4. 파라미터 바인딩

SQL 값은 전부 `$n` 바인딩이다. 문자열 연결로 값을 넣는 곳이 없다.
`updateJob` 의 부분 수정도 **미리 정한 컬럼 표**를 거치며, 호출자가 준 키를
SQL 에 그대로 넣지 않는다. 검증 스크립트가 템플릿 보간을 전수 검사한다.

### 3-5. 오류에 자격증명이 섞이지 않는다

`pg` 의 오류 메시지에는 연결 문자열·호스트·사용자명, 때로는 실패한 SQL 의
파라미터까지 들어간다. `lib/autobook/postgres/client.ts` 의 `redactDbError` 가
**SQLSTATE 코드와 제약 이름만** 남기고 원문을 버린다. 실제 DB 테스트가 던져진
오류에 연결 문자열·사용자명·비밀번호·호스트가 없는지 직접 확인한다.

## 4. Migration

`db/postgres/migrations/0003_autobook_worker.sql` 을 **추가**했다. 0002 는
고치지 않았다 — 이미 적용한 환경이 있을 수 있고 되감기는 위험하다.

| 변경 | 이유 |
|---|---|
| `claim_claimed_at` 컬럼 추가 | "언제 집었는가"와 "언제 마지막으로 썼는가"는 다른 값이다 |
| `autobook_jobs_reservation_idem` UNIQUE | 예약 멱등키의 마지막 방어선 |
| `autobook_jobs_claimable` 재생성 | 실제 claim 쿼리 조건에 맞춤 |
| `autobook_jobs_by_user` | 사용자별 목록 조회 |
| `autobook_jobs_stale_claims` | 죽은 claim 진단 |
| `autobook_notifications_unclaimed` | Outbox 집기 |
| `autobook_audit_pseudonym` | 감사 기록 조회 |

전부 `IF NOT EXISTS` / `IF EXISTS` 다. **반복 실행해도 안전하고**, 테스트가
같은 파일을 두 번 실행해 그 사실을 확인한다. 파괴적 구문(`DROP TABLE`,
`DROP COLUMN`, `TRUNCATE`, `DELETE`)이 없다는 것도 검증 스크립트가 검사한다.

**운영 DB 에는 적용하지 않았다.** 적용 방법은 §9.

### 후보 열차를 별도 테이블로 쪼개지 않은 이유

후보는 언제나 작업과 함께 통째로 읽고 쓴다(한 후보가 확정되면 나머지가 같은
순간에 중단된다). 별도 테이블로 쪼개면 그 원자성을 트랜잭션으로 다시 만들어야
하고 얻는 것이 없다. 0002 의 `candidates JSONB` 를 그대로 쓴다.

## 5. Worker 실행 기반

`lib/autobook/worker-entry.ts` 의 `runAutobookWorkerOnce()` 가 유일한 진입점이다.

### 하지 않은 것

- **공개 HTTP endpoint 를 만들지 않았다.** 그런 주소가 하나 생기면 인증·속도
  제한·재시도 폭주를 그 자리에서 전부 다시 풀어야 하고, 실수로 열려 있으면
  남이 우리 Worker 를 돌릴 수 있다. 검증 스크립트가 어떤 라우트도
  `worker-entry` 를 부르지 않는지 검사한다.
- **Vercel Cron·외부 Queue 를 배포·설정하지 않았다.**

### 멈추는 순서

1. `AUTOBOOK_KILL_SWITCH=on` → DB 에 손도 대지 않고 중단
2. `ENABLE_AUTOBOOK_JOBS` 가 `true` 가 아니면 중단
3. 저장소를 쓸 수 없으면 중단 — **memory 로 후퇴하지 않는다**
4. Provider 가 좌석 조회를 못 한다고 밝히면 외부로 아무 것도 보내지 않고 중단
   (공식 Stub 이면 `OFFICIAL_INTEGRATION_REQUIRED`)
5. 여기까지 통과해야 작업을 진행하며, 한 번에 **최대 5건**이다

검증 스크립트가 이 순서를 소스에서 검사하고, `tests/autobook/worker-entry.test.mjs`
가 각 조건에서 **외부 요청 0회**를 `fetch` 를 가로채 직접 센다.

### 개발용 실행기

`pnpm autobook:worker:dev` (`scripts/autobook-worker-dev.cjs`) 는 진입점을 한 번
부른다. `NODE_ENV=production` 에서는 실행을 거부한다. **운영 배포가 아니다.**

## 6. 저장소 선택과 fail-closed

```
AUTOBOOK_STORE=disabled   # 기본값
AUTOBOOK_STORE=memory     # 개발·테스트 전용. Production 에서는 값과 무관하게 금지
AUTOBOOK_STORE=postgres   # 연결 설정이 있을 때만
```

`AUTOBOOK_DATABASE_URL` 이 있으면 그것을, 없으면 `DATABASE_URL` 을 쓴다.
둘 다 없거나 형식이 틀리면 **실패한 저장소**를 돌려준다. memory 로 자동
후퇴하지 않는 이유는 하나다: 후퇴하는 순간 "서버가 대신 지켜본다"는 약속이
"이 인스턴스가 살아 있는 동안만"으로 조용히 바뀐다.

`kill switch` 는 이 모든 것보다 먼저다.

## 7. 테스트 — 실제로 한 것과 하지 못한 것

### 실제로 실행한 것

| 테스트 | 결과 |
|---|---|
| Memory 저장소 계약 (19건) | **통과** |
| **PostgreSQL 저장소 계약 (24건, 실제 PostgreSQL 16)** | **통과** |
| Worker 실행 진입점·안전 조건 (10건) | **통과** |
| v0.9 Worker·안전 테스트 (35건) | **통과** |

PostgreSQL 통합 테스트는 이 작업 환경에 설치된 PostgreSQL 16.13 로 **임시
테스트 클러스터**를 띄워 실행했다. 운영 DB 에 붙지 않았고, 테스트가 끝난 뒤
클러스터를 정리했다.

실제 DB 에서만 확인할 수 있어 따로 둔 것:

- 동시 Worker 20개가 붙어도 한 작업은 한 번만 집힌다
- 작업이 여러 개면 `SKIP LOCKED` 가 Worker 들에게 나눠 준다
- 연결을 완전히 끊고 다시 붙어도 작업·claim·후보가 그대로다(**서버 재시작 상당**)
- DB 오류에 연결 문자열·사용자명·비밀번호·호스트가 들어가지 않는다
- 예약·알림 멱등키 UNIQUE 가 **저장소를 우회한 직접 INSERT 도** 막는다
- migration 을 두 번 실행해도 안전하다

### 하지 못한 것

- **운영 DB 에서의 검증.** 운영 DB 가 없고, 만들지도 않았다.
- **여러 프로세스·여러 서버에 걸친 동시성.** 한 프로세스 안의 동시 요청으로
  경쟁을 재현했다. 진짜 다중 인스턴스 검증은 Worker 를 배포한 뒤에 해야 한다.
- **장시간 운전.** Worker 는 아직 24시간 돌고 있지 않다.
- **실제 좌석 조회·예약.** Provider 가 Stub 이므로 시도 자체가 없다.

### 다른 환경에서 PostgreSQL 테스트를 돌리는 방법

```
AUTOBOOK_TEST_DATABASE_URL=postgres://<user>@<host>:<port>/<test-db> \
  node --test tests/autobook/postgres-store.conformance.test.mjs
```

이 변수가 없으면 테스트는 실행되지 않고 **NOT RUN** 으로 남는다. 변수 이름이
`DATABASE_URL` 과 다른 것은 의도적이다 — 테스트가 자동예약 테이블을
`TRUNCATE` 하므로 운영 DB 를 절대 가리키면 안 된다.

**Memory 저장소 테스트 통과는 PostgreSQL 검증이 아니다.**

## 8. 화면과 상태 API

`/api/autobook/status` 의 `readiness` 가 다음을 **각각 다른 필드로** 내보낸다.

- `postgresStoreImplemented` — 어댑터 코드가 저장소에 있는가
- `postgresConfigured` — 이 환경에 연결 설정이 있는가
- `postgresConnected` / `postgresConnectionChecked` — 실제로 연결되는가
- `workerEntrypointImplemented` — 실행 진입점 코드가 있는가
- `workerScheduleConfigured` — Cron·Queue 가 그것을 부르도록 배포됐는가
- `officialProviderConnected` — 공식·승인된 Provider 가 연결됐는가
- `liveReservationPossible` — 실제 예약이 일어날 수 있는 조합인가

**연결 문자열은 어떤 형태로도 응답·화면·로그에 담기지 않는다.** 설정이 없거나
형식이 틀렸을 때도 이유 코드만 나간다.

실제 감시 작업 등록 버튼은 계속 비활성이며, 비활성 사유는 다음을 유지한다.

- 공식 연동 Provider 없음
- 계정 연결 방식 없음
- **Worker 운영 배포·스케줄 미설정**
- 영속 DB 미연결 (어댑터 코드는 있지만 이 환경에 연결 설정이 없다)

## 9. 다음 단계에서 준비해야 할 것

### 반드시 필요한 것

1. **PostgreSQL 인스턴스 하나.** 관리형(Neon·Supabase·RDS 등) 어느 쪽이든
   된다. 필요한 것은 연결 문자열 하나뿐이다.
2. 그 연결 문자열을 **서버 Secret** 으로 등록 (`AUTOBOOK_DATABASE_URL`).
   이 저장소의 파일이나 채팅에 적지 않는다.
3. `0002_autobook.sql` → `0003_autobook_worker.sql` 순서로 migration 적용.
4. **Worker 를 주기적으로 부르는 것.** Vercel Cron, 별도 Node 프로세스,
   Queue 소비자 중 하나. 이 선택은 비용과 운영 방식이 달라 사용자 결정이 필요하다.

### 선택 사항

- `AUTOBOOK_AUDIT_SALT` — 감사 가명의 salt. 없어도 동작하며, 있으면 배포별로
  가명이 달라진다.
- `AUTOBOOK_DATABASE_URL` 을 `DATABASE_URL` 과 분리할지. 자동예약만 별도
  인스턴스로 두고 싶을 때만 필요하다.

### 이것을 다 해도 되지 않는 것

**실제 좌석 조회와 예약은 여전히 되지 않는다.** 그것은 DB 나 Worker 의 문제가
아니라 **공개·승인된 연동 명세를 확보하지 못한 문제**다
(`docs/V0.9-KORAIL-INTEGRATION-RESEARCH.md`). 인프라를 먼저 갖추더라도
그 조사 문서의 §6 1번 — **코레일 공식 "예약대기"로 충분한지** — 을 확인하는
것이 여전히 먼저다.

## 10. 바뀌지 않은 원칙

- 실제 코레일·SR 사이트로 요청하지 않는다.
- 비공개 endpoint 를 추측하지 않는다.
- 브라우저 자동화로 공식 예매 화면을 조작하지 않는다
  (`docs/adr/0003-abandon-browser-agent.md`).
- 쿠키·세션을 추출하거나 저장하지 않는다.
